api_gateway_service — Spec

Requirements, personas, acceptance criteria, constraints.

Overview Spec Architecture Design Decisions
1Personas

Employee - every request from them passes through here first, invisibly; they should never notice the Gateway exists except when it rejects something. Admin - same path, different role claims. A future service builder - adds a new backend behind the Gateway by registering one route-to-service mapping, not by re-implementing RBAC/CORS/rate-limiting themselves.

2Functional requirements
  • MUSTValidate every request's user_profile role against the target route's allowed roles before forwarding - same contract require_role() already enforces today.
  • MUSTReject cross-origin requests from anything but hrb-chatbot-ui.rvsree.dev - same policy main.py's CORSMiddleware already enforces today.
  • MUSTRate-limit per employee_id, backed by Redis so the limit holds across Gateway replicas, not just in one process's memory.
  • MUSTForward every request to the correct backend service by path prefix, with the original request body/headers intact except an added request_id.
  • SHOULDValidate the outbound request body against the target backend's declared Pydantic contract before forwarding, returning a 422 at the Gateway rather than letting a malformed request waste a backend round-trip.
3Non-functional requirements
  • Added latency: under 20ms p95 for the Gateway's own validation/routing logic - it sits on every single request, so its own overhead compounds.
  • Availability: ≥2 replicas from day one - every request flows through this one service, so it cannot be a single point of failure the way "one busy admin feature" can tolerably be.
  • Statelessness: no in-process session storage - session/rate-limit state lives in Redis, so any replica can serve any request.
4Acceptance criteria
  • A request with a role not permitted on the target route gets a 403 from the Gateway, and the backend service never sees the request at all.
  • 60 requests in 60 seconds from one employee_id past the configured limit get a 429, and the limit holds even when tested against 2 different Gateway replicas.
  • Stopping rag_retrieval_service entirely and sending it a request through the Gateway returns a clean 503 with a typed error body, not a hung connection or a raw stack trace.
  • The existing Postman collection's happy-path requests, pointed at the Gateway instead of directly at hrb_chatbot_service, pass unchanged.
5Constraints
  • Python 3.12, FastAPI - matches every other service, no new framework introduced for just this one.
  • Identity stays self-asserted (user_profile in the body) until real OAuth2 lands - this service does not silently upgrade the security model beyond what's already decided (see Decisions).
  • Depends on hrb_common_libs[observability,db,cache,auth] only - never llm or mcp (see Common-Libs Connectors doc).
