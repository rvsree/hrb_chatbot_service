CS-16 LangChain splitters + 1 own, no custom reimplementation
Context
Text splitting is a well-covered problem; LangChain already ships several real splitter implementations.
Decision
fixed / recursive / semantic / markdown / html are thin wrappers over LangChain's own CharacterTextSplitter / RecursiveCharacterTextSplitter / SemanticChunker / MarkdownHeaderTextSplitter / HTMLHeaderTextSplitter - only document_structure is this project's own logic, since it depends on this project's real KB heading format.
Why
Matches the workshop's own Module 2 approach directly - six plain functions, no classes, nothing reinvented that a maintained library already does well.
CS-2Tables always pulled out, kept whole
Context
A table split mid-row by a size-based chunk boundary becomes unreadable noise at retrieval time, regardless of which strategy caused it.
Decision
Every [TABLE]...[/TABLE] block is removed before any strategy runs and reattached afterward as its own whole chunk - the rest of the document's chunk sizing isn't influenced by table size either.
Why
A table's internal structure matters more than uniform chunk sizing; no strategy needs to special-case tables since they never see them.
CS-3semantic / document_structure stay explicit-only
Context
semantic costs one embedding call per sentence - real money per document. document_structure would actually fire for nearly every real KB document if auto-selected (they all use the real "Section N:" heading format).
Decision
Neither is reachable from decide_chunking_strategy() - both only run when a caller names them directly.
Why
semantic: cost control, not a correctness issue. document_structure: auto-enabling it risks silently shifting golden-dataset scores on a routine re-index - kept opt-in deliberately, not an oversight.
CS-4Oversized-chunk safety net on every strategy
Context
Phase 149 built _split_oversized_chunks() for semantic alone - it has no size ceiling of its own, so a topically-uniform document could collapse into one or two 15K+ character chunks, diluting their embeddings.
Decision
Phase 156 extended the same safety net to markdown/html/none too - every strategy now respects a caller-given chunk_size, not just the 3 that take it as a direct split target.
Why
A big document under none, or PDF-extracted text with no real markdown/HTML headers under those 2 strategies, hit the exact same uncapped-giant-chunk problem - one shared fix, not three separate ones.
CS-5Chunk size auto-scales for large documents
Context
A long document at the default 1000-char chunk size fragments into 10+ tiny pieces, each losing surrounding context the next piece has.
Decision
decide_chunk_size() bumps the target to 1500 chars once the table-free text exceeds 10,000 characters - only ever grows past the default, never shrinks it.
Why
Tables no longer factor into this decision either - each becomes its own whole chunk regardless of size, so there's no need to inflate chunk size for the rest of the document just because one table happens to be large.
CS-6section_id derived from heading text, not number
Context
document_structure tags each chunk with a section_id so retrieval can cite which section a chunk came from.
Decision
The id is a slug of the heading's own text (e.g. eligibility), not its number (e.g. section-2).
Why
A document renumbered on a later edit (section 2 becomes section 3) keeps the same stable section_id as long as the heading text itself doesn't change - a number-based id would silently break every existing citation pointing at that section.
