Chunking Strategy

Turning one document's extracted text into appropriately-sized pieces before embedding - 7 real strategies, auto-selected by content shape, override-able per document.

Overview Spec Design Decisions

Purpose

How a chunk is drawn matters as much as what embeds it - too small and a chunk loses context, too large and its embedding gets diluted across unrelated ideas. This feature is the real chunking layer: text_chunker.py's 7 functions, each a different technique (fixed-size, recursive, semantic, markdown/HTML headers, whole-document, or this project's own document-structure splitter), picked automatically from the document's shape or chosen explicitly per document from the Documents page.

Every table extracted from a PDF is pulled out before any strategy runs and kept as its own whole chunk afterward - no strategy, auto-picked or explicit, is ever allowed to split a table across a chunk boundary.

Scope

Covers all 7 real strategies (fixed, recursive, semantic, markdown, html, none, document_structure), the auto-selection logic that picks one when a caller doesn't (decide_chunking_strategy()), chunk-size auto-scaling for large documents, the oversized-chunk safety net every strategy now respects, and the Documents page's own per-document re-chunk control (re-embeds and re-indexes with a new strategy on demand).

Does not cover embedding generation or vector-store writes themselves - those are embedding_generator.py/vector_indexer.py's own jobs, called right after chunking finishes.

High-level workflow

  1. 1Tables pulled out - every [TABLE]...[/TABLE] block is set aside before any strategy sees the text.
  2. 2Strategy resolved - explicit if the caller gave one, otherwise auto-picked from markdown/HTML heading sniffing or document length.
  3. 3Chunk size resolved - explicit if given, otherwise auto-scaled up for long documents.
  4. 4Strategy runs - one of the 7 functions splits the table-free text.
  5. 5Oversized-chunk safety net - any chunk still over the resolved size gets re-split recursively.
  6. 6Tables reattached - each table block comes back as its own whole chunk, appended after the prose chunks.

Where this fits in the HR Benefits RAG system

Called from ai/doc_processing/pipeline.py::index_document() on every document upload, and again from the Documents page's "Chunking Strategy" dropdown whenever HR Support explicitly re-chunks an already-indexed document (POST .../documents/{document_id}/rechunk) - same underlying function either way, just whether chunking_strategy is auto-picked or caller-given.
