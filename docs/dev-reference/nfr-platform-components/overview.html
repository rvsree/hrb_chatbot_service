NFR Components

The cross-cutting resiliency, security-baseline, and observability patterns every microservice inherits rather than reinvents - a prerequisite layer, built before any new service's business logic.

Overview Spec Architecture Design Decisions

Purpose

Splitting hrb_chatbot_service into multiple services (api_gateway_service, rag_ingestion_service, rag_retrieval_service, chat_audio_service, employee_401k_service) means every one of them independently needs retry/backoff on flaky calls, a circuit breaker on a dependency that's down, structured logging with a correlating request_id, and a security baseline (secrets in Secrets Manager, never plaintext env; no service trusts an unsigned identity it didn't itself validate). Building each of these five times, once per service, is how services silently drift - one gets a circuit breaker, another doesn't, and an outage three weeks later is debugged blind because only two of five services actually log request_id. This document defines the one shared shape, built once, before the services that depend on it.

Scope

Covers four concerns, each already proven somewhere in the current codebase and being promoted from "one service's local pattern" to "every service's shared baseline": Resiliency (retry/backoff and circuit breaking - the MCP integration's Phase 185 circuit breaker is the real precedent, not a new design), Observability (structured logging via call_logger.py's pattern, request_id/response_id propagation from Phase EX-1, LangSmith tracing hooks), Security baseline (Secrets Manager-backed config - already this project's convention - plus the identity-validation contract every service must apply to whatever the Gateway forwards it), and Caching primitives (the Redis connection/key-naming convention the answer cache and embedding cache already use).

Does not cover RBAC/CORS/rate-limiting logic itself - that's api_gateway_service's own business logic, built on top of this layer, not part of it. Does not cover per-service NFR specifics (e.g. rag_ingestion's file-size validation) - those live in that service's own Design doc.

High-level workflow

  1. 1A service's entry point extracts or generates a request_id and attaches it to its logger context for the lifetime of the request.
  2. 2Every outbound call (DB, vector store, LLM provider, another service) goes through a retry/backoff wrapper with sane defaults, overridable per call site.
  3. 3A dependency that fails repeatedly trips a circuit breaker - the same consecutive-failure-count + cooldown pre-flight check Phase 185 already proved for MCP calls, generalized.
  4. 4Every log line and trace carries the request_id, so one failure is traceable across service boundaries in LangSmith and CloudWatch alike.
  5. 5Secrets are read through one settings helper that only ever resolves from Secrets Manager/env, never a hardcoded default.

Where this fits in the microservices rollout

This is Phase 0 work, alongside the schema migration and the hrb_common_libs package extraction (see microservices-rollout-plan.html) - it has to exist before api_gateway_service or any split RAG service is built, because every one of them is written to depend on it from its first commit, not retrofitted after.
