Request Unpaid Leave

A real human-in-the-loop workflow - a leave request that genuinely pauses for a specialist's decision, then resumes and notifies the employee.

Overview Spec Architecture Design Decisions

Purpose

Four leave types - Unpaid, Critical CareGiver, STD, LTD - always need a real human specialist's judgment, not an automated approval. This feature is that path: an employee submits a structured request with an optional supporting document, a small LangGraph workflow validates it and generates a plain-English summary for the specialist, then the graph genuinely pauses - not a polling loop, a real suspended process, checkpointed to Postgres - until an HR specialist reviews the summary and the original document and decides. The graph then resumes from exactly where it stopped, records the decision, and emails the employee.

This is this project's most complete real-world A2A/HITL showcase: two LLM calls (intake validation, specialist-facing summary) bracket one genuine human decision that is never an LLM call at all.

Scope

Covers the full lifecycle: document upload to a private, separate S3 bucket, request submission through the intake graph, specialist review (a queue of pending requests, each with an AI-generated brief and a link to the real document), resolution that resumes the paused graph and sends a decision email, and an employee-facing view of request status and HR comments. Also covers admin-only data cleanup (listing and hard-deleting requests), kept deliberately separate from the HR decision path itself.

Does not cover the other, simpler leave types (PTO, Sick, Sabbatical, Maternity, Paternity) that just need a regular manager's approval, not specialist review - those follow a different, simpler path this feature doesn't touch. Also deliberately not built into the GenAI Chat Workflow's attach-files popup, which has no MCP access by design.

High-level workflow

  1. 1Submit - an employee fills out the Request Leave form, optionally attaching a supporting document first.
  2. 2Validate & file - the graph checks eligibility and creates the real leave request and HITL request via MCP.
  3. 3Summarize - one LLM call writes a plain-English brief for the specialist - no recommendation, just context.
  4. 4Pause - the graph genuinely suspends here, checkpointed to Postgres, for however long it takes a human to respond.
  5. 5Specialist decides - an HR specialist reads the brief and the original document, approves or rejects.
  6. 6Resume & notify - the same graph run resumes, records the decision, emails the employee, and logs the email as a produced artifact.

Where this fits in the HR Benefits RAG system

This sits apart from the RAG retrieval modes entirely - it's not a chat question, it's a structured workflow with a real pause for human judgment. It shares the hrb_lms_mcp A2A connection the retrieval modes also use for GetLeaveBalance/GetLeaveHistory, but goes further: those modes only ever read live data, this feature writes it, through a genuine multi-day-capable workflow. It's the system's clearest demonstration of HITL done for real, not simulated with a status flag.
