2
State machines

leave_requests.status (the graph's own state, mirrors where the LangGraph run currently is):

PENDING_HITL→ APPROVED or REJECTED

hitl_requests.status (the review-queue record's own state):

PENDING→ COMPLETED

The two stay in sync via resolve_unpaid_leave_decision() - resolving the HITL request is what moves the leave request out of PENDING_HITL in the same transaction, never two independent writes.

unpaid_leave_documents.leave_request_id is deliberately nullable - the upload happens before the leave request exists (the manifest row is created at upload time, keyed by upload_token, then linked once /request succeeds). specialist_leave_reviews links to both hitl_requests and leave_requests directly, so either side reaches a review without a join through the other.

4
Real constraints
ConstraintEnforcement
Document ownershipDownload endpoint checks caller is the document's owner OR hr_support/admin - 403 otherwise. Role alone never proves "may see this specific record."
Resolve is HR_SUPPORT-onlyDeliberately not opened to ADMIN - see Decisions RUL-6.
S3 key layout{leave_type_code}/{employee_id}/{leave_request_id}/{filename} inside the dedicated private bucket.
Repeat-request checkSame leave_type only - a 2nd STD request within 12 months flags as repeat; a CCG request doesn't affect an unrelated STD check.
Assignment modelShared queue, not per-specialist claim - any hr_support persona can resolve any pending request. hr_specialist_employee_id records who actually resolved it, not a pre-assignment.
