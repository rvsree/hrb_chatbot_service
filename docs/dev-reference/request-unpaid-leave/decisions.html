RUL-1A new entry point, not the GenAI Chat Workflow popup
Context
The original ask described something like the attach-files popup extended to handle leave requests.
Decision
A genuinely new entry point ("Request Leave" form), not an extension of the GenAI Chat Workflow.
Why
adhoc_document_agent.py's own docstring is explicit: that agent has "no vector store or MCP access, by design." A leave request fundamentally needs MCP (to call create_leave_request/create_hitl_request). Building it into that popup would mean reversing a foundational scoping decision of a different, already-shipped feature - not extending it.
RUL-2Postgres checkpointing, not an in-memory wait
Context
A request can sit pending for hours to days before a specialist reviews it - across however many App Runner instances happen to be running, and through any redeploy in between.
Decision
AsyncPostgresSaver checkpoints the entire graph state to Postgres at the interrupt() point; resume_unpaid_leave_decision() resumes the exact same run later, not a fresh invocation.
Why
This is real transactional business-process data that must never silently vanish and must be consistent regardless of which instance eventually handles the resume - a strictly stronger durability requirement than an in-memory or single-process wait could satisfy.
RUL-3No new table in hrb_chatbot_v2
Context
The natural instinct when adding a feature is often a new local table to track its state.
Decision
All request/review state lives in hrb_lms_mcp's own Postgres schema (leave_requests, hitl_requests, specialist_leave_reviews) - this project's own side queries live via MCP each time, with no local cache table duplicating data the other service already owns.
Why
A cache table here would just be a second source of truth for the same data, with its own staleness problems - the same reasoning this project already applies to its own gateway/enum patterns elsewhere.
RUL-4A separate private S3 bucket, not the KB ingestion path
Context
RAG Ingestion already has a working presigned-upload pattern; reusing it directly would have been the fastest path.
Decision
A new, separate, private bucket for leave documents - the presigned-upload pattern is reused, the bucket is not.
Why
The KB ingestion path embeds uploaded content into the shared vector index. A medical certificate or supporting document for a leave request must never end up retrievable by every other employee's RAG query - the two document types have fundamentally different access requirements, even though the upload mechanics look similar.
RUL-5HR_SUPPORT excluded from submitting its own requests
Context
Before this fix, an hr_support persona could submit a leave request through the same flow employees use - confirmed live as a real gap, not theoretical.
Decision
require_role(EMPLOYEE, MANAGER, ADMIN) on upload-url/request/my-requests - HR_SUPPORT deliberately excluded from all three.
Why
HR_SUPPORT's role in this feature is reviewing and deciding on other people's requests (/pending, /resolve), not filing their own through the same entry point.
RUL-6ADMIN can clean up data, cannot resolve a decision
Context
Phase 178's RBAC superuser sweep added ADMIN to most routes in this file (upload-url, request, my-requests, pending, list-all, delete) - but deliberately not /resolve.
Decision
/resolve stays require_role(HR_SUPPORT) only - the one real HR-decision action in this feature is not opened to ADMIN.
Open tension, flagged not resolved
This directly conflicts with "admin is a superuser, reaches every feature" - the design reasoning here ("admins manage/clean up data, they don't make HR decisions," from LeaveReviewModal.tsx's own Phase 168-round-3 design) is sound on its own, but it's a real exception to the superuser pattern applied everywhere else, noted directly in the route's own code rather than silently decided either way.
