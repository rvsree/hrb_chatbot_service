ASC-1Add a masked secret-code field, on top of self-asserted RBAC
Context
Every role in this project, including admin, was selected by the caller and trusted immediately - is_known_persona() only checked that the id/name/role triple matched a known row. Anyone who knew ADM001/"Sree Rad" from the public KNOWN-PERSONAS.md table could select Admin with nothing further - including, during a live demo, anyone watching the screen.
Decision
Add an optional secret_code field to LoginRequest, checked only when role == "admin", rendered as a native type="password" input so it's masked on screen.
Alternative
Leave RBAC as the only gate (do nothing) - rejected, since admin is the one role that can hard-delete data outright; every other role is read-mostly or scoped to the caller's own records.
Why
A masked field is the smallest possible addition that (a) isn't visible on screen during a demo and (b) can't be bypassed just by knowing the public persona roster, without touching this project's documented "RBAC is a formality" stance anywhere else.
Trade-off
This still isn't real authentication - it's one extra speed bump for the single highest-blast-radius role, not a security boundary. Explicitly documented as such, not oversold.
ASC-2One-time seed code that forces a reset, not a fixed demo credential
Context
Phase 169's first version stored the secret code as a plaintext literal in known_personas.py, compared with a plain == - functional, but a fixed value sitting in source control forever, with no path to ever actually change it.
Decision
A one-time seed code (the literal value is intentionally not documented here - see ADMIN_ONE_TIME_SEED_SECRET_CODE in api/auth/login.py) is used only the very first time admin_credentials has no row for an employee_id; that login always comes back with must_reset_secret_code: true, and a dedicated POST /v1/admin/reset-secret-code route (reachable only by an already-authenticated admin) is the only way to clear that flag.
Alternative
Keep a single fixed code indefinitely (simpler, no reset flow to build) - rejected: a credential that can never change is a standing liability the moment it's ever shared or exposed, which is exactly what happened to it appearing in example documentation this same session.
Why
Forcing a reset on first use means the seed value is bootstrap-only by construction, not by convention - there's no way to keep relying on it past the first login, so documenting it (even accidentally) doesn't grant standing access.
Trade-off
Adds a real stateful flow (a reset endpoint, a must_reset column, UI routing on login) for what's conceptually a one-line credential check - more code than the simplest possible version, justified by removing a standing-liability credential.
ASC-3Salted SHA-256 (stdlib) over bcrypt/argon2, and over OAuth2/JWT entirely
Context
With the plaintext storage flagged (ASC-2's own context), three real options existed: a proper slow password hash (bcrypt/argon2), stdlib-only salted SHA-256, or reframing the whole problem as OAuth2/JWT. The OAuth2/JWT question was asked directly.
Decision
Stdlib hashlib/secrets/hmac only - SHA-256 of salt + secret_code, a fresh random salt per seed/reset, compared with hmac.compare_digest() (constant-time). No new dependency.
Alternative
bcrypt/argon2 - deliberately-slow hashing, the real-world standard for password storage. OAuth2 - solves delegated third-party authorization, which isn't this problem (there's no third party involved). JWT - a session-token format, a real but separate gap (this project's own documented "role is self-asserted on every request" limitation), not a storage mechanism for the secret itself.
Why
bcrypt/argon2 would add a new dependency this project's own "no unreviewed libraries without approval" standard gates, for a benefit (brute-force resistance against an offline hash-cracking attempt) that doesn't move the needle for one admin passphrase in a capstone demo. SHA-256+salt+constant-time-compare already defeats the two realistic threats here: casual reading of the stored value, and a timing attack on the compare itself. OAuth2/JWT solve different, real, but unrelated problems - conflating them with this one would have been scope creep, not a fix.
Trade-off
Explicitly weaker than bcrypt/argon2's deliberate slowness against a real offline brute-force attempt on a leaked hash. Accepted as proportionate for this feature's actual blast radius (one demo-project admin passphrase), not presented as production-grade password security.
ASC-4Store the credential in its own Postgres table, not a field in code
Context
Phase 169's plaintext code lived as a literal field on ADM001's entry in known_personas.py - the same file that defines every other (non-secret) persona, checked into source control.
Decision
A new, dedicated admin_credentials table, same Postgres connection and psycopg/asyncio.to_thread() pattern every other store in this project already uses (feedback_store.py, conversation_store.py). known_personas.py's own secret_code key was removed entirely - the DB table is now the only source of truth.
Alternative
Keep the hash in code (e.g. a constant in known_personas.py) instead of a new table - simpler, no new store class - rejected: a hash committed to source control is still visible to anyone with repo access, and can't support the reset flow (ASC-2) without a redeploy every time the code changes.
Why
Matches this project's own established pattern of one gateway-backed store per concern, keeps the credential mutable at runtime (required for reset), and keeps anything secret out of version control entirely - the only thing in source control now is the seed value's one-time bootstrap use, not the real operating credential.
Trade-off
A new table for exactly one row is more infrastructure than the problem strictly needs at today's single-admin scale - accepted because it costs nothing extra (same connection, same pattern already paid for by other stores) and removes the redeploy-to-rotate problem the in-code alternative would have kept.
