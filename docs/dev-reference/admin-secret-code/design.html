Admin Secret Code

The real wire shapes and the one table this feature owns - grounded directly in models/auth.py, api/auth/login.py, and admin_credential_store.py, not re-derived from memory.

2
DB schema admin_credentials - the one table this feature owns
ColumnTypeNotes
employee_idPKTEXTAlways ADM001 today - one row total. PK rather than a surrogate id since there's exactly one credential per admin identity.
secret_code_hashTEXT NOT NULLsha256(salt + secret_code), hex-encoded. Never the plaintext code.
secret_code_saltTEXT NOT NULLsecrets.token_hex(16), regenerated on every seed/reset - a fresh random salt each time, not reused across rows (moot today with one row, but correct practice regardless).
must_resetBOOLEAN NOT NULL DEFAULT TRUETrue only while the stored code is still the one-time seed; flips to false the moment a real reset succeeds.
updated_atTIMESTAMPTZ NOT NULL DEFAULT now()Bumped on every successful reset - not on a login/verify, which never writes.

Postgres only - same connection feedback_store.py/conversation_store.py already use, same psycopg + asyncio.to_thread() pattern as every other store in this project. No SQLite path - this table didn't exist before the metadata store migrated to Postgres in production, so there was no legacy SQLite shape to also support.

3
Key flows step-by-step, in plain language
First-ever admin login
1No admin_credentials row exists for ADM001 yet.
2get_or_seed() inserts one, hashing the one-time seed code, must_reset=true.
3Login succeeds if the caller's code matches the seed; response flags must_reset_secret_code: true.
4UI routes to the reset screen before normal use continues.
Every login after that
1A row already exists - get_or_seed() returns it unchanged, no write.
2verify_secret_code() hashes the caller's candidate with the stored salt and compares.
3Match -> 200 with must_reset_secret_code: false. No match -> 401, no row touched.
4
NFR - narrow, feature-scoped system-wide scaling/security lives in scaling-latency-design.html - this is only what's specific to this one feature
NFRBuilt (today)Target / known gap
Credential confidentialitySalted SHA-256 hash, never plaintext, constant-time compareDeliberately not deliberately-slow (bcrypt/argon2) - proportionate for one admin passphrase, not a password system at real user-scale (see Decisions)
Brute-force resistanceGlobal Redis-backed rate limiter (APP_RATE_LIMITING) applies to this route like every otherNo dedicated lockout-after-N-failed-attempts specific to this one credential
AvailabilitySingle Postgres row read on every login - negligible load, scales with the whole metadata store (Panel 7, system-wide doc)N/A - this is the lightest-weight table in the whole schema
Multi-admin supportNot built - employee_id as PK assumes exactly one admin identityWould need the PK to stay a real key (it already is) plus an admin-management UI - not currently a requirement
5
Known limitations

Single hardcoded persona (ADM001) - adding a second admin means a second known-personas row plus a second admin_credentials row, not a schema change (the table already supports it, nothing in the design assumes exactly one row - only today's product scope does). Role itself stays self-asserted in the request body, unchanged by this feature (documented project-wide, api/gateway/rbac.py) - this only raises the bar for successfully claiming the admin role, not for every request afterward.
