HRB Chatbot ⇄ 401(k) Loan Agent — Integration & Isolation

Assuming "HRB 401k Manager" is built and running as its own separate A2A service (per design.html), this is how hrb_chatbot_v2 (backend + frontend) extends to talk to it — with a hard isolation boundary so none of this code path intermixes with the existing RAG/agentic features.

00

Correction from revision 1 — naming

What was wrong

Revision 1 of this doc named every new backend/frontend artifact with an a2a_/A2A_ prefix — api/a2a_401k/, services/a2a_401k_service.py, A2A_401K_LOAN_AGENT_URL, route /v1/a2a-401k. That bakes a transport protocol (A2A) into business-domain names, and it's inconsistent with how this project already names things: github_actions_client.py is named for the target (GitHub Actions), not the transport (REST); HRB_LMS_MCP_URL leads with the business system name, with the protocol only a trailing qualifier. A2A is an implementation detail of how this project happens to reach the Loan Agent today — the business concept (processing a 401(k) loan request) doesn't depend on it and shouldn't be named after it. It's also a real Python issue, not just style: a package can't be named starting with a digit, so even 401k_loans alone wouldn't import.

Fixed — naming used from here on

Business-layer code (routers, services, models, routes, settings) is named loan_401k / LOAN_401K — domain first, no protocol prefix. The one place a protocol name is legitimate is the literal transport client, same as this project's own oauth_client.py/mcp_tools/ precedent — and even there, the file is named for the counterparty it talks to (loan_401k_agent_client.py), not for the wire format alone.

The one rule that keeps this isolated

  • Dependency direction is one-way. loan_401k/* may import shared primitives (models/common.py's UserProfile, api/dependencies.py's json_error, the RBAC gateway) — the same way every existing router already does. Nothing in ai/rag_pipeline/* or ai/agents/* imports anything from loan_401k/*. If that direction ever reverses, the isolation is broken.
  • New router, mounted separately. app.include_router(loan_401k_router, prefix="/v1/401k-loans", dependencies=[...]) in main.py — one new line next to the existing router mounts, same Phase 23 gateway-at-mount-level pattern already used for everything else. Its own RBAC rule, not reusing an existing one verbatim (loan requests need EMPLOYEE write access that documents/ingestion don't grant today).
  • New settings, own prefix — business name first. LOAN_401K_AGENT_URL, LOAN_401K_CLIENT_ID/_SECRET — same shape as the existing HRB_LMS_MCP_URL/HRB_LMS_MCP_OAUTH_* settings (business system name leads, protocol is never the primary identifier), not folded into any existing settings group.

Why 2 new pages, not 2 new tabs on existing ones

Folding the specialist-review UI into AdminDashboardPage.tsx as another tab would repeat exactly the mistake already caught and fixed once this session (the "Build & Deployment" menu item that turned out to be a reskinned Admin Dashboard, not a real separate surface). A dedicated route, dedicated component, dedicated data-fetch — same pattern the fixed /deployments route now uses (standaloneCategory prop), but here as a genuinely separate page from the start rather than a shared component.

One shared touchpoint, unavoidable and small

  • App.tsx gains 2 new <Route> entries and ChatPage.tsx's nav menu gains one new link — both additive, no existing route/link edited.
  • IdentityContext is reused as-is (same UserProfile shape already threads through every page) — not duplicated.

The one optional seam: chat integration — deliberately deferred

Tension worth naming directly

A user asking the chatbot "I want to borrow from my 401(k)" and getting routed to a real loan flow is the more impressive demo — but it requires adding a new domain agent to multi_agent_pipeline.py's own Planner dispatch table, which is touching existing routing logic, even if the agent's own body just calls loan_401k_service.py. That's a real, if small, intermix — not a false alarm.

Recommendation: build §02–03 first as a fully standalone surface (own page, own API, zero chat involvement) and treat chat integration as a separate, later, explicitly-scoped phase — exactly the same phasing discipline already applied to Phase 233 (visibility, built) vs. Phase 234 (trigger-from-UI, spec-only, deliberately deferred). Isolation stays perfect until that phase is deliberately opened.

Blind spots and course corrections

Straight answers to "are we missing anything" — ranked by how much it actually matters.

1 · biggest gap — identity trust doesn't hold up for real money

Every RBAC check in this project today reads an unsigned, caller-supplied user_profile straight from the request body — documented and accepted deliberately, because nothing load-bearing depended on it being real. A 401(k) loan is the first feature in this project where that stops being a comfortable assumption: it authorizes a real financial transaction against a specific employee's real account. Options, not yet decided: (a) explicitly scope this as a simulation — no real money, no real identity guarantee, stated plainly in the UI, matching how the Loan Agent itself is already simulated (design.html §09); (b) treat this as the actual forcing function for finally building the "human-to-app OAuth2" design that's existed only as a placeholder (common/clients/auth_client/oauth_client.py) since early in this project. Building the loan feature without picking one of these is the real risk, not a hypothetical one.

2 — PII/financial data handling, not yet designed

Vested balance, loan amount, and (eventually) disbursement details are more sensitive than anything this project currently logs. The existing LangSmith tracing, request-metrics logging, and Explainability panel were all designed around RAG/retrieval content — none of them have been reviewed for "should a dollar figure ever reach a trace." Needs an explicit redaction pass before this ships, not an assumption that existing guardrails already cover it.

3 — idempotency over a 5–7 day async process

A message/send retried after a timeout, or a double-click on "Submit," can create two real loan Tasks instead of one. Needs an idempotency key (client-generated, carried in the DataPart) from day one — not something to patch in after a duplicate is found in production.

4 — async client style is a real departure worth deciding on purpose

This project's existing external clients (github_actions_client.py, etc.) use synchronous requests. A real A2A SDK exchange, especially with push-notification callbacks (design.html §07), fits this project's otherwise-async FastAPI style much better with httpx's async client. Flagging so it's a deliberate choice for loan_401k_agent_client.py, not an accidental inconsistency with the rest of common/clients/.

5 — smaller, easy to fold in: testing isolation

Already covered by this project's own existing convention, just worth stating: tests/hrb_chatbot/loan_401k/ mirrors src/hrb_chatbot/loan_401k/ 1:1, same as everywhere else. No special casing needed from the spec_gate.py hook either — it already gates all of src/hrb_chatbot/** uniformly, this subtree included.

6 — worth confirming explicitly, not a correction

Is "HRB 401k Manager" meant to actually get built and deployed, or does this stay a pure architecture/learning exercise (like the course's own simulated buyer/seller agents)? Doesn't change §01–05's design, but changes how much of §02–05 is worth building for real right now versus keeping as reference material.

Next steps

  2. If proceeding: a real RAG-ROADMAP.md phase + an endpoint-request-response-contracts.md section for /v1/401k-loans/*, same SDD process as every other phase in this project.
  3. Backend subtree (§02) and frontend subtree (§03) can be built and reviewed independently of each other and of the Loan Agent service itself, as long as the client is stubbed against the Agent Card shape in design.html §05 first.
