01

Verdict, up front

Natural fit - once correctly homed

This is a genuinely natural extension, but not quite the shape you described. The "popup window" instinct is right for submitting a request - wrong popup, though: it can't live in the GenAI Chat Workflow's attach-files popup. And "2 agents negotiating" isn't quite right either - this needs a human decision, not two LLMs agreeing. The sections below explain both, with the evidence, then propose the shape that does fit.

The one finding that matters most

Before any of the design below is worth building: there is currently no way, anywhere in either repo, for a human to actually resolve a HITL or leave-exception request. Not a UI gap - a code gap. I checked both services end to end. This has to be built in hrb_lms_mcp first, or the whole feature is an elegant front door with no exit. Full details in §03, Gap 1.

02

What's already real - checked directly, not assumed

Read the actual code in C:\workspace\poc\2026\hrb_lms_mcp before writing any of this. More exists than I expected:

  • hrb_emp_lms.hitl_requests (Postgres, already live) - request_type, related_entity_type/id, employee_id, query, a JSON context column, status (PENDING/IN_PROGRESS/COMPLETED/CANCELLED), assigned_to, and already-present-but-unused response/responded_at columns.
  • Two real, registered MCP tools: create_hitl_request and get_hitl_status (api/controller/lms_mcp_tools.py).
  • hrb_emp_lms.leave_requests already has a PENDING_HITL status and auto-fires create_hitl_request_for_leave_exception() when a request exceeds the employee's balance (leave_request_service.py's submit_leave_request()).
  • leave_types already has a requires_approval boolean and an approver_id on leave_requests pointing at the employee's manager.

None of this was reachable from hrb_chatbot_v2 before today - its own MCP tool wrapper (ai/rag_pipeline/tools/mcp_tools/__init__.py) only ever calls get_leave_balance/get_leave_history. The HITL machinery exists; nothing on this side has ever used it.

03

Blind spots found - the part you asked me to actually look for

Five, found by reading the real code, not by guessing at what's "probably there."

1No resolve/respond path exists for ANY request type, today

I grepped both repos for approve/reject/resolve/respond methods against HitlRequest or LeaveRequest. There are none. HitlService only has create_hitl_request(...) and get_hitl_request(...) - read-only status check. The response/responded_at columns sit unused. This isn't specific to the new leave types - it means today, a PTO-exception HITL request filed right now can never be resolved by anything in either codebase. This blocks every leave type, not just the new ones.

grep -rn "def approve|def reject|def resolve|def respond" hrb_lms_mcp/ -> 0 matches

2Unpaid leave is the opposite case from what you described

submit_leave_request()'s own balance-exception check is if leave_type_obj.requires_approval and leave_type != "UNPAID" - unpaid leave is explicitly excluded from the HITL path. Today it just gets status = PENDING, assigned to the regular manager, same as any other request - no specialist routing at all. Building "unpaid leave needs specialist HR review" means adding that behavior, not extending something that already does it.

leave_request_service.py:66 - if leave_type_obj.requires_approval and leave_type != "UNPAID":

3STD, LTD, and critical-care leave don't exist as leave types yet

Seeded leave_types today: PTO, SICK, UNPAID, SABBATICAL, MATERNITY, PATERNITY. No STD/LTD/critical-care rows. More importantly, there's no column distinguishing "needs the regular manager" from "always needs a specialist, regardless of balance" - today the only thing that ever triggers HITL is a balance shortfall. A leave-type-driven trigger ("STD always goes to a specialist") is new logic, not a parameter change.

4Neither repo has anywhere durable to put the supporting document

adhoc_extraction.py's own docstring: "nothing written to a persistent directory, nothing chunked or embedded." The GenAI Chat Workflow processes an attached file in-memory, in-request, then discards it. A specialist reviewing hours or days later needs the actual document still there. Reusing the KB-ingestion S3 path is also wrong in the other direction - that path embeds content into the shared vector index, and a medical certificate must never end up retrievable by every other employee's RAG query.

5The GenAI Chat Workflow popup is architecturally the wrong home

adhoc_document_agent.py's own docstring is explicit and deliberate: "Still no vector store or MCP access, by design." A leave request fundamentally needs MCP (to call create_leave_request/create_hitl_request). Building it into that popup means reversing a foundational scoping decision of that specific pipeline, not extending it. The natural home is a new entry point with real MCP access - see §06.

One more, smaller but real

This project's own docs are explicit that gateway RBAC is self-asserted and unverified (rbac.py trusts a caller-supplied role, "a formality, not a real control"). Gating a specialist's review queue - and medical documents inside it - behind that same mechanism is a real weakness worth naming now, even for an educational capstone, rather than discovering it after the feature ships.

04

Proposed architecture

Two practical roles, not two negotiating LLMs. The course's own exercise 6 (human-approval checkpoint) is the closer analog here than the buyer/seller negotiation demos - a real human has to decide, the same way it would in production.

flowchart TD
    Emp["Employee: Request Leave form
(new entry point, not the attach-files popup)"]
    Intake["Intake agent
validates dates, reads/uploads document,
calls create_leave_request"]
    S3["S3: private leave-documents bucket
(new, separate from KB ingestion)"]
    MCP1["hrb_lms_mcp:
create_leave_request -> create_hitl_request"]
    Queue["Specialist review queue
(new hr_support-only UI)"]
    Brief["Review-support agent
summarizes request + document for the specialist
- recommends nothing, decides nothing"]
    Human["HR specialist (human)
reads summary + original document, decides"]
    MCP2["hrb_lms_mcp:
resolve_hitl_request (NEW - doesn't exist yet)"]
    Notify["SES: decision email to employee
(reuses existing send_email client)"]

    Emp --> Intake --> S3
    Intake --> MCP1 --> Queue
    Queue --> Brief --> Human --> MCP2 --> Notify --> Emp

Only 2 real LLM calls in the whole loop: the Intake agent (parses/validates the request) and the Review-support agent (summarizes for the specialist). The specialist's decision itself is never an LLM call - matching the scope boundary you already set ("approved by specialized HR specialist team").

05

SQLite vs. Postgres - and a sharper question underneath it

Not a close call

Postgres, full stop. This is real transactional business-process data that must survive hours-to-days of waiting on a human, must never silently vanish, and must be consistent across however many App Runner instances are running. That's a strictly stronger durability requirement than the GenAI Chat Workflow memory proposal, where SQLite-vs-Postgres was a genuine judgment call. Here it isn't.

The sharper question is actually "does hrb_chatbot_v2 need a new table of its own at all?" - and the honest answer is probably no:

hrb_lms_mcp (existing Postgres schema)
  • New column on leave_types: a specialist-review flag, separate from requires_approval (that one already means "needs a manager").
  • New seed rows: STD, LTD, CRITICAL_CARE leave types.
  • New method + MCP tool: resolve_hitl_request - writes response/responded_at, flips status. This is the Gap 1 blocker, and the one piece that has to land first.
  • Document reference: an S3 key stored inside the existing context JSON column - no new column, no new table.
hrb_chatbot_v2 (no new table proposed)
  • New MCP tool wrappers (client-side) for create_leave_request, create_hitl_request, get_hitl_status, the new resolve_hitl_request.
  • "My leave requests" / the specialist queue both query live via MCP each time - no local cache table duplicating data hrb_lms_mcp already owns.
  • Only new storage: the S3 bucket for uploaded documents (bucket + presigned-upload flow, reusing the pattern already built for KB document uploads - not a database table).
06

UI - both sides, not just the one you named

You asked about the employee-facing popup. The specialist-facing side is just as necessary and wasn't mentioned - flagging it now rather than discovering it mid-build.

Employee side - "Request Leave," a new entry point

  • Not the attach-files popup (§03, Gap 5). A new button/modal, structured form: leave type dropdown (now including STD/LTD/Critical Care/Unpaid), start date, end date, reason, a document upload field.
  • Reuses the presigned-S3-upload pattern already built for KB documents - a new, separate, private bucket, not the KB ingestion path (§03, Gap 4).
  • Submits to a new route that calls the Intake agent, which calls create_leave_request via MCP.

Specialist side - a review queue, not a chat (new, not in your original ask)

  • A 4th item alongside the existing hr_support-only Admin menu entries (Upload documents, Manage documents, View feedback) - "Leave Approvals."
  • Lists pending hitl_requests (via get_hitl_status/a new list tool), each with the Review-support agent's plain-English summary, a link to the original document, and Approve/Reject actions that call the new resolve_hitl_request tool.
  • On resolution: an SES email to the employee (reusing this week's send_email client) and a status update the employee's chat/history view can show.
07

Build order - the dependency is real, not a formality

  1. In hrb_lms_mcp (prerequisite, outside this repo): build resolve_hitl_request, add the specialist-review leave-type column, seed STD/LTD/CRITICAL_CARE. Nothing downstream is worth building before this exists.
  2. In hrb_chatbot_v2: MCP tool wrappers for all 4 tools, the private S3 document bucket, the Intake agent.
  3. In hrb_chatbot_ui: the "Request Leave" form.
  4. In hrb_chatbot_v2: the Review-support agent (summarization only).
  5. In hrb_chatbot_ui: the "Leave Approvals" specialist queue.
  6. Live round-trip verification: submit a real request with a document, resolve it as the specialist, confirm the employee gets a real notification - not a unit test standing in for it.

09

Phase 162 reality check - what actually shipped, verified directly against the running code and schema, not assumed from this proposal

This section exists because the user asked, after trying it locally: where is this stored, how many tables, how does the employee find out, who does a request go to? The honest answers below came from reading hrb_lms_mcp/src/app/models/models.py, hitl_service.py, and hrb_chatbot_v2's routes directly - not from this proposal, which predates the real implementation and drifted from it in 3 places.

Storage - confirmed, 2 tables, zero new ones added for this feature

  • hrb_emp_lms.leave_requests - the leave record itself (employee_id, leave_type_id, dates, days, reason, status, approver_id, approved_at, rejection_reason) - already existed for the balance-driven leave flow, reused as-is.
  • hrb_emp_lms.hitl_requests - the review-queue record (request_type, employee_id, query, a JSON context column, status, assigned_to, response, responded_at) - also pre-existing, reused. The uploaded document's S3 key lives inside context, not a column of its own.
  • No table needed for the attached document itself - only its S3 key, inside context.

Gap 1 - no employee notification exists at all

Confirmed by reading the code, not assumed

resolve_unpaid_leave_request (api/leave/unpaid_leave.py) writes the decision and returns it to the HR specialist's own browser - nothing emails or otherwise notifies the employee who filed the request. This §04's original "Notify" node (SES email) was never built. There is also no "my requests" view the employee could check instead - the one post-submit confirmation screen the UI used to show (reference numbers, repeat-flag note) was just removed per the user's own Phase 164 request that the popup close immediately on submit, so right now an employee who submits a request has literally no way to learn the outcome inside this app at all.

Gap 2 - HR reviewers can't actually open the attached document

Confirmed by reading the code, not assumed

LeaveApprovalsPage.tsx renders context.document_reference as plain text (the raw S3 key) - not a link. Only a presigned upload URL exists (generate_leave_document_upload_url); nothing generates a presigned download URL for review. An HR specialist today cannot open the file an employee attached - they can only see its key.

Gap 3 - "assigned_to" is a placeholder queue label, not a real per-specialist assignment

Confirmed by reading hitl_service.py directly

Every request is created with assigned_to="hr-team@company.com" hardcoded - a flat shared-queue label, never a specific specialist. resolve_hitl_request then overwrites that same column with resolved_by - the resolving specialist's full name string (user.full_name from the request body), not their employee_id, and not a separate column from the pre-resolution assignment. So today: any hr_support persona can see and resolve any pending request (first-come-first-served, confirmed via LeaveApprovalsPage showing the full pending list to every such persona); there is no concept of "my assigned requests" distinct from "the whole queue"; and the only record of who resolved a request is a display name, not a structured reference back to employees.

None of these 3 gaps need a new table to close - §08's Q5/Q6 are about which approach to take, not about schema headroom. A notification (email and/or a view) can be built off existing columns; a download link only needs a new presigned-GET helper next to the existing presigned-PUT one; real per-specialist assignment could reuse assigned_to pre-resolution instead of only post-resolution, or add one new column if the user wants assignment and resolver tracked separately - a design choice to make with §08 Q6's answer, not before it.

DecisionAnswer

New table 1 - hrb_emp_lms.unpaid_leave_documents (the manifest)

One row per uploaded supporting document - replaces today's single S3 key buried inside hitl_requests.context JSON with real, queryable columns, and is the single link both UIs (employee's own view, specialist's review queue) go through to reach a real file - neither UI ever talks to S3 directly.

  • id (PK)
  • upload_token (the random token already generated by the existing /upload-url route - unique, not null)
  • leave_request_id (FK -> leave_requests.id, nullable - see the upload-ordering note below for why)
  • s3_key, original_filename, content_type
  • uploaded_at
A real gap this table also closes - found while designing it, not asked for

Upload happens before the leave request exists. The employee-side flow uploads to S3 first, then calls submit - confirmed by reading UnpaidLeaveModal.tsx's own handleSubmit() directly. If submit fails after a successful upload (a real possibility - a backend error, a dropped connection), today's design leaves a real file sitting in S3 with nothing in any database referencing it at all - a silent orphan, invisible to both UIs and never cleaned up. Fix: the /upload-url route itself inserts the manifest row immediately (keyed by upload_token, leave_request_id still null), and submit fills in leave_request_id once the real request exists. This makes every uploaded file trackable from the moment it's uploaded, not just once a request successfully completes - and "documents with leave_request_id IS NULL older than 24h" becomes a real, running query that finds orphans, instead of them being invisible.

New table 2 - hrb_emp_lms.specialist_leave_reviews

The full HITL review lifecycle, with real typed columns instead of overloading hitl_requests.assigned_to with a name string. Deliberately not named "unpaid_leave_*" - it covers all 4 leave types now, not just unpaid.

  • id (PK)
  • hitl_request_id (FK -> hitl_requests.id) and leave_request_id (FK -> leave_requests.id) - both, so a review is reachable from either side without a join through the other.
  • leave_type_code (denormalized copy of the leave type at submission time - so this table alone shows "what kind of request was this," no join needed for the common read)
  • status (mirrors hitl_requests.status - kept in sync, not a second source of truth for anything hitl_requests itself still drives)
  • decision (APPROVED/REJECTED, null until resolved)
  • hr_specialist_employee_id (FK -> employees.id - a real reference, not a name string; the specialist's name/email are a join away, never duplicated here)
  • hr_comments (text)
  • created_at (entered the queue), responded_at (null until resolved)

"Elapsed time" is deliberately not a stored column - it's responded_at - created_at (or now() - created_at while still pending), computed at read time. A stored elapsed-time value would go stale the moment it's written; this avoids that whole class of bug.

On "can these support the full lifecycle, not just approve/reject": yes - this is a normal table with normal columns, and adding a column later (e.g. a claim/assign step, if §08 Q6's answer ever changes) is an additive migration, not a redesign. Nothing about this shape is a dead end. The columns above cover exactly the lifecycle this phase's scope actually needs (submitted -> pending -> decided) - a claim/assign step is deliberately left out because Q6's answer was to keep the shared queue, not because the table can't hold it.

leave_types - 3 new rows, 1 new column

Matches this doc's own original §05 proposal, never built until now: CRITICAL_CAREGIVER, STD, LTD seed rows alongside the existing UNPAID, plus a new requires_specialist_review boolean column (separate from the existing requires_approval, which means "needs a manager") - all 4 of these set it true.

S3 layout

LEAVE_DOCS_S3_BUCKET (already exists, Phase 162) gains a leave-type-prefixed layout: {leave_type_code}/{employee_id}/{leave_request_id}/{filename} - "a separate folder" per the user's own wording, inside the existing dedicated bucket rather than a second bucket.

Document review - a real download, not an in-app viewer

A new presigned-GET endpoint (mirrors the existing presigned-PUT upload one) returns a short-lived download URL, looked up from the manifest table above by leave_request_id; LeaveApprovalsPage.tsx renders each document's real filename (from the manifest, not the raw key) as <a href={url} target="_blank" rel="noreferrer">. The same endpoint also serves the employee's own "My Requests" view, for their own documents. Honest caveat: a web app can trigger a real file download/the browser's native PDF handling, which is the practical equivalent of "not displayed within the chat app's own window" - it cannot force a specific desktop application to open, since that's an OS/browser setting outside any website's control.

RBAC gap to close, not inherited "for free"

The download endpoint must check that the caller is either the employee who owns that leave_request_id or an hr_support persona - the same per-route require_role() pattern every other route here already uses, but this one needs an extra ownership check on top of the role check, since today's RBAC only verifies role, never "does this specific record belong to this specific caller." Without it, any logged-in employee could fetch any other employee's document by guessing or enumerating a leave_request_id - a real gap to close in this phase, not something the existing pattern already covers.

Email notification

Sent at the moment a specialist resolves a request (approve or reject), reusing the existing send_email client, to the employee's own address (employees.email, looked up in hrb_lms_mcp and returned as part of resolve_hitl_request's response so hrb_chatbot_v2 doesn't need a second round trip to fetch it).

"My Requests" view (employee side)

A new page/section listing the logged-in employee's own past requests - leave type, dates, status, the specialist's comments once decided, submitted/decided timestamps. New MCP tool (list a specific employee's own specialist_leave_reviews joined to leave_requests), a wrapper, a route, and a UI page - same shape as the existing LeaveApprovalsPage but scoped to employee_id instead of showing everyone's pending queue.

One default I picked, flagged for override

The "repeat within 12 months" eligibility check will compare same leave type only (e.g. a 2nd STD request within 12 months flags as repeat; a CCG request doesn't make an unrelated STD request look like a repeat) - a real HR-policy distinction, not a technical default. Say so if you want it to mean "any of these 4 types" instead.

Phase 165 - built and live-verified, all 3 §09 gaps closed

The user gave explicit go-ahead to build §10's finalized design. All 3 repos (plus hrb_chatbot_ui) are done, live-verified, and not yet committed anywhere - full detail is in RAG-ROADMAP.md's own Phase 165 entry; this section is the short version.

Not fixed here - naming/provisioning a real bucket is an infrastructure decision, not something to guess at unilaterally.
