How does tool calling actually work - does the model run the tool itself?
HintModel picks → backend executes → result goes back to model
Concept

The model never executes anything. It reads a list of tool names, descriptions, and parameter schemas and replies with a JSON object saying which tool to call and with what arguments - plain text, not code. Your own backend parses that JSON, makes the real call, and feeds the result back to the model for a second pass that writes the final answer. Think of it like a manager (the model) writing a work order for a specific engineer (your code) - the manager never touches the server.

Answer - STAR
Situation

An HR chatbot needs to answer "How many PTO days do I have left?" - that number lives in a separate leave-management system, not in any document the RAG pipeline has indexed.

Task

Let the model decide, per query, whether to answer from retrieved documents or fetch a live number from that system - without hardcoding keyword rules for every possible phrasing.

Action

Register a GetLeaveBalance tool with a typed schema (employee_id). The model emits a tool-call JSON block; the backend calls the real MCP server over an authenticated HTTP request, gets back a number, and passes it to the model as new context for the final reply.

Result

The model answers with a real, current PTO balance instead of a hallucinated or stale one - and the same mechanism extends to any new tool without retraining anything.

tool_call = model.decide(query, available_tools)  # model: "call GetLeaveBalance(employee_id=...)"
result = backend.execute(tool_call)                # backend runs the real HTTP call, not the model
final_answer = model.generate(query, tool_result=result)
Project link
HRB v2ai/rag_pipeline/tools/mcp_tools/__init__.py's _call_mcp_tool() is exactly this - the LLM selects a tool (e.g. get_leave_balance), this function makes the real authenticated call to the separate hrb_lms_mcp service, and the result flows back into the model's own context.
Leadership angle Every tool you expose to a model is a new surface the model can trigger in production - a Director will ask "what's the blast radius if the model calls this wrong?" before "does it work." Scope tools narrowly and log every call.
Trade-offs and pitfalls
  • Too many tools (20+) degrades selection accuracy - the model starts picking the wrong one more often.
  • A tool with a vague description gets called at the wrong time; the description is part of your prompt, not documentation.
  • Never let a tool call execute something irreversible (delete, pay, send) without a confirmation step outside the model's control.
Keywords
TermPlain English
Tool callingThe model names a function and its arguments in its reply; your code runs it.
MCPModel Context Protocol - a standard shape for exposing tools/data to a model over HTTP, so different models/apps can reuse the same tool server.
Parameter schemaThe typed list of inputs a tool accepts, shown to the model so it knows what to fill in.
A tool call arrives with invalid arguments - what should happen?
HintValidate → never trust the model's own output → fail safely, don't crash
Concept

A model's tool-call output is still just generated text that happens to look like JSON - it can be malformed, miss a required field, or pass a string where a number belongs. Validate it exactly like you'd validate untrusted user input, because that's what it is. Same discipline as never trusting a form submission from a browser, even your own frontend's.

Answer - STAR
Situation

A tool-calling agent occasionally emits a call missing a required argument, or the external tool server itself is briefly unreachable.

Task

Keep one bad or failed tool call from crashing the whole response - the user should still get an answer, degraded if necessary.

Action

Wrap every tool execution in a try/except. On failure, catch it, log the real error server-side, and fall back to the next-best behavior (e.g. retrieval-based answer instead of a live number) instead of surfacing a raw exception.

Result

A down or misbehaving tool degrades the answer quality for one query - it never returns a 500 or an unhandled crash to the user.

Project link
HRB v2Documented directly in this project's own MCP integration notes: "Any MCP failure (network, auth, tool error) is caught and falls back to normal RAG, not a 500 - the pipeline never assumes MCP is available." Same principle the client layer's error-handling convention applies everywhere else in this codebase.
Leadership angle This is a reliability/SLA conversation, not just an engineering nicety - a Director cares that one flaky downstream dependency can't take the whole chat experience down with it.
Trade-offs and pitfalls
  • Silently swallowing every error hides real outages - always log server-side even when you degrade gracefully for the user.
  • A fallback that's indistinguishable from a real answer can mislead the user - say when you're degraded, don't pretend.
Keywords
TermPlain English
Graceful degradationKeep serving a reduced-quality response instead of failing outright when a dependency breaks.
FallbackThe next-best behavior used when the preferred path isn't available.
What is a multi-agent system, and when is it the wrong choice?
HintSplit → specialize → merge - but only if one agent genuinely can't do it alone
Concept

A multi-agent system splits one task across several specialized agents (a planner, domain workers, a reviewer) instead of one agent doing everything. It adds real latency and cost - more LLM calls - so it's only worth it when a single agent's context or focus genuinely can't cover the task. Like splitting a project across a team instead of one generalist - only worth the coordination overhead for genuinely cross-functional work.

Answer - STAR
Situation

An HR chatbot gets a compound question spanning two unrelated domains at once - e.g. policy knowledge plus a live leave balance - in a single sentence.

Task

Answer both halves accurately without one domain's retrieval noise degrading the other's.

Action

A Planner agent splits the query into sub-tasks, dispatches each to its own domain agent in parallel, and a Reviewer agent merges the two partial answers into one coherent reply - not critiquing and sending work back, just synthesizing.

Result

Each domain agent stays focused and accurate; the merged answer covers both halves of the question in one response.

Project link
HRB v2The multi-agentic-rag pipeline (ai/agents/workflow_agents/multi_agent_pipeline.py, a real LangGraph graph) is exactly Planner → parallel domain agents → Reviewer. One documented, deliberate decision worth knowing cold: the Reviewer node is a merge/synthesis step, not a Critic - it doesn't send work back for revision, it combines what came back. For most single-domain HR questions, this project's own simpler genai-rag or single-agentic-rag pipeline is the right choice instead - multi-agent is reserved for genuinely cross-domain compound queries.
Leadership angle Multi-agent is a build-vs-buy-style cost decision as much as an architecture one - each added agent is more LLM spend and more latency per request. A Director wants to know you reach for it only when a simpler pipeline measurably can't do the job, not by default.
Trade-offs and pitfalls
  • Multi-agent for a simple, single-domain question is pure overhead - more cost and latency for no quality gain.
  • A Planner that always splits into the same fixed sub-tasks, regardless of the real question, is worse than no planner at all.
  • Parallel domain agents need a real merge step - concatenating their raw outputs isn't synthesis.
Keywords
TermPlain English
Planner agentBreaks one request into sub-tasks for other agents to handle.
Domain agentA specialized agent focused on one topic area only.
LangGraphA library for wiring agents together as a graph of steps, with explicit control over the flow between them.
What should you log on every agent run?
HintInputs, decision, outcome, timing - enough to replay the run later without guessing
Concept

Log enough that you could explain, after the fact, exactly why the agent did what it did - not just that it succeeded or failed. The query, which tool (if any) it picked, the tool's result, and how long each step took. Think of it like an audit trail for a loan-approval decision - "approved" alone isn't enough, you need the inputs that led there.

Answer - STAR
Situation

A user reports a wrong or strange chatbot answer days after the fact, with no way to reproduce it live.

Task

Diagnose what the agent actually did on that run without re-running anything against the (possibly now-different) live data.

Action

Log the query, every tool call with its arguments and result, token usage, per-step latency, and the exact context sent to the model for its final answer - structured, not free text, so it's queryable later.

Result

The original run can be reconstructed and explained from logs alone, without needing to reproduce it live.

Project link
HRB v2Every external call goes through log_backend_call() (backend name, operation, kwargs, timing, success/failure), and the API's own Explainability response includes an llm_context field - the literal context sent to the model - specifically so a reported bad answer can be explained from the stored record alone.
Leadership angle This is the difference between "we think it's fine" and "we can prove what happened" when a bad answer reaches a real employee - governance and audit requirements in regulated industries (banking included) often require exactly this level of traceability.
Trade-offs and pitfalls
  • Logging the full prompt/context can capture PII - redact or scope access before it becomes a compliance problem.
  • Unstructured log lines ("agent ran ok") are nearly useless for later debugging - log structured fields you can actually query.
Keywords
TermPlain English
Structured loggingLog entries as named fields (not free text), so they can be searched/filtered later.
ExplainabilityExposing enough detail about how an answer was produced that it can be audited or debugged.
