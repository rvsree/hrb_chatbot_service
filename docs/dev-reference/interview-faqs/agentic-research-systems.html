01ReAct vs Plan-and-Execute vs HybridQ1-5
Q1. What is the ReAct pattern, and how does it differ from a single LLM call?
HintReason → Act (tool call) → Observe result → repeat until done
Concept

ReAct (Reason + Act) is a loop: the model reads the question, decides whether it needs a tool, calls one if so, reads the real result, and decides again - repeating until it can answer or it hits a step limit. A single LLM call just produces text once, from whatever it already knows; ReAct lets the model pull in fresh, real data mid-answer. Like a support engineer who checks a live dashboard before replying to a ticket, instead of answering from memory alone.

Answer - STAR
Situation

An employee asks a JPMC HR chatbot "How many PTO days do I have left, and can I use the healthcare FSA for my kid's braces?" - half policy, half a live personal number.

Task

Answer both halves correctly without hardcoding a rule for every possible phrasing of "needs a live number vs needs a policy document."

Action

Bind a list of tool definitions to the model. On each loop iteration, the model either calls a tool (GetLeaveBalance, SearchKnowledgeBase) or returns a final answer. The backend executes any tool call and feeds the real result back as a new message before the next iteration.

Result

One agent handles both the live-data half and the policy half of a compound question, in the same run, without a separate hardcoded path for each.

Project link
HRB v2ai/agents/workflow_agents/orchestration_agent.py's run_agent() is a real ReAct loop: llm = _build_llm().bind(tools=AGENTIC_TOOL_DEFINITIONS), then a for loop up to DEFAULT_MAX_ITERATIONS (5) that calls the model, checks response.tool_calls, runs any tool via the TOOL_FUNCTIONS dispatch dict, and appends the result as a ToolMessage before looping again. This is the real backend behind POST /v1/single-agentic-rag/query.
Leadership angle ReAct trades predictable cost for flexibility - a Director will ask how many LLM calls a worst-case query makes before approving it for production traffic, not just whether it answers correctly.
Trade-offs and pitfalls
  • Every extra iteration is a real, billed LLM call - ReAct costs more and is slower than a fixed retrieve-then-generate pipeline for questions that never needed a tool.
  • Don't use ReAct when the answer path is always the same - that's just added latency for no benefit.
  • A loop with no step cap can run away on a confused model; always bound it.
Keywords
TermPlain English
ReActReason + Act - a loop where the model alternates between deciding and calling tools.
Tool callThe model's structured request to run a specific function with specific arguments.
IterationOne pass through the reason/act loop.
Q2. What is Plan-and-Execute, and how is it structurally different from ReAct?
HintPlan upfront (all sub-tasks) → dispatch in parallel → merge - not one step at a time
Concept

Plan-and-Execute writes out the full list of sub-tasks before doing any of them, then runs those sub-tasks (often in parallel), then merges the results. ReAct decides one step at a time, reading each result before deciding the next step; Plan-and-Execute decides the whole shape of the work upfront. Like a project manager who writes the full task breakdown before assigning any of it, instead of assigning one task, waiting, then deciding the next.

Answer - STAR
Situation

A compound HR question spans two unrelated domains at once - internal policy and a live leave balance - in a single sentence.

Task

Split the question into independent sub-tasks that can run at the same time, instead of serially re-deciding after each one.

Action

A Planner node makes one structured-output LLM call that returns a list of {agent, focus} tasks upfront. An Orchestration step fans every task out in parallel to its domain agent. A Reviewer node merges whatever comes back into one final answer.

Result

Independent sub-tasks run concurrently instead of one-at-a-time, and each domain agent only sees the slice of the question it's responsible for.

Project link
HRB v2ai/agents/workflow_agents/multi_agent_pipeline.py is a real LangGraph graph: planner_node() calls planner_agent.plan() once to get the full task list, dispatch_to_agents() fans every task out via LangGraph's Send() API to up to 5 domain agent nodes in parallel, and reviewer_node() merges every result. This backs POST /v1/multi-agentic-rag/query.
Leadership angle Plan-and-Execute is the right pitch when a Director asks "why does this cost more per query" - the answer is "it runs several LLM calls in parallel on purpose, to cover a genuinely compound question in one response instead of several round trips."
Trade-offs and pitfalls
  • The Planner's own routing call can be wrong - a misrouted task either wastes a call on an irrelevant agent or skips a relevant one.
  • Parallel dispatch needs a real merge step after - concatenating raw outputs isn't synthesis.
  • More upfront LLM calls (Planner + N domain agents + Reviewer) than a single-agent ReAct loop for the same question, if the question didn't actually need splitting.
Keywords
TermPlain English
Plan-and-ExecuteDecide every sub-task upfront, then run them, instead of deciding one step at a time.
LangGraphA library for wiring agent steps together as an explicit graph.
Fan-outSending the same or different work to several workers at once, in parallel.
Q3. How do you decide whether a question needs ReAct, Plan-and-Execute, or neither?
HintSimple → fixed pipeline. Tool-dependent/ambiguous → ReAct. Compound cross-domain → plan-like
Concept

Pick the cheapest architecture that can still answer correctly. A fixed retrieve-then-generate pipeline is cheapest and fastest; a ReAct loop costs more per query but handles tool-dependent or ambiguous questions; a plan-like multi-agent system costs the most but is the only one of the three that can cover a genuinely compound, cross-domain question in one response. Like choosing between a form, a help-desk agent, and a cross-functional task force - escalate only as far as the question actually needs.

Answer - STAR
Situation

An HR chatbot gets three different kinds of questions in one day: a plain policy lookup, a "what's my balance" question, and a compound policy-plus-balance question.

Task

Serve all three without forcing every query through the most expensive path.

Action

Offer three separate endpoints, each a real tier: a fixed retrieve-then-generate pipeline for the simple case, a ReAct tool-calling loop for the tool-dependent case, and a LangGraph plan-dispatch-merge pipeline for the compound case.

Result

Each question type gets routed to the cheapest architecture that can actually answer it, instead of every query paying multi-agent cost by default.

  • Picking the wrong tier for a question (e.g. sending every query to multi-agentic-rag) erases the whole point of tiering.
  • A caller has to know which endpoint to call - this project doesn't (yet) have one smart router that picks the tier automatically.

TieringOffering multiple architectures at different cost/capability points instead of one default for everything.

Q4. What does a real hybrid ReAct/Plan-and-Execute architecture look like - does your planner ever re-plan?
HintTextbook hybrid = plan, execute, re-plan on surprise. This project's graph has no edge back
Concept

A true hybrid plans upfront like Plan-and-Execute, but can re-plan mid-run if a step's result is surprising - closer to ReAct's one-step-at-a-time responsiveness, layered on top of an initial plan. Like a project manager who writes the task breakdown, then actually revises it when one team's finding changes what the other teams should do.

Answer - STAR
Situation

A domain agent in a plan-dispatch-merge system comes back with an unexpected result - say, a "no leave balance found" error partway through a compound query.

Task

Decide honestly whether the system re-plans around that surprise, or just carries the surprising result straight into the merge step.

Action

Trace the actual graph edges, not the intended design: does any node have an edge back to the Planner, or does every domain agent flow straight to the merge step regardless of what it returned?

Result

In this project's real graph, every domain agent node flows straight to the Reviewer, which flows straight to END - there is no edge back to the Planner anywhere. A surprising result gets merged, not re-planned around.

  • Without re-planning, a failed or wrong domain-agent result still gets merged into the final answer as best the Reviewer's LLM call can manage - it can't be caught and retried.
  • Adding real re-planning means adding a real edge back to the Planner and a stopping condition, so it doesn't loop forever - non-trivial, not a one-line change.
  • Don't claim "hybrid" in an interview for an architecture that's actually plan-once-execute-merge; be precise about which pattern is really built.

Q5. A ReAct agent is stuck looping - how do you stop a runaway agent, and what does the user see?
HintHard step cap → stop the loop → return a clear, honest fallback message, not a crash
Concept

A ReAct loop with no cap can call tools indefinitely if the model keeps deciding it needs "one more" step. The fix is a hard iteration limit, checked every pass, with a graceful fallback answer when it's hit - never an unhandled crash or an infinite bill. Like a support call that auto-escalates to a human after N failed troubleshooting attempts, instead of looping the same script forever.

Answer - STAR
Situation

A confusing or ambiguous HR question causes the agent to keep calling tools without ever producing a final answer.

Task

Cap the damage - bound the cost, and still give the user something useful instead of a timeout or an error.

Action

Run the loop inside a for i in range(max_iterations) bound. If the loop exhausts every iteration without the model returning a final (non-tool-call) response, return a fixed, honest fallback message instead of raising.

Result

The agent's cost per query is bounded no matter how confusing the question is, and the user gets a clear, actionable message instead of a crash or a silent hang.

Project link
HRB v2orchestration_agent.py's run_agent() caps the loop at DEFAULT_MAX_ITERATIONS = 5 (overridable via a max_iterations parameter - not the 40-step scenario this question often describes, this project's real default is 5). On exhaustion it returns this literal string: "I wasn't able to finish reasoning about this within the allowed number of steps. Please rephrase or ask a more specific question." - confirmed as the real code, not a paraphrase.
Leadership angle An uncapped agent loop is a real cost and availability risk at scale - a Director will ask for the worst-case LLM-call count per request before sign-off, and "it's bounded at 5, here's the fallback message" is the answer that passes that review.
Trade-offs and pitfalls
  • Too low a cap cuts off genuinely multi-step questions before they finish; too high defeats the point of having one.
  • A fallback message that looks like a real answer (instead of clearly saying "I couldn't finish") misleads the user about what actually happened.
  • A step cap alone doesn't catch a tool that silently returns garbage every iteration - that still burns every allowed step.
Keywords
TermPlain English
Iteration capA hard maximum number of loop passes, enforced in code, not left to the model's own judgment.
Graceful fallbackA clear, honest message returned when the normal path can't complete, instead of an error or a crash.
02Tool Integration & Circuit BreakersQ6-10
Q6. What is a "tool" in an agentic system, mechanically - what actually happens on a tool call?
HintModel names a function + args as JSON → your backend runs it → result goes back as a new message
Concept

A tool is a function the model can request by name, with typed arguments - the model never executes it. The model emits structured text naming the function and arguments; your backend parses that, makes the real call, and returns the result as a new message for the model to read on its next turn. MCP (Model Context Protocol) is a standard shape for exposing those tools over a network connection, so different clients can reuse the same tool server. MCP is like a REST contract for agent tools - a fixed shape (name, schema, how to call it) any client can rely on, instead of each app inventing its own.

Answer - STAR
Situation

An HR chatbot needs a real, current PTO balance that lives in a separate leave-management service, not in any indexed KB document.

Task

Let the model fetch that live number through a well-defined contract, without the backend guessing which service to call from free text.

Action

Open an MCP client session over HTTP to the leave-management server, call get_leave_balance with the employee's id, and read back the result's text content.

Result

The agent answers with a real, live number instead of a hallucinated one, through a protocol the backend didn't have to hand-roll.

async with streamablehttp_client(mcp_url, headers=headers) as (read_stream, write_stream, _):
    async with ClientSession(read_stream, write_stream) as session:
        await session.initialize()
        result = await session.call_tool(tool_name, arguments)

Trade-offs and pitfalls
  • Too many tools degrades the model's own selection accuracy - it starts picking the wrong one more often.
  • A vague tool description is part of the prompt, not documentation - the model only knows what the description tells it.
  • Never let a tool call execute something irreversible without a check outside the model's control.

Q7. What is a circuit breaker for tool calls, and why not just retry on failure?
HintN consecutive failures → trip → skip real calls for a cooldown → fail open if the check itself fails
Concept

A circuit breaker is a pre-flight check: before making a real call, ask "is this dependency known to be down right now?" and skip the call entirely if so, instead of paying a full network timeout on every single request during a known outage. Retrying just repeats the same timeout cost per request; a circuit breaker remembers the outage across requests. Like a receptionist who stops transferring calls to a phone line after it's rung out twice in a row, instead of making every caller wait through the same dead line.

Answer - STAR
Situation

The separate leave-management MCP service goes down during business hours - every leave-balance query from every employee still tries to call it.

Task

Stop paying a full network timeout on the 3rd, 4th, 100th request once the outage is known, without ever blocking a real call that might actually succeed.

Action

Before every real MCP call, read a cached connection-status row. If it shows 2+ consecutive failures and the last failed check was within a 10-second cooldown window, skip the real call and raise immediately instead. Record every real call's own outcome (success or failure) for the next check to use. If the status read itself fails for any reason, let the real call proceed anyway.

Result

During a known outage, requests fail fast instead of each paying a real network timeout - and the breaker can never itself become the reason a real, working call gets blocked.

Project link

MCP_CIRCUIT_BREAKER_FAILURE_THRESHOLD = 2, MCP_CIRCUIT_BREAKER_COOLDOWN_SECONDS defaults to 10 (env-configurable). _check_circuit_breaker() explicitly fails open - if reading the cached status itself raises, it logs a warning and lets the real call proceed, on the stated principle that "a pre-flight check that can itself fail must never block a real call."
Leadership angle This is a cost/latency governance story as much as a reliability one - a Director cares that a known downstream outage doesn't multiply into thousands of full-timeout requests before anyone notices.
Trade-offs and pitfalls
  • A circuit breaker needs its own storage for recent outcomes - that storage becoming unavailable must never block real traffic (fail open, not fail closed).
  • Too low a failure threshold trips on ordinary transient blips; too high delays protection during a real outage.
  • A tripped breaker still needs a real, working fallback behavior for the user - tripping it isn't itself the fix.

TermPlain English
Circuit breakerA pre-flight check that skips a call once a dependency is known to be down, instead of trying and timing out every time.
Fail openIf the safety check itself breaks, let the real action proceed rather than blocking it.

Q8. A tool call is slow or times out - what's the retry strategy?
HintNot every client in a system needs the same strategy - check each one, don't assume
Concept

Retry with exponential backoff means retrying a failed call, waiting longer between each attempt (e.g. 2, 4, 8 seconds), capped at a maximum wait. It's not universal - a system can have one client with real retries and another with none, by deliberate design or by gap. Like redialing a busy number with a longer pause each time, versus just hanging up after one failed attempt and trying a different number instead.

Answer - STAR
Situation

Two different external calls in the same system behave differently under a slow or failing dependency: one is a single-attempt MCP tool call, the other is a web-search API call.

Task

Describe each one's real, current behavior honestly rather than assuming both have the same resilience pattern.

Action

Read both client implementations directly: does either one retry, and with what backoff?

Result

One has real retry-with-backoff; the other makes a single attempt and relies on a higher-level fallback instead. Both are legitimate patterns - the point is knowing which one you actually have.

Project link
HRB v2A genuine, honest contrast in this project: mcp_tools/__init__.py's _call_mcp_tool() makes exactly one attempt and raises on any failure - no retry-with-backoff. The failure is caught one level up in try_route_to_mcp(), logged, and falls back to the normal RAG answer path instead. By contrast, common/clients/web_client/tavily_client.py's search() has real retry-with-exponential-backoff: up to max_retries (default 3) attempts, waiting min(2**attempt_number, MAX_SECONDS_BETWEEN_RETRIES) seconds between them, and never raises - it returns an empty-result shape with an error field on exhaustion.
Leadership angle Knowing exactly which dependency has retries and which doesn't - rather than assuming uniform resilience - is what a Director expects before an incident, not after one.
Trade-offs and pitfalls
  • Retrying a call that's slow because the dependency is genuinely down just multiplies load on something already struggling - pair retries with a circuit breaker, not instead of one.
  • Retrying a non-idempotent call (one with a side effect) can duplicate the side effect - check idempotency before adding retries.
  • A single-attempt call with a good fallback (like the MCP path here) can be a perfectly reasonable choice - retries aren't automatically "more correct."
Keywords
TermPlain English
Exponential backoffWaiting longer between each retry attempt, rather than retrying immediately every time.
IdempotentSafe to run more than once with the same effect as running it once.
Q9. How should a tool's schema be designed so the model picks it correctly?
HintName + description + typed parameters, written for the model, registered somewhere queryable
Concept

A tool's description is part of the prompt the model reads to decide whether to call it - vague or overlapping descriptions cause wrong tool picks. A typed parameter schema (what arguments, what type, which are required) lets the model fill in a call correctly instead of guessing a shape. Like an API's OpenAPI spec - the description and parameter types are the only contract the caller (here, the model) has to go on.

Answer - STAR
Situation

An HR chatbot's ReAct agent has three tools available: a KB search, a leave-balance lookup, and a leave-history lookup - all plausible for a vague question.

Task

Make the model pick the right one reliably, not by trial and error.

Action

Write each tool's description to state explicitly when to use it (e.g. "Use this for 'how do I' or 'what is the policy on' questions... This is the PRIMARY tool for policy/benefits questions") and give each parameter a real JSON-schema type, with required fields marked.

Result

The model's tool choice is driven by an explicit, written contract instead of an implicit guess from the tool's name alone.

Q10. Search, browser, or a retrieval tool - how do you choose, and does this project have all three?
HintClosed KB → vector retrieval. Open/live web → search API. No general browser tool here
Concept

Vector retrieval searches a closed, pre-indexed document set. A web search tool (an API like Tavily, not a full browser) fetches live results from the open internet. A browser tool would actually render and navigate a page - a different, heavier capability neither of the first two provides. Pick based on whether the answer lives in your own indexed documents, needs fresh external information, or needs to interact with a real page. Like choosing between a library catalog search, a phone call to an outside expert, and sending someone to physically go read a sign - three different capabilities, not interchangeable.

Answer - STAR
Situation

A multi-domain HR agent needs to answer from indexed benefits PDFs, from a live per-employee balance, and potentially from current external information a closed KB wouldn't have.

Task

Use the right retrieval mechanism for each kind of need instead of forcing every query through one tool.

Action

Route policy questions to vector search over the indexed KB; route live personal-data questions to the MCP leave-management tool; route a domain agent that specifically needs external web information to a web-search API client.

Result

Each kind of question is served by the mechanism actually suited to it, and the system is honest about not having a fourth, heavier capability it doesn't need.

03Guardrails, Hallucination & Citation GroundingQ11-15
Q11. How do you reduce hallucination in a RAG answer - what's the real mechanism, not just "add a guardrail"?
HintGround the answer in retrieved text + score groundedness + rail check output - three mechanisms, not one
Concept

Hallucination is the model stating something not actually supported by its source material. Reducing it isn't one switch - it's retrieval grounding (build the answer from real retrieved chunks), a measured groundedness score (how well the answer's claims are supported by that context), and an output guardrail (a rule-based check, separate from the LLM itself, that can mask or block). Like a financial report that cites its own source ledger lines, gets audited for whether those citations actually support the numbers, and still goes through a compliance review before publishing.

Answer - STAR
Situation

An employee asks about a specific 401(k) match percentage - a number that must be exactly right, not approximately right.

Task

Reduce the chance the model states a wrong number, and catch it through more than one layer.

Action

Generate the answer only from retrieved chunks (not open-ended model knowledge), score the answer's groundedness against those chunks with a separate judge call, and run the final text through an output guardrail before it reaches the user.

Result

Three independent checks have to fail at once for a wrong, unflagged number to reach the user - not just one.

Project link
HRB v2Real, layered: ai/pre_processing/guardrails_input.py (Gate 1, "Firewall") and ai/rag_pipeline/response_generation/guardrails_output/__init__.py (Gate 6) are NeMo-Guardrails-backed input/output rails - both real code now, not the empty placeholders they once were. Separately, evaluate_groundedness() (used in both pipeline.py and orchestration_agent.py's own _score_live_answer()) is a DeepEval-based score, not a block - it's measured and surfaced, not enforced as a hard gate.
Leadership angle In a regulated industry, "we measure groundedness on every answer" is a materially different governance story than "we trust the model" - a Director needs the measured number, not a vibe.
Trade-offs and pitfalls
  • A groundedness score that's measured but never gates anything in production is observability, not prevention - know which one you've built.
  • Output rails catch some failure shapes (blocked content, PII) but not a subtly wrong number that reads fluently - see Q13's real incident.
  • Retrieval grounding only helps if retrieval itself found the right chunk - a bad retrieval still grounds the model in the wrong source.

Q12. What does real citation grounding look like in the response - not just "the model said it checked"?
HintEvery cited source traces to a real document_id/chunk_index, not free-text attribution
Concept

Real citation grounding means every source in the response is a structured reference to an actual indexed chunk - document id, filename, position, score - not the model describing in prose where it "found" something. The former can be checked by a machine; the latter can only be checked by trusting the model's own claim. Like a court citation with a real case number and page, versus a witness saying "I read it somewhere."

Answer - STAR
Situation

An HR answer needs to be auditable - if a user questions it, there must be a real document to point to.

Task

Attach a structured, checkable source to every answer, not just a confident-sounding sentence.

Action

Concept

Q31. The circuit breaker trips at 2 consecutive failures with a 10-second cooldown - why those numbers, and what does tuning them trade off?
