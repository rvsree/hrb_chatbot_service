01Agentic AI Foundations & Reflex Agents21 cards, from 22 source questions

Agent types: reflex, goal-based, utility

What is an AI agent, and how is it different from a chatbot?
  • A chatbot maps input to output text. An agent runs a loop: decide an action, take it (often by calling a tool), observe the result, decide again - until it has an answer or hits a stop condition.
  • The defining trait isn't "uses an LLM" - it's that the program's next action depends on the outcome of its previous one, not just on the user's message.
builtThe ReAct-style tool-calling loop in orchestration_agent.py (single-agentic-rag) is a real instance of this - it calls a tool, reads the result, and decides whether to call another or answer.
What is a reflex agent, and does this project use one?
  • The simplest agent type: a fixed input-to-output mapping, no planning, no memory, no model call required.
  • Good for high-frequency, low-ambiguity cases; useless the moment the task needs more than one step.
builtai/rag_pipeline/tools/mcp_tools/__init__.py's try_route_to_mcp() is exactly this - plain keyword matching (e.g. "leave balance") routes straight to an MCP tool call, no LLM involved in the routing decision itself. Its own docstring calls it "a prototype before real ReAct tool selection."
Goal-based vs. utility-based agents - what's the real difference?
  • Goal-based: binary - did it reach the target state or not.
  • Utility-based: scores multiple acceptable options against each other (cost, speed, quality) and picks the best, not just any valid one.
noneNeither pattern applies cleanly here - this project's agents classify/retrieve/generate, they don't plan multi-step paths toward a stateful goal.
When would you choose a reflex layer over a full planning agent?
  • When most traffic is simple and repetitive - a rule-based fast path is cheaper, faster, and trivially testable, with a hand-off to the full agent only when confidence is low.
builtThat's the literal shape of genai-rag's pipeline: MCP keyword fast-path first, full retrieve-generate pipeline only on a miss.

Agent architecture: Controller, Toolset, Memory, Environment

What are the 4 parts of an agent's architecture?
  • Controller: runs the loop, builds the prompt, calls the model, decides what happens next.
  • Toolset: the functions the agent can call, each with a name/description/schema.
  • Memory: what persists within a run and across turns.
  • Environment: everything outside - APIs, databases, the user.
differentThe separation is real but the names differ: controller = run_agent()'s own loop in orchestration_agent.py; toolset = agentic_tools.py; memory = conversation_memory.py (Postgres); environment = the vector store, MCP server, and LLM provider behind their own gateways.
What does the controller actually do, step by step?
  • Build the prompt from instructions + memory + tool list, call the model, check whether the reply is a final answer or a tool-call request, run the tool if so, feed the result back in, repeat.
  • It also owns the stop rules - without them a confused model loops forever.
builtExactly this shape in orchestration_agent.py's run_agent() - a bounded for loop, not while True.
What stop conditions does a real agent loop need?
  • A max-iteration cap, ideally also a budget/timeout, plus a repeat-call detector - and always return why it stopped, not just a blank result.
differentDEFAULT_MAX_ITERATIONS = 5 is real and enforced (orchestration_agent.py). No budget/dollar cap or repeat-call detector exists yet - a real, logged gap, not silently assumed covered.
Why keep controller, toolset, memory, and environment as separate concerns?
  • Each becomes independently testable and swappable - change the model without touching tools, fake the environment without touching the loop.
builtThis is exactly why common/clients/** gateways exist - the model/vector-store/MCP clients are swappable behind one interface each, independent of the agent loop that calls them.

Prompt chaining vs. function chaining

What is prompt chaining, and what's its real failure mode?
  • Feeding one LLM call's output into the next. Works when every step genuinely needs language understanding.
  • Failure mode: errors compound - four 90%-accurate steps in a row is roughly 65% accurate overall, and a long chain hides exactly where it broke unless each step's output is checked before moving on.
builtgenai-rag's own multi-step shape (decompose -> per sub-question retrieve/generate -> merge) is a real prompt chain, with structured JSON between steps specifically to avoid the compounding-error trap.
How is function chaining different, and why prefer it?
  • Plain code controls the order; the LLM is used only at the specific steps that need it. Deterministic steps (math, lookups, formatting) stay as regular code - faster, cheaper, and testable without an API key.
builtAcross this whole codebase, actually - chunking/embedding/caching/eval-scoring are all plain code; only generation, decomposition, guardrail checks, and tool-routing decisions are real LLM calls.
In an extraction-then-validate-then-decide pipeline, which steps need an LLM?
  • Only the step that genuinely needs language understanding (e.g. parsing varied document layouts). Arithmetic/validation must be code - an LLM can get numbers wrong with no reason to accept that risk. Policy decisions belong in config, not a prompt.
builtai/doc_processing/pipeline.py's ingestion flow: LLM only for chunk-worthy text extraction; chunk-size/table decisions are plain code in text_chunker.py.
Write the basic agent loop in pseudocode.
  • for step in range(max_steps): response = model(messages, tools); if no tool call: return response; else: run tool, append result, continue. After the loop ends with no answer, return a clear "ran out of steps" result, never silence.
builtNear-identical real code in orchestration_agent.py's run_agent().

Tool calling with parameter schemas

How does tool calling actually work - does the model run the tool itself?
  • No. The model only replies with a tool name and arguments; your own code runs the real function and sends the result back. The model picks a tool mainly from its description, so descriptions matter more than names.
builtagentic_tools.py's 3 tools, each with a name/description/JSON-schema, called via LangChain's own tool-calling convention.
What makes a good parameter schema?
  • A one-line description per field saying the exact expected format, enums wherever the values are a fixed set (stops invented values), explicit min/max and required fields. Good descriptions do more for accuracy than good types.
builtTool schemas are plain JSON-schema dicts today, not Pydantic models - flagged as a real, open gap (confirmed via a direct course-coverage check this project ran), not silently assumed covered.
The model keeps picking the wrong tool - what do you check first?
  • Overlapping tool descriptions (the most common cause) - rewrite to say what each tool is not for. Check for confusing names, too many tools exposed at once, and whether you're showing only the tools relevant to the current step.
builtsingle-agentic-rag exposes a small, fixed toolset (3 tools) specifically to keep this risk low; multi-agentic-rag's Planner (planner_agent.py) does the equivalent routing one level up, picking which agents run rather than which tool a single agent calls.
A tool call arrives with invalid arguments - what should happen?
  • Don't run it and don't silently fix the value. Validate against the schema, send a specific error back to the model (which field, which rule, a valid example), allow one or two retries, then stop.
differentTools in agentic_tools.py return a plain error string on bad input (verified in tests) rather than a structured schema-validation error with a retry budget - close in spirit, less formal.
How would you make a destructive tool (e.g. delete_account) safe?
  • Split preview/confirm into two tools so one call can't reach it; require human approval for anything marked destructive; use soft-delete with a restore window; check permissions inside the tool itself, never trust the schema alone.
noneNo destructive tool exists in this project's own toolset - every real tool is read-only (retrieve, look up leave data). The pattern would matter the moment a write-capable tool is added.

Deterministic reflex responses

What is a deterministic reflex response, and when do you need one?
  • A response that's exactly the same every time for a given input - from a template or lookup, not generated. Needed for anything that must be word-perfect (legal text, prices). Temperature 0 reduces variation but doesn't guarantee it - model versions change over time too.
noneNo templated/lookup-only answer path exists - every real answer in this project passes through an LLM generation step at least once, even the MCP fast-path (which returns real tool data, formatted, not a canned string).
How would you build a reflex layer in front of an agent?
  • A function that returns an answer or None to fall through - try exact match, then keyword/regex, then similarity search, in order. Pick what goes in it from real traffic, and track the hit rate so it isn't confidently answering the wrong thing.
builtThis is a precise description of try_route_to_mcp() - keyword match, returns a real result or None to fall through to full retrieval.

Logs & unit tests

What should you log on every agent run?
  • A run/session ID, which model and prompt version, every step's prompt/reply/tool-call/result, tokens and time per step, and why the run stopped - as structured data, never passwords or PII in plain text.
differentlog_backend_call() (used throughout) logs structured step-level data per backend call. No single run/session ID threads every log line yet - that's the same gap as "correlation ID" below, tracked once in BACKLOG.md, not duplicated per topic.
How do you unit-test an agent when the model's output changes every time?
  • Test everything that isn't the model as normal code. Replace the model with a fake returning a scripted reply so the loop/retries/error paths are fully predictable. For the rare case that truly needs the model, check properties ("valid JSON", "right tool chosen"), not exact text - and keep those slower tests in their own suite.
builtThis is this project's whole testing philosophy, stated directly in CLAUDE.md: "No test needs a real API key" - every client has a fake matching its real signature exactly (tests/conftest.py).
02Multi-Agent Systems (Planner-Executor-Critic)21 cards, from 22 source questions

Planner-Executor-Critic pattern

What is a multi-agent system, and when is it the wrong choice?
  • Several agents, each with a narrow job, passing structured messages instead of one agent doing everything. Costs more (every agent is another model call) and adds a coordination layer with its own bugs. Wrong choice most of the time - use it only when steps genuinely benefit from parallelism or different permissions, and prove the win with a real test set.
builtmulti-agentic-rag is a real instance (Planner + 5 parallel domain agents + Reviewer, multi_agent_pipeline.py) - built specifically because some queries genuinely need more than one data source answered in parallel (KB + live leave data + web search).
Explain the Planner, Executor, and Critic roles.
  • Planner: turns the goal into steps. Executor: runs one step at a time, calling tools. Critic: checks the executor's work and says accept, retry, or replan - the piece that catches mistakes before the user sees them.
differentPlanner and Executors are real (planner_agent.py + 5 domain agents). The third node, reviewer_agent.py, is explicitly a merge step, not a Critic - no accept/retry/reject verdict exists. Recorded directly as decision MA-3 in multi-agentic-rag/decisions.html, not left implicit.
What should the planner's output look like?
  • Structured JSON, not prose - each step with an ID, which tool/agent runs it, inputs that can reference an earlier step's output, a depends_on list, and success criteria a critic can check against. Validate the plan (tools exist, no loops) before running anything - catching a broken plan costs one function call; running half of one costs real money.
differentPlannerOutput is just {tasks: [{agent, focus}]} - no depends_on, no success criteria. A deliberate simplification (decision MA-5): every dispatched task runs in parallel via LangGraph's Send(), so there's no real dependency graph to express yet.
The planner does well on simple requests, badly on complex ones - why, and how do you fix it?
  • One planning call can't hold a long plan together coherently. Fix: plan in two levels (phases first, detail later), replan after each phase instead of committing everything up front, and add a critic that checks the plan before anything runs.
noneNot a live concern yet - the Planner here does one shallow classification pass (which agents, what focus), not a deep multi-level plan, so this failure mode hasn't shown up.
Design a multi-agent system for automated code review.
  • No planner needed if the workflow is always the same (a fan-out, not a plan). One step finds changed files, several narrow reviewers (correctness/security/performance/style) run in parallel on the diff, a verifier tries to disprove each finding before it's shown (LLM reviewers produce confident false alarms), then merge and sort by severity.
noneOutside this project's own domain (HR benefits, not code review) - included for completeness since it's a named interview topic, not because this project implements it.

Critic-based quality evaluation

What does a good critic return, and how is it used?
  • A decision (accept/retry/replan) plus specific, actionable problems - "quality: 6/10" tells the executor nothing it can act on; "missing the Q3 revenue figure" does. Limit retries per step and per run so one stubborn step can't eat the whole budget.
noneNo critic exists in this codebase to return a verdict from (see MA-3) - this answer is the textbook shape, not a description of real behavior here.
What should a critic actually check, concretely?
  • Check what you can verify, not what you have to feel. Citation-points-to-a-real-source and covers-every-sub-question are both plain lookups, no model needed. Only the harder judgment (faithful to sources?) needs the model - run the cheap checks first so most rejections cost nothing.
differentThe groundedness/completeness scoring this project does run (evaluate_groundedness/evaluate_completeness, DeepEval-backed) happens after the final answer is produced, for observability - not as a gate that can send work back for a retry.
Your critic accepts bad output about a third of the time - what do you check?
  • Measure it first against real labeled examples. Check what the critic can actually see (inputs/tool results/criteria, not just the output). A vague rubric gets agreeable answers; replace it with a specific checklist. If the same model wrote and reviewed the output, it shares the same blind spots - use a different one.
noneNo critic to debug - same gap as above.

Orchestration frameworks: CrewAI, Autogen

What do CrewAI and Autogen do, and when would you build your own instead?
  • Both are libraries for wiring multiple agents together so you write less plumbing. CrewAI thinks in roles/tasks; Autogen thinks in conversations between agents. Building your own is a few hundred lines and full control of prompts/logging - common path is prototype with a framework, hand-roll once the shape is clear.
differentNeither framework is used - orchestration is a real LangGraph StateGraph (multi_agent_pipeline.py), which is lower-level than CrewAI/Autogen but higher-level than hand-rolling the dispatch/merge logic from scratch.
Three agents run in parallel, then results are merged - how do you write that?
  • Group independent steps into a level, run the level with asyncio.gather() (or your framework's own fan-out primitive), cap concurrency with a semaphore, pass return_exceptions=True so one failure doesn't cancel the others, and record start/end time per agent so you can see which one was slow.
differentReal parallel fan-out exists, but via LangGraph's own Send() API (dispatch_to_agents()), not raw asyncio.gather() - the framework's own primitive does the same job.
How do you add a human-approval step without blocking the whole system?
  • Gate only irreversible steps (spend money, delete things), not every run. Save the run's full state so it can pause for hours and resume later rather than holding a process open. Send approvals to a queue with what/why/impact, one click to approve/reject.
noneNo human-in-the-loop gate exists anywhere in this project's agent flows today - every tool is read-only, so nothing yet needs this kind of approval step.

Task decomposition & message passing

How would you split "research this company and write a summary" into subtasks?
  • Split by what can be researched independently (financials, competitors, leadership, news), not by sections of the final document - those run in parallel since none depends on the others. One writer agent then takes all the structured findings and writes the summary; don't give each agent a section to write, or you get disconnected pieces.
builtExactly this shape - 5 domain agents each own an independent data source (KB, leave ops, SQL, analytics, web search), running in parallel, then reviewer_agent.py is the single writer that synthesizes them into one answer.
Should agents pass plain text or structured data to each other?
  • Structured data with a defined shape at every boundary - plain text makes each agent guess what the last one meant, and small wording changes break things silently with no error anywhere. Text is fine inside a field (a summary is a string); control information (type, sender, trace ID) should be structured.
builtEach domain agent returns a fixed dict shape (agent/focus/result/sources/latency_ms, see multi_agent_pipeline.py's node functions) - structured control fields, free text only inside result.

Cost/latency tracking

How do you track cost and latency across a multi-agent run?
  • Record tokens in/out, model, and time on every single model call; roll up per step, per agent role, per whole run. The two numbers that matter: cost per finished request, and p95 total time - then find the biggest single contributor and fix that first.
differentlatency_ms per stage and llm_call_count are real and returned on every response (multi_agent_pipeline.py). Per-domain-agent token capture specifically is a known, logged gap (BACKLOG.md) - the overall count is real, the per-agent token breakdown isn't yet.
Write a budget guard for an agent run.
  • A budget object with token/dollar/time/step limits, checked before every model call (checking after is too late - you already paid). Raise a clear exceeded-error the orchestrator can catch and turn into a partial result; make counters thread-safe since parallel agents update them at once; warn at 80% so monitoring sees it coming.
noneNo budget enforcement exists anywhere in this project - only the fixed DEFAULT_MAX_ITERATIONS = 5 step cap (single-agentic-rag), nothing dollar- or token-denominated.
Your multi-agent version costs 8x more and is 15% better - what do you do?
  • Find out where the 15% actually comes from. If it's concentrated in the hardest slice of questions, route only those through the expensive path - usually captures most of the gain for a fraction of the cost. Try removing parts individually; often one piece (e.g. the critic alone) accounts for most of the improvement.
noneNo A/B harness exists yet to even measure this comparison (see CICD-BRANCHING-STRATEGY.md's own "Phase 8, still planned" note) - the question is relevant the moment genai-rag and multi-agentic-rag are compared head to head.

Multi-agent debugging patterns

The critic keeps rejecting and the executor keeps producing the same thing - how do you break the loop?
  • Detect it: hash the output each round and compare to previous rounds - near-identical output after feedback means the feedback wasn't usable. Always cap retries per step as a backstop regardless of cause. After repeated failures, escalate to the planner; if that fails too, stop and explain why.
noneNo critic-executor loop exists to get stuck - directly follows from the no-Critic gap (MA-3/MA-4).
How do you trace a multi-agent run so you can debug it?
  • A tree, not a flat log - run at the top, plan steps below it, agent/tool calls below those. Every level records inputs, outputs, tokens, time, status, so you can tell a bad plan followed correctly from a good plan followed badly, which a flat log can't show.
differentLangSmith tracing exists and gives this tree shape automatically when enabled (common/observability/langsmith_tracing.py) - off by default (free-tier trace budget), so it's available, not always on.
One agent in a five-agent pipeline fails - what are your options?
  • Retry for transient errors; degrade (skip that agent, mark the result partial) for a nice-to-have step; replan for a genuinely wrong route; fail fast only when the step is essential with no alternative. Mark each step critical or not in the plan - don't use one global rule for all of them.
differentToday it's always "degrade silently" - a failing domain agent returns an "Error: ..." string (e.g. lms_ops_agent.py) that flows straight to the merge step with no retry/replan/fail-fast branch. Recorded as decision MA-4, an accepted gap at today's traffic, not a hidden bug.
How do you unit-test a single agent inside a multi-agent system?
  • Because messages are structured, an agent is just a function from input to output - save real production messages as fixtures, replace the model with a fake, and test prompt-building/validation/error-handling fully predictably. For real model behavior, check properties, not exact text.
builttest_multi_agent_pipeline.py/test_planner_agent.py/test_reviewer_agent.py all follow exactly this pattern with fakes, no real API key required.
Should agents share one memory store, or pass everything in messages?
  • A shared mutable store is convenient but hides who depends on what, breaks under parallel writes, and can't be replayed deterministically. Messages make dependencies visible and each agent independently testable; a good middle ground is a shared read-only context nobody can mutate.
differentMixed: domain agents communicate via structured messages (no shared mutable store between them), but multi-agentic-rag's own Planner never loads conversation memory at all yet (confirmed - multi_agent_pipeline.py never calls load_history()), a real, open gap, not the "shared store" problem this question is about.
03Agent Communication Protocols (MCP, A2A, ACP)20 cards, from 22 source questions

Intro to MCP, A2A, ACP

What is MCP, and what problem does it solve?
  • Model Context Protocol - a standard way to connect an agent to tools/data, like one plug shape instead of a custom cable per device. An MCP server exposes tools/resources/prompts; the agent discovers what's available rather than having it hardcoded, so a new server-side tool needs no agent redeploy.
builtReal and live - this project connects to hrb_lms_mcp as a genuine MCP server over OAuth2 client-credentials auth (Phase 53), with its tools registered via a real tools/list discovery call, not hand-entered (Phase 50).
MCP vs. A2A vs. ACP - what's the real distinction?
  • MCP: agent-to-tool. A2A: agent-to-agent, for independently-built agents working together as peers. ACP: a general umbrella term for agent-communication rules. They're complementary - an agent can use MCP for its tools and A2A to delegate to another agent.
differentMCP is real (above). Nothing in this project is A2A in the formal sense - the domain agents in multi-agentic-rag are all owned and orchestrated by this same codebase, not independently-built peer agents negotiating as equals.
Why would you use MCP instead of just writing tool functions directly?
  • Pays off when the same tools are needed by several different agents/apps, or when another team owns the tool and should own its interface. Gives you discovery (no hardcoded list) and lets a new tool appear with no agent redeploy. Cost: another process to run, plus network calls.
builtExactly the real reason MCP was adopted here - hrb_lms_mcp's leave data is owned by a separate service; this project calls it as a client rather than re-implementing that data access itself.
What are the security risks of connecting an agent to an external MCP server?
  • Tool descriptions come from the server and the model reads them as instructions - a malicious description can redirect the agent (prompt injection). Data the server returns is untrusted input, not fact. Only connect to reviewed servers, keep permissions narrow, require human approval for destructive tools, log every call.
differentThe real MCP connection (hrb_lms_mcp) is first-party and OAuth2-authenticated (not an arbitrary external server), which narrows but doesn't eliminate this risk - its tool descriptions are still read as instructions by the model. No explicit prompt-injection-from-tool-description defense is documented as tested.

Structured messages: states, transitions

Why do agents need a structured message format instead of free text?
  • Free text makes the receiving agent guess; a structured message has fixed, validatable fields (type, sender, recipient, correlation ID, payload) that catch bad messages at the boundary instead of three steps later, and can be saved and replayed to test one agent alone.
builtEvery domain-agent result in multi_agent_pipeline.py follows one fixed shape; MCP calls themselves are real JSON-RPC-style structured messages by protocol definition.
What are states and transitions in an agent conversation, and why write them down?
  • A state is where things currently stand (e.g. "awaiting approval"); a transition is a move between states, triggered by a message or event. Writing them down turns vague behavior into something you can reason about, makes illegal moves impossible, and makes the system resumable (save state, reload later).
differentLangGraph's own StateGraph (multi_agent_pipeline.py) is a real state machine with explicit nodes/edges - but it's a fixed, single-pass DAG (planner -> dispatch -> domain agents -> reviewer -> end), not one with conditional states like "awaiting approval" that this project actually uses today.
Design the message format for two agents working on one task.
  • message_id (dedupe), correlation_id (tracing), sender/recipient, type (request/response/error/status), payload validated per type, timestamp, schema_version so the format can evolve without breaking older agents.
differentThe real domain-agent result dict has most of these conceptually (agent = sender, result = payload) but no explicit message_id, correlation_id, or schema_version field - see correlation-ID gap below, same root cause.
How do you version message schemas as your agents change?
  • Put a schema_version field in every message from day one. Only make additive changes when you can; when you must break it, run both versions side by side, update receivers to accept both before updating senders, and log unknown fields rather than rejecting them.
noneNo message versioning exists - internal dict shapes change freely since every caller is this same codebase, deployed together. Would matter the moment an external, independently-deployed consumer exists.

LangGraph communication graphs

What is LangGraph, and why model an agent as a graph instead of a chain?
  • Builds a workflow as nodes (a model call, a tool, a bit of code) and edges (what runs next, possibly conditional on the result). A graph handles loops and branches a straight-line chain can't, and supports pausing/resuming - which matters for human-approval steps.
builtReal, live - multi_agent_pipeline.py's _build_graph() is a genuine LangGraph StateGraph, chosen specifically for its Send() fan-out over plain Python for the parallel-dispatch step.
What is conditional routing in an agent graph, and how do you avoid infinite loops in it?
  • An edge whose destination is picked by a function reading the current state - e.g. "retry" goes back, "accept" goes forward. Always include a counter in state with a hard exit path; make the routing function pure code, not a model call, so it's predictable.
differentConditional routing is real (dispatch_to_agents() picks which domain-agent nodes run), but it's a one-shot fan-out with no loop-back edge anywhere in the graph - so there's no retry loop to guard against yet (also follows from no-Critic, MA-3).
Draw the graph for a research agent with a review step.
  • Start (plan) -> Search (possibly parallel sources) -> Write (draft from findings) -> Review (check draft against sources) -> conditional edge: accept goes to end, reject goes back to search, with a retry counter and an error edge from every node to a failure handler.
differentThis project's real graph is the fan-out/merge shape (Planner -> parallel domain agents -> Reviewer -> End) - no reject-and-loop-back edge, matching the no-Critic decision (MA-3) again rather than this textbook review-graph shape.

WebSockets for agent streams

What is a WebSocket, and why would an agent use one?
  • A connection that stays open so either side can send messages anytime, unlike request-then-close HTTP. Lets you stream the answer as it's written, push progress updates ("searching documents"), and let the user cancel mid-run. Server-sent events are a simpler alternative when you only need server-to-client.
noneNeither exists - every endpoint in this project is plain request/response HTTP. A deliberate, recorded choice (not an oversight) - see the polling-over-streaming decision in rag-architecture-layers.html's own history.
What has to be handled when a WebSocket connection drops mid-run?
  • Don't stop the run just because the socket closed - keep it going server-side, give every message a sequence number, let the client say which number it last received on reconnect, and replay from there. Add exponential backoff and periodic heartbeats so both sides notice a dead connection.
noneNot applicable - no streaming connection exists to drop.
How would you stream an agent's output to a browser?
  • Open a WebSocket or SSE connection at run start, send typed events (token, tool_start, tool_end, error, done) rather than raw text, include run ID and sequence number on every event, and send a final done event with the complete answer so the client can verify.
noneNot built - every response today is one complete JSON payload returned after the full pipeline finishes, no incremental events.

Error propagation & retry logic

An error happens deep inside a chain of agents - how should it travel back?
  • Wrap it so the caller knows which agent failed and at which step, keep the original error (don't replace it with something generic), carry the correlation ID, and mark whether it's retryable or permanent - the key field. Never swallow an error into an empty result; that hides the failure.
differentA failing domain agent's error becomes a plain string embedded in a normal-looking result ("Error: ...") rather than a distinct, typed error object the orchestrator can branch on - exactly the gap recorded as MA-4.
Write retry logic with exponential backoff - and which errors should never be retried?
  • Loop up to 3-5 attempts, only for retryable error types (timeouts, 429s, 5xx), doubling the wait each time with a small random jitter and a cap, respecting a Retry-After header if present. Never retry bad input, auth/permission errors, not-found, or any non-idempotent action that may have already succeeded (e.g. a payment) - retrying those either can't help or can cause real harm.
noneNo retry-with-backoff exists on any LLM or vector-store call in this project - confirmed directly across every client (openai_client.py, anthropic_client.py, bedrock_client.py, open_router_client.py). Only tavily_client.py (web search) has any. A real, documented gap, not an oversight glossed over.

Multi-agent debugging & tracing

What is a correlation ID, and why does it matter?
  • One ID generated at the start of a request, passed to everything it touches - every log line, message, and tool call carries it, so one complaint means searching one ID instead of guessing across separate log files. The cheapest debugging feature you can build, and the one people skip.
noneConfirmed not built - grepped the whole codebase for a real correlation/request-ID field threaded through log lines; none exists. Listed as an open item in BACKLOG.md's Observability section, worth adding once this app sees real concurrent traffic.
How would you trace a request that passes through four agents?
  • Spans in a tree - one root span for the request, child spans per agent, their tool/model calls as children of that. Every span carries the correlation ID, start time, duration, status, inputs, and outputs. OpenTelemetry is the general standard; LangSmith gives this shape for LLM apps directly, out of the box.
differentLangSmith tracing is real and gives exactly this tree shape when enabled - but it's off by default to stay inside the free-tier trace budget (LANGSMITH_ENABLED=false), so it's available infrastructure, not an always-on practice today.
One agent is slow but you can't tell which - how do you find out?
  • Look at the trace tree sorted by span duration. Check whether it's the model call (usually a too-long prompt) or a tool call (usually a slow external API). Check whether steps that could run in parallel are actually running sequentially. Use p95, not the average - averages hide the bad cases.
differentPer-stage latency_ms is captured and returned on every real response (both genai-rag and multi-agentic-rag), which answers "which stage" without needing a trace tool - genuinely useful, just coarser-grained than full per-span tracing.
Two agents disagree about who should do a task - how do you avoid that?
  • Don't let agents negotiate ownership if you can avoid it - unreliable and slow. Assign each task to exactly one agent in the plan before anything runs, with clearly non-overlapping job descriptions. If delegation is unavoidable, use a single coordinator that decides - one decision-maker beats several agents negotiating.
builtExactly this - the Planner assigns each task to exactly one named agent ({agent, focus}) before dispatch; domain agents never negotiate with each other, and their job descriptions (KB/leave-ops/SQL/analytics/web-search) are non-overlapping by design.
