Microservices Rollout Plan

Companion to service-boundary-decision.html — that doc decided what the services and schemas are; this one covers how to build them: shared libraries, final schema naming, the dependency-ordered sequence, and the HLD/LLD documentation every service needs regardless of whether it already exists.

1Shared libraries across services — share infra & NFR code, not business logic

CategoryShare?Lives inWhy
Infra connectors (ChromaDB/Pinecone, Postgres, S3, LLM provider)sharehrb_common_libsAlready a Base*Client/Gateway pattern in one repo — this is exactly what it generalizes into across repos
NFR / cross-cutting (structured logging, request_id, retry/backoff, error_codes + json_error, guardrails core)sharehrb_common_libsEvery service needs these identically — duplicating risks inconsistent observability, which breaks the explainability work already built
Wire-contract models (UserProfile, common envelopes)share, contracts onlyhrb_common_libsInterface shape, not behavior — safe to share
Domain/business logic (chunking strategy, HITL rules, 401k rules, audio processing rules)do not sharestays in the owning serviceSharing business logic across service boundaries recreates tight coupling — the classic "distributed monolith" trap
↳
Repo and versioning: new repo hrb_common_libs, installed as a pinned git-tag dependency (e.g. git+https://github.com/.../hrb_common_libs.git@v0.3.0) in each service's requirements.txt — never a floating/latest dependency. Pinning means every service upgrades deliberately; a change in the shared lib can't silently break a service that hasn't opted in yet. A private PyPI index would be overkill for a solo project — git-tag pinning gets the same safety for free.

3Dependency-ordered execution sequence — lowest-risk, additive changes first

0Foundations — zero behavior changerisk: low
  • New repo: hrb_common_libs — extract Base*Client/Gateway code, tag v0.1.0. Touches nothing live yet.
  • Schema move, same repo: create the 10 schemas above in the existing Neon database, ALTER TABLE ... SET SCHEMA, update every *_store.py to qualify table names. Done before any physical service split — isolates this risk from the split's risk.
  • Rename: hrb_chatbot_v2 → hrb_chatbot_service (repo/folder/LangSmith) — cheap, do it here since you're already touching things.
↓
1api_gateway_service — additive, fronts the still-undivided backendrisk: medium
  • Prerequisite: Redis live in production (needed for shared rate-limit state) — this was already next in your own deployment-guide order; now it's a hard blocker, not optional.
  • New repo: hrb_api_gateway_service. Build RBAC (decide: absorb api/gateway/rbac.py or coexist), CORS, rate-limit, contract validation.
  • Cutover: point hrb_chatbot_ui at the Gateway, which forwards 1:1 to hrb_chatbot_service (still undivided). Proves the Gateway in isolation before anything else changes.
↓
2Split RAG ingestion / retrieval — the real migrationrisk: highest
  • New repos (per your own ask — protects the working app): rag_ingestion_service, rag_retrieval_service, each depending on hrb_common_libs.
  • Move ai/doc_processing/** + ingestion routes → ingestion repo. Move ai/rag_pipeline/** + ai/agents/** + retrieval routes + api/admin/** (Support, co-located) → retrieval repo.
  • New ECR repo + App Runner service + IAM deploy user + deploy.yml per new service (mirrors the existing pattern).
  • Gateway routes ingestion-shaped vs. retrieval-shaped requests to the right service.
  • Keep hrb_chatbot_service running dormant as a rollback safety net until both new services are verified against real production traffic — don't decommission on day one.
↓
3New capabilities — build fresh, no migration riskrisk: low (isolated)
  • chat_audio_service, plan_401k_service — new repos, depend on hrb_common_libs. Can start in parallel with Phase 1/2 since they touch no existing working code.
↳
Milestone framing: each phase above is a shippable, independently-verifiable milestone — Phase 0 alone is a safe place to pause; Phase 1 alone delivers a working Gateway with zero RAG-pipeline risk; Phase 2 is the one phase that actually touches working functionality, which is why it's last and gets the dormant-fallback safety net.
