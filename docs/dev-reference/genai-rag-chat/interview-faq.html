Memory & Session Persistence8 cards
Why does a chatbot need memory at all, and what's the simplest form (buffer memory)?
  • The model has no memory of its own between calls - anything it should remember must be sent again in the next prompt. Buffer memory is the simplest answer: keep the last N messages and send them all every time. Nothing is lost within that window, but the prompt grows every turn until you hit the context limit.
differentReal, but not windowed - load_history() (conversation_memory.py) returns the entire stored history for a conversation every time, not just the last N messages. One durable Postgres store, no separate short-term/long-term split despite the module's own docstring using those terms (recorded directly as decision GR-4).
What is summary memory, and what does it cost you?
  • Instead of keeping every message, an LLM call periodically rewrites the older part of the conversation into a shorter summary once the buffer fills up. Keeps the prompt small no matter how long the conversation runs, at the cost of an extra model call each time and real detail loss that repeated summarization can compound.
noneNot built - no summarization step exists anywhere in conversation_memory.py. A real, undocumented-until-now gap: nothing currently stops the prompt from growing without bound on a long conversation (see GR-4's own trade-off note).
What is vector memory, and when do you actually need it?
  • Past messages are embedded and stored in a vector store; each new message searches that store and pulls back only the relevant older turns - RAG applied to the conversation itself. Needed when history is long and older facts still matter, at the cost of possibly missing context that matters but doesn't match the search.
noneNot built - this project's conversation memory has no search/retrieval step over past turns at all, only full linear replay.
A support bot breaks after 40 turns - which memory type do you actually ship?
  • Most likely the prompt has outgrown the context window - check that first, it's usually a hard error, not a mysterious quality drop. What most real systems ship is a hybrid: keep the last 5-10 turns exactly, summarize older ones, and store hard facts (order number, customer name) as structured fields that never get summarized away.
noneThis project's own full-history approach would hit exactly this failure mode on a long enough conversation - there's no truncation, summarization, or structured-fact extraction to fall back on, an accepted gap at today's traffic (GR-4).
How do you store structured facts about a user separately from the chat history?
  • A small profile object (name, preferences, open items) in a normal database, not buried in the conversation log - update it when the user tells you something worth remembering, inject it as a short block into every prompt (cheap in tokens), and let users see/delete what's stored about them.
noneNot built - no structured per-user fact store exists separate from the raw conversation turns themselves.
What is session persistence, and where would you store chat sessions?
  • Saving a conversation so closing the app and coming back doesn't lose it - message history with roles/timestamps, the session ID and owner, any summary/facts, model and prompt versions used. A normal database like Postgres is the right default - easy to query and back up; add Redis in front only if active-conversation reads need to be very fast.
builtReal, Postgres-backed (Phase 76) - replaced an earlier in-memory dict specifically because a server restart wiped every live conversation. conversation_turns table, keyed by conversation_id, survives restarts by design.
Two browser tabs have the same conversation open - what can go wrong, and how do you fix it?
  • Both tabs read the same history, both append - messages can end up out of order or one tab's write overwrites the other's. Fix: append with a server-assigned sequence number instead of rewriting the whole history, use a version check so a stale write is rejected, or simplest, allow only one active tab per session.
noneNo concurrency control exists - save_turn() is a plain append with no sequence number or version check, so two simultaneous writers to the same conversation_id would both succeed with no conflict detection. Not yet a problem at today's traffic, but a real gap, not an invisible one.
How do you keep personal data safe when it's flowing through a conversation memory system?
  • Chat logs contain personal data - set a retention policy, and make it possible to delete one user's sessions completely on request, not just hide them from the UI.
builtReal, exercised - delete_conversation() removes every turn for a conversation, the documented logic behind this project's own NFR delete-my-data endpoint. No separate time-based retention policy auto-expires old conversations, though; deletion today is request-driven, not scheduled.
Persona & Dialogue Design3 cards
What makes a good agent persona?
  • A short, specific description of who the agent is and how it speaks - role, tone, how long answers should be by default, what it must never do, and what to say when it doesn't know something. Concrete beats vague ("friendly but brief, two sentences by default" beats "be helpful") - a long persona eats context and gets ignored anyway.
builtReal system prompts exist per mode (prompts/agent_prompts.py) with a defined role and scope (HR benefits assistant) - tested but not formally measured for adherence over long conversations.
An agent's tone drifts over a long conversation - why, and what do you do about it?
  • The persona sits at the top of a long prompt, far from where generation happens, and loses influence as the prompt grows; the model also copies the style of its own recent (possibly long) replies, so one long answer snowballs into more. Fixes: repeat a short version of the persona right before the latest message, and cap output length in code rather than trusting the prompt alone.
noneNot measured - no test checks answer length/style consistency across a long conversation (turn 2 vs. turn 30), and the system prompt isn't re-injected mid-conversation beyond its normal place in the message list.
How do you design what happens when the agent doesn't understand the question?
  • Decide this on purpose rather than leaving it to the model - say clearly it didn't understand rather than guessing, ask one specific clarifying question (not "can you rephrase?"), limit to one or two attempts then offer a human, and never loop asking the same thing. Log every one - it shows what the agent is actually missing.
differentThe no-answer-found path (relevance-bar filtering, see the retrieval-strategies FAQ) is the closest real equivalent - a clear "couldn't find this" response rather than a guess. No structured clarifying-question flow or attempt-limit exists specifically for "I don't understand" as distinct from "I don't have the data."
Voice & Multimodal4 cards, all not built
What is Whisper, and how would a voice assistant pipeline work end to end?
  • Whisper is OpenAI's speech-to-text model - audio in, text out, fairly robust to accents/noise. A voice pipeline: capture audio -> detect when the user stops speaking -> Whisper for text -> the LLM agent -> TTS for audio back -> play it. Every stage adds delay, so start speaking the first sentence while the model is still writing the rest, rather than waiting for the whole answer.
noneNot built - this is a text-only chatbot, no audio input/output anywhere in the pipeline.
TTS - gTTS vs. ElevenLabs, and how do you keep personal data safe in a voice agent?
  • gTTS is free and simple but sounds clearly robotic; ElevenLabs is paid with natural, human-sounding voices and real voice cloning/emotion control. For privacy: decide up front whether to keep audio at all, encrypt and set a short retention period if you do, check whether your STT/TTS providers train on your data, and make sure a deletion request removes audio, transcript, and any embeddings together.
noneNot applicable - no voice data of any kind is captured, so none of this privacy surface exists here.
How does an agent handle an image the user uploads?
  • Use a vision-capable model, send the image plus a question, get text back - resize before sending (most tasks don't need full resolution), check file type/size before accepting, and verify anything important since vision models still make things up.
noneNot built - no image/vision handling anywhere; every input is plain text.
A voice agent feels slow - where does the time actually go, and how do you fix mis-transcribed product names?
  • Measure each stage separately - silence detection and full-recording STT are common hidden costs, since transcription can't start until the user finishes speaking. The biggest win is streaming the LLM output and starting TTS on the first sentence immediately. For mis-transcribed names: pass a vocabulary hint to the STT call, correct known repeat-mistakes with a lookup table built from real transcripts, and ask the user to confirm critical values like order numbers.
noneNot applicable - no voice pipeline exists to have a latency budget or a transcription-accuracy problem in the first place.
Chat UI & Feedback3 cards
What makes a good chat UI for an AI agent, and how do you show a long-running agent is still working?
  • Stream the answer so progress is visible immediately, show what the agent is doing rather than a blank spinner ("searching documents"), let the user stop a bad response, show sources as links, make it obvious this is AI and can be wrong, and suggest a few starting prompts since a blank box is intimidating. For long runs: push server-side progress events rather than making the user wait on silence, and always allow canceling.
noneNo streaming exists anywhere - every response is one complete payload after the full pipeline finishes (see the system-level FAQ's WebSocket answer - a deliberate, recorded choice, not an oversight). No mid-run progress events or cancel button either, since there's no long-lived connection to carry them.
How would you collect useful feedback from chat users?
  • Thumbs up/down on each answer - low effort, so people actually use it. On a thumbs-down, ask one optional question with a few fixed reasons (easier to analyze than free text). Link every rating back to the full trace of that run, and also watch implicit signals (rephrasing the same question, abandoning the chat) - often more honest than explicit ratings.
builtReal: POST /v1/feedback takes a vote, reason_tags, and free-text notes, tied to conversation_id/message_id plus the actual question/answer text (manage_feedback.py). No implicit-signal tracking (repeated questions, abandonment) exists - only explicit votes.
What UI detail matters most for trust in an AI product, beyond the answer itself?
  • Showing real sources as checkable links, and being honest about uncertainty rather than always sounding confident - a user who can verify an answer trusts the system more than one who has to take it on faith.
builtReal sources (actual retrieved chunks, not model-generated citation markers) are returned with every answer across all 3 retrieval modes - see the retrieval-strategies FAQ's citations answer for why that sidesteps the "fabricated citation" failure mode by construction.
