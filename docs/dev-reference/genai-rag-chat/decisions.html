GR-1Kept the existing rag-architecture-layers.html Architecture doc, didn't force-fit a deck slide
Context
The RAG Ingestion pilot replaced its Mermaid diagram with a corrected PowerPoint deck export (slide 12), and the standing instruction is to standardize on that pattern. The deck's own candidate for this feature - slide 8, "Sequence: Policy Question (cache miss)" - was reviewed as a possible replacement.
Decision
Not used, this round. Slide 8 depicts a materially different target architecture: separate "Chat Gateway"/"Conversation"/"Knowledge Retrieval"/"Agent Orchestrator" microservices, a LangGraph-based orchestrator even for a plain policy question, and SQS-queued async writes for the answer cache and conversation-turn save.
Alternative
Correct slide 8 the same way slide 12 was corrected (small, targeted text fixes) - rejected after checking the real code: rag_pipeline.py has zero LangGraph references, answer_cache.py and conversation_memory.py have zero SQS references - both write synchronously, in-request. These aren't label mismatches like slide 12's were; they're structural differences from today's single-process reality, and correcting them honestly would mean substantially redrawing the slide, not editing a few text runs.
Why
rag-architecture-layers.html (Phase 170, already synced) was independently verified accurate for this exact feature before this round even started. Replacing working, accurate content with content requiring a much larger correction pass - just to match a stylistic preference - would have been a worse outcome than keeping what already works.
Trade-off
This Architecture doc looks visually different from RAG Ingestion's (still a styled HTML view, not a deck-image panel) - a real, visible inconsistency across the doc family. Accepted deliberately; flagged here rather than silently normalized by force-fitting inaccurate content. Slide 8 remains genuinely interesting as a target-state reference (a future microservices decomposition) - a candidate for its own clearly-labeled callout or companion doc later, not this round.

Revisited: see GR-5 - this feature got its own real-current-state slide after all, 2026-10-14, by building fresh rather than correcting slide 8.

GR-2Shared Redis answer cache across all 3 modes, each with its own live-data exclusion filter
Context
Correction made while writing this doc, not before: an earlier draft of this decision (and this project's own CLAUDE.md context) claimed the Redis answer cache "stays genai-rag-only." Direct inspection of orchestration_agent.py (Phase 110) and multi_agent_pipeline.py (Phase 115) found both import build_cache_key and call get_db_gateway().answer_cache().get()/.set() for real - that claim was wrong, caught before shipping rather than after.
Decision
All 3 modes share the same Redis-backed cache infrastructure, each with its own pipeline-namespaced key (build_cache_key(query, pipeline="single-agentic-rag", ...) / pipeline="multi-agentic-rag") and its own LIVE_DATA_TOOLS exclusion set ({"GetLeaveBalance", "GetLeaveHistory"}) - a result only gets cached when no tool call in it could have returned live, per-employee data.
Alternative
Cache every agentic-mode answer unconditionally, same as genai-rag - rejected: a tool call result (a leave balance, a leave history) is per-employee and time-sensitive; caching that answer and serving it to a later, different caller would be a real correctness bug, not a staleness nuisance.
Why
search_knowledge_base (the one tool genai-rag's own retrieval effectively mirrors) queries the same static document index either way, so an agentic-mode answer that only used that tool - or no tool at all - is exactly as safe to cache as a genai-rag answer. The exclusion set is scoped precisely to the tools that actually return live data, not "any tool use at all."
Trade-off
Each mode's cache-eligibility logic is duplicated (the same LIVE_DATA_TOOLS pattern re-implemented per pipeline, per multi_agent_pipeline.py's own comment: "mirrors orchestration_agent.py's own LIVE_DATA_TOOLS, one level up, at agent-dispatch granularity") rather than factored into the shared guarded-pipeline core - a real, acknowledged duplication, not yet consolidated.
GR-3Guardrails moved to a shared core instead of each pipeline wiring its own
Context
Before Phase 98, each of the 3 retrieval pipelines independently decided whether to wire in input/output guardrails and conversation memory - a direct code review found single-agentic-rag had shipped with no guardrails at all as a result.
Decision
All 3 pipelines now funnel their guardrail/memory/logging concerns through one shared run_guarded_pipeline() core (ai/rag_core/guarded_pipeline.py), even though each still does its own answer generation independently (genuinely different: fixed retrieve-then-generate vs. a tool-calling loop vs. a LangGraph multi-agent graph).
Alternative
Leave each pipeline responsible for wiring its own guardrails/memory, just fix the one found gap - rejected: that's exactly the situation that produced the gap in the first place; a shared core makes "no guardrails" structurally impossible for any future mode, not just the current 3.
Why
Guardrail/memory/logging concerns are identical across all 3 modes regardless of how each generates its answer - factoring them out removes the chance of any one pipeline forgetting to wire them in.
Trade-off
multi-agentic-rag still calls check_input/check_output directly rather than through the shared core - an earlier, still-correct implementation not yet migrated. A real, acknowledged inconsistency, not yet closed.
GR-4Conversation memory is full-history buffer memory, not summary or vector memory
Context
Multi-turn chat needs some strategy for what past conversation to send back to the model. The three common options: buffer memory (keep recent turns verbatim), summary memory (compress older turns via an extra LLM call), vector memory (embed and retrieve only relevant past turns).
Decision
ai/pre_processing/conversation_memory.py implements plain buffer memory: load_history() returns every turn ever saved for a conversation_id from Postgres, unsummarized and untruncated - no distinction between "short-term" and "long-term" memory tiers despite the module's own docstring using those terms; it's one durable store, read in full every time.
Alternative
Summary memory (rewrite older turns into a running summary once the buffer grows) or vector memory (embed turns, retrieve only relevant ones) - neither is implemented. No code path truncates, summarizes, or selectively retrieves history.
Why
Simplest option that works for this project's actual conversation lengths - no extra LLM call per turn (unlike summary memory), no extra retrieval infrastructure (unlike vector memory). Matches this project's general bias toward the simplest option that works over a more "correct" one, until a real problem forces a change.
Trade-off
A long-running conversation grows the prompt on every turn with no ceiling - no code enforces a token or turn-count limit today. This is an accepted, undocumented-until-now gap, not a hidden bug: a conversation long enough to hit the model's context window would fail loudly (a real API error), not silently lose history.
GR-5Revisited GR-1 - built a fresh real current-state diagram instead of correcting slide 8
Context
GR-1 deferred this feature's own Architecture doc, reusing rag-architecture-layers.html instead, because slide 8's target-state design (separate microservices, LangGraph, SQS) was too structurally different from the real code to honestly "correct" with small text edits.
Decision
Not correcting slide 8 - GR-1's objection to that still holds. Instead, slide 28 is a brand new swim-lane slide, built from scratch against ai/rag_pipeline/pipeline.py and ai/rag_core/guarded_pipeline.py (both read in full first), matching the real call order including a detail that doesn't match this feature's own design.html text exactly (the answer-cache check happens before conversation-memory load, not after, confirmed directly from the code). Slide 8 stays in the deck untouched, as historical reference.
Alternative
Keep reusing rag-architecture-layers.html indefinitely - rejected now because the milestone's own goal was closing the "weakest diagram" gap feature-by-feature, and a shared system-level doc standing in for a feature-specific one was flagged as exactly that kind of gap.
Why
A fresh slide sidesteps GR-1's real objection entirely - there's nothing dishonest about a new diagram that only shows what's actually true, unlike editing an existing one built around different assumptions.
Trade-off
This feature now has two architecture-shaped diagrams in the deck (slide 8, historical/inaccurate-as-target-state; slide 28, real/current) - a reader going straight to the deck instead of this doc could pick the wrong one. Mitigated by this doc's own Architecture tab pointing only at slide 28, and slide 28's own subtitle naming slide 8 explicitly.
