the App Runner deploy workflow, GitHub Secrets, the honest rollback state, and the system diagrams
01
Trigger, poll, and smoke-test the deploytrigger → poll for RUNNING → smoke test against /ping
1
Trigger the App Runner deployment explicitly
Remember: pushing :latest to ECR does not redeploy anything by itself (AutoDeploymentsEnabled=false). deploy.yml runs this on every push to master.
aws apprunner start-deployment --service-arn arn:aws:apprunner:us-east-1:418884736369:service/hrb-chatbot/f957548202f343aa8ca91f341d71d85a
2
Poll for RUNNING - don't trust the API call returning
start-deployment only starts a deployment and returns almost immediately, well before the new container is actually serving traffic. deploy.yml polls Service.Status every 10 seconds, up to 5 minutes, and fails the job outright if App Runner reports anything other than OPERATION_IN_PROGRESS while waiting, or if it times out - both real outcomes seen during this project's own first deployment attempts, not hypothetical.
aws apprunner describe-service --service-arn <ARN> --query 'Service.Status'
3
Smoke test against the live URL
One curl --fail against /ping - deliberately not /health, since this job has no reason to spend a provider call just to confirm the container booted. A non-200 fails the GitHub Actions run, so a deploy that "succeeds" by AWS's own accounting but produces a container that never comes up now fails the pipeline too, instead of leaving a broken container quietly live.
02
What CI/CD needs to even run, and what happens when a deploy failsGitHub Secrets, and the honest state of rollback
deploy.yml needs two GitHub Secrets
AWS_ACCESS_KEY_ID/AWS_SECRET_ACCESS_KEY, belonging to the scoped IAM user hrb-chatbot-github-actions-deploy (ECR push + apprunner:StartDeployment/DescribeService on this one service only - no wildcard resource beyond the unavoidably account-wide ecr:GetAuthorizationToken). Added once via GitHub's own UI, not via any API.
If a deploy fails: go to logs first, not your Python code
The generic CREATE_FAILED/zero-app-logs pattern from the Production Monitoring Guide's CloudWatch panel is almost always the image itself (manifest format, architecture) when the container never starts at all - check that before debugging application logic that never ran.
⚠ No formal rollback procedure exists today
deploy.yml tags the image :latest only - there is no :<sha> tag to redeploy from if a new image breaks something the health check doesn't catch. docs/agent-reference/CICD-BRANCHING-STRATEGY.md flags SHA-tagging as a known, deliberately queued follow-up, not yet built. Today's practical path is reverting the source commit and rebuilding/redeploying from a known-good commit - there's no tagged-image shortcut.
03
The norm that sits above all of thisnothing above gets exercised without a human looking first
Per this project's own working norms (CLAUDE.md, added 2026-10-14): nothing gets pushed, deployed, or synced to AWS without the developer's own local review and explicit go-ahead first - even when a push is clearly the obvious next step, ask anyway, every time, not just the first time. Every command in this section is meant to be run and verified locally (or read and understood) before git push to master is the thing that actually arms deploy.yml.

Worth adopting as a general practice, not just a rule specific to this repo: a pipeline this automated (test → build → push → deploy → smoke-test, all machine-triggered on a single branch push) is exactly the kind of pipeline where "it'll probably be fine" silently becomes the actual review process, one push at a time, unless a human deliberately stays the last gate before anything goes live - a discipline a solo developer has to choose to keep, since there's no second reviewer here to catch it if they don't.

High-level: what runs whereevery real deployable in this system, zone by zone - Users / Edge-DNS / AWS / External Services

4 real deployables: hrb-chatbot (App Runner, this repo), hrb-lms-mcp (App Runner, the sibling hrb_lms_mcp repo), hrb-chatbot-index-document (Lambda, Phase 88), and the hrb_chatbot_ui static site (S3 + the system's only CloudFront distribution, Phase 117). No ECS, no ALB, no CloudFront+WAF in front of the API itself, no Cognito, no ElastiCache - that's the reference AWS screenshot's own architecture, not this one.

Doc discrepancy found while building this, flagged rather than silently resolved: docs/agent-reference/AWS-DEVOPS-RUNBOOK.md's top-level "What's actually live vs. planned" table still says S3/Lambda are "not implemented at all." That's stale - docs/agent-reference/RAG-ROADMAP.md's Phase 88/89 built and verified the real S3 → SQS → Lambda async ingestion path live on AWS, 2026-10-06 (additive alongside the still-live synchronous upload, not a replacement). Worth a separate pass to update that runbook table; not done here.
Don't conflate the two Postgres uses: RAG_METADATA_STORE (one row per uploaded document) is still sqlite in production, per the Production Monitoring Guide's own card on this - a hosted Postgres for that store hasn't been provisioned. The Neon hr_chatbot database shown in the External Services zone is a separate, already-live thing: this project's own hrb_chatbot_v2_core/_sessions schemas (admin credentials, the reused MCP tool registry) plus hrb_lms_mcp's own hrb_emp_lms/hrb_lms_mcp_auth schemas (Phase 118) - see docs/dev-reference/database/db-model-overview.html.
