Production Readiness Scorecard

Where this project stands against the AI-reliability evaluation framework (rubric method, golden datasets, confidence-trap avoidance) and the RAG performance framework (latency staging, re-ranking trade-offs, caching) — checked against the live code, not assumed.

Reliability Evaluation
Strong in substance, not yet enforced

Golden dataset, groundedness scoring, and a real release gate all exist and are well-designed. The gate is manual (pytest -m eval), not wired into CI — nothing stops a deploy if it's skipped.

RAG Performance Engineering
Early-stage

No re-ranking stage, no TTFT/streaming, no rolled-up per-request latency breakdown, and zero response caching of any kind. Personalization exists and would complicate caching — but there's no base cache yet for that to apply to.

Define success & failure Partial Forbidden actions are documented, but scattered — the agent system prompt states "never invent a policy detail or a balance number" (orchestration_agent.py), and NeMo Guardrails' rails define unsafe-input/output behavior. Matches the guideline's "situations not covered" requirement directly.

RAG Performance Engineering

GuidelineStatusEvidence
Stage-by-stage latency measurement Partial log_backend_call() logs latency per individual backend call (e.g. chromadb vector.query, openai chat.ask) with distinct service/operation tags — the raw signal exists. Never rolled up into a per-request "retrieval took Xms, generation took Yms" report.
TTFT vs. total response time Gap No streaming anywhere in the codebase (confirmed: zero matches for streaming/TTFT). Responses are generated in full before returning, so TTFT isn't a meaningful concept yet — it would equal total latency.
Re-ranking decision Gap No re-ranking stage exists (confirmed: zero matches for rerank/cross-encoder anywhere). This isn't a documented "retrieval is strong enough to skip it" trade-off decision — it was simply never built or evaluated either way.
Caching Gap Zero response caching of any kind. The only "cache" hits in the codebase are an OAuth2 Bearer token cache and generic client-singleton caching — unrelated to RAG response reuse.
Personalization Strong Real, not hypothetical: server-side conversation memory (Phase 58) and per-employee MCP tool scoping (GetLeaveBalance/GetLeaveHistory, scoped by employee_id from user_profile) both exist. This is exactly the kind of personalization that would make caching non-trivial — relevant context for when caching eventually gets built.

If this needs to be demo-ready at a production-grade level, in priority order

1
Wire the release gate into CI
The single highest-leverage fix: the eval harness already exists and is well-designed. Today it only protects a deploy if someone remembers to run it manually.
2
Write a structured rubric per task, not just keyword + holistic score
Replace/augment expected_keywords with multi-point criteria per golden-dataset case (e.g. "states the match % AND the vesting period AND does not claim eligibility before 1 year").
3
Roll up per-request latency into a stage breakdown
The raw data already exists in logs (retrieval calls and generation calls are separately tagged) — this is an aggregation/reporting task, not new instrumentation.
4
Make a documented re-ranking decision, not a default-by-omission
Either evaluate a reranker against current retrieval precision/recall (now measurable via Phase 62's deterministic metrics), or write down explicitly why current retrieval is judged good enough to skip it.
5
Caching, tiered by personalization
Lowest urgency for a demo, but worth planning given personalization already exists: a global cache for non-personalized policy Q&A, separate from the per-employee MCP lookups that can never be cached the same way.
