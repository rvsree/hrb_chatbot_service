Gaps in the Course Sample's Own Implementation

Not "vs our project" — real issues in the notebook's own code, found by tracing its logic carefully

1

Stale results silently accumulate across turns

With the checkpointer enabled, agent_results/search_messages/planner_messages are all operator.add-reduced - but every new call still passes "agent_results": [] hoping to reset them. Under operator.add, adding [] is a no-op, not a clear - the previous turn's results never actually get purged, so the Synthesizer can merge in stale results from an earlier, unrelated question on a later turn.

TravelPlannerState, cells 62 & 99-101
2

Zero input safety

No prompt-injection check, no off-topic rejection, no PII handling anywhere - the router and both workers act on raw user text directly. Reasonable for a teaching notebook, but a real gap if any of this pattern gets reused for a real system.

no guardrail cell exists in the notebook
3

Router has no "neither" path

The classifier is only ever told about 2 named agents and must pick at least one - there's no graceful way to say "this question isn't about travel at all." A real off-topic question would still get force-routed somewhere.

classify_query_parallel()'s own system prompt
4

No error handling around the router's own LLM call

structured_llm.invoke(...) has no try/except - a rate limit, a malformed structured-output response, or a network blip crashes the whole graph with no fallback.

classify_query_parallel()
5

Unbounded synthesis prompt

results_formatted concatenates every worker's full output with no truncation or token budget - a couple of long worker responses and the synthesis call's prompt size is fully unbounded.

synthesizer_node()
6

Three different agent-construction styles, no stated reason

create_deep_agent() (a separate library) for one worker, create_agent() (LangChain's own prebuilt) for prototyping the other two, then fully hand-rolled node functions for the actual production graph - the notebook never explains why the prototyped agents weren't wired in directly instead of being reimplemented by hand.

cells 24, 41-44, 77-81

Critic Agent Dropped — What Reviewer Agent Absorbs

Your question, answered directly: these are two different things, and only one of them is free of conflict

Option A - evaluates each domain agent's raw result

No conflict, nothing built does this today

Reviewer Agent checks each domain agent's own output before using it - e.g. "did SQL DB Agent return usable rows, or an error/empty result?" This is a quality-filter over inputs to synthesis, a different target than anything this project's Gate 5 or Phase 62 evaluate. Your phrasing ("evals for the outputs coming from each domain agent") reads as this option.
Option B - evaluates the final synthesized answer

Same conflict as before, just renamed

Reviewer Agent runs a faithfulness/hallucination check on what the user actually receives. That is literally Gate 5's job (rag-validation-gates.html), which this project deliberately keeps offline, not live, specifically to avoid an extra LLM-judge call on every request. Moving it into Reviewer Agent doesn't resolve that tension, it just moves which file it lives in.

Not decided here - confirm which one (or both, with the cost of Option B understood) before this becomes part of a real spec.

Planned Implementation Steps

Corrected 2026-10-04 - the earlier 6-step version only covered the 3 agent stubs and silently skipped the surrounding pipeline. 8 steps now, in build order; each one either closes a Phase 61 NotImplementedError stub or wires in a piece this endpoint needs that isn't optional

1

Input Guardrails + load session history llm

Missing from the original plan entirely - flagged by direct question, not found by re-reading. Before the Planner sees anything: run check_input() (first agentic endpoint to call it - today only genai-rag does), and if enable_conversation_memory is set, load_history(). Neither step exists in the current stub.

2

Planner Agent - orchestrator_router.py::route_query() llm

One structured-classification LLM call, mirroring ClassificationResult (tasks + requires_synthesis), returning list[AgentTaskInfo] - the type Phase 61's response contract already reserves. Needs an explicit fallback route for an off-topic/unparseable classification - Travel Planner's own router has no such path (gap #3 above); don't repeat it here. Open question (see current-state.html footer): does this overlap with the separate, API-layer Query Decomposition step?

3

Orchestration Agent - fan-out via asyncio.gather()

No model call itself. One run_agent() call per task, same concurrency Travel Planner's Send() gets, no new dependency. Each call passes the task's own user_query and a tool_subset derived from task.source.

4

Domain agents - four thin files, not four tool-loops

One file per knowledgebase in ai/agents/domain_agents/ - vector_kb_agent.py, lms_ops_agent.py, sql_db_agent.py (no badge - no model call, deterministic wrappers) each just call run_agent() or its underlying client directly with a fixed scope - no new tool-calling loop, since Phase 55 already built and iteration-capped that once. lms_analytics_agent.py llm is the one file that's genuinely new logic - NL2SQL generation, one-shot for now not a loop (open), and depends on Phase 52's MCP server existing first.

5

Reviewer Agent - synthesizer.py::synthesize_results() llm

Port synthesizer_node()'s three-way branch directly: zero results → safe fallback message, no model call. One result → pass through unchanged, no model call. Two or more → one merge call formatting each worker's output against its task's focus. This logic has nothing LangGraph-specific in it - a plain function, matching this project's existing style.

6

Output Guardrails + save session turn llm

Also missing from the original plan. After the Reviewer Agent produces a final answer: run check_output(), then - only here, only once - save_turn(). This is the single-writer design from the State & Session diagram above, now stated as an actual build step instead of only shown in a diagram.

7

Wire into multi_agent_pipeline.py::run_multi_agent()

Replace the three NotImplementedError stubs (route_query(), dispatch_to_agents(), synthesize_results()) with steps 1-6 above, in sequence - the entry point and its contract (Phase 61) don't change.

8

Tests, then a real spec

Mirror Phase 55/58's existing fake-LLM-client test pattern - guardrails, memory load/save, router classification, dispatch fan-out, and the reviewer's three branches each independently testable with no real API key, plus one end-to-end contract test matching the existing route tests. Once Decision 1 and Decision 2 below are actually confirmed, this whole plan becomes Phase 61's follow-up **Spec:** block in RAG-ROADMAP.md, per spec_gate.py - not before.

What Decision 2 Opens Up - Not Decided, Flagged

Confirming "one agent per knowledgebase" surfaced three real items this plan didn't have before

1

Not all four agents need to be LLM agents

vector_kb_agent.py (wraps retriever.py), lms_ops_agent.py (wraps Phase 49's existing tools), and sql_db_agent.py (fixed queries) are plausibly deterministic function calls with no judgment to make - matching this project's own reliability stance (don't agent-ize a deterministic step). lms_analytics_agent.py is the one that genuinely needs an LLM - NL2SQL, translating a free-text trend question into a query, is an actual generation task. Worth deciding per-agent, not assuming all four need the same tool-calling-loop shape run_agent() already provides.

2

LMS Analytics Agent needs real historical data to demo against

100+ historical records, maps to Phase 52 (planned, not started - hrb_lms_analytics exists in the DB design doc, not built) and its own MCP server. Captured as its own item in docs/agent-reference/BACKLOG.md rather than assumed here - needs a schema decision (benefits-cost trends? leave patterns by type? both?) before data generation makes sense.

Gaps Not Yet Addressed

Checked against the live code, not assumed - timeouts, validation, persistence, logs, error handling, async, and whether this plan allows a worker to talk back to the Planner Agent

1

Timeouts - none exist anywhere in this path

Confirmed by direct search across ai/agents/, query_retrieval/, and rag_pipeline/tools/ - zero timeout/wait_for references. asyncio.gather() waits for every task by default; one hung domain agent blocks the whole request. Needs asyncio.wait_for() per domain-agent call, with a per-knowledgebase budget decided before this is built (Vector KB and SQL DB should be fast; LMS Analytics' NL2SQL path may legitimately need longer).

2

Validation - Planner Agent's fallback is required but not specified; LMS Analytics Agent needs a safety rail of its own

Step 1 above already requires a fallback route for an unparseable classification - no concrete mechanism chosen yet (Pydantic-validating tasks[].source against the real agent names is the direct fix). Separate, higher-stakes gap: if lms_analytics_agent.py executes LLM-generated SQL directly, that's a real injection risk even with no malicious user - a hallucinated query is enough. Needs a read-only DB role and/or a SELECT-only check before execution, not just a prompt instruction not to.

3

Persistence - who writes conversation memory, and when

conversation_memory.py is in-memory only today, unchanged by this plan. New question this plan introduces: should all 4 domain agents write to it, or only the Reviewer Agent once, after merging? Recommended: Reviewer Agent only, matching Phase 55's existing single-writer pattern (run_agent() calls save_turn() once, not per tool call) - avoids 4 concurrent writers racing on the same conversation_id. See the State & Session Management diagram below for exactly where each read/write happens.

4

Logs - no request correlation, and it's about to matter a lot more

Confirmed: zero request_id/correlation_id anywhere in this codebase. Already flagged in docs/agent-reference/BACKLOG.md's Observability section as a gap worth closing "once this app sees real concurrent traffic" - multi-agentic-rag is that traffic. Five parallel domain-agent log lines with no shared id are unattributable to one request. Should move from "nice to have" to a prerequisite for this phase.

5

Error handling - one failing agent shouldn't fail the whole request

asyncio.gather() defaults to propagating the first exception and cancelling the rest - one domain agent's failure takes down all four, even the three that succeeded, without return_exceptions=True and per-result handling. The Reviewer Agent's existing 0/1/2+ branch already tolerates a missing result almost for free - a timed-out or failed agent can feed into that same path instead of needing new logic.

6

Async/parallel - verified partly good, partly unverified

Checked, not assumed: postgres_client.py correctly wraps its sync driver (psycopg) in asyncio.to_thread() - genuinely non-blocking, SQL DB Agent is safe to build on it as-is. Not yet verified: whether every domain agent's full call chain (MCP client, vector store client) stays async all the way down. One accidentally-synchronous call inside any domain agent would stall the event loop for all four, silently defeating the whole point of asyncio.gather() - worth a direct check per agent before relying on it.

7

Feedback loop - not a hard limitation, just not built yet

The Planner→Orchestration→domain agents→Reviewer shape is a single-pass pipeline today - no domain-agent result currently flows back to the Planner Agent for re-planning. This is a design choice, not a constraint of nodes/edges (see the direct answer above) - and it's exactly what your original target-state image's "Reviewer Agent... critique + revise (max N)" already named as wanted, not yet built anywhere. If wanted, the cheapest version: the Reviewer Agent, after seeing results, can call the Planner Agent again with a bounded retry count instead of returning immediately - plain Python recursion/looping, no graph required.
