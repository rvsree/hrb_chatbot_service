Multi-Agent Orchestration

A plain-language tour of the orchestrator → parallel workers → synthesizer pattern taught in the IK FDE cohort's Multi-Agent Travel Planner class (LangGraph), followed by an honest status check against what hrb_chatbot_service has today. Status only — no ranking, no build/defer/drop recommendation made here.

source: docs/id-fde-cohort/multi-agentic-system/Multi-Agent Travel Planner.ipynb

The Workflow

One user question, split across specialist agents, run at the same time, merged into one answer

The Concepts, One at a Time

Same order the diagram reads in, explained plainly

01

Orchestrator / Router

One LLM call reads the question and decides which specialist(s) should handle it — by filling out a structured form (a validated object), not by writing free-text. Like a receptionist who fills in a routing slip instead of just describing the problem out loud.

classify_query_parallel()
02

Send() — Parallel Dispatch

Normally a graph runs one step, then the next. Send(node, state) lets one decision point start multiple nodes at the same time, each with its own copy of state — one manager splitting a request into two tickets handed out at once, not one after another.

dispatch_to_agents()
03

Worker Agent + Tool Loop

Each specialist is a small loop: ask the LLM → if it wants a tool, run the tool and feed the result back → ask again → repeat until it gives a real answer instead of a tool request. The same tool-calling loop this project already has in single-agentic-rag — just run twice here, once per worker.

search_agent_node() / planner_agent_node()
04

Sub-Agent as a Tool

One whole agent can be wrapped up and handed to another agent as if it were an ordinary function. The Planner doesn't know itinerary_research_agent is secretly a full reasoning agent underneath — calling it looks exactly like calling a search function.

@tool("itinerary_research_agent")
05

Synthesizer (fan-in)

If only one worker answered, its raw answer becomes the final answer — no extra step. If more than one answered, this makes one more LLM call whose only job is to organize what's already been found into one readable response. It does no new research.

synthesizer_node()
06

Concurrent-Safe State (reducers)

Two workers can try to update the same shared state at almost the same moment. Marking a field Annotated[List, operator.add] tells the graph "combine both writes into one list" instead of letting one silently overwrite the other.

agent_results: Annotated[List[dict], operator.add]
07

Persistence / Checkpointing

The graph can remember a conversation across separate calls, as long as the same thread_id is passed each time and the graph is compiled with a checkpointer. Same goal as this project's own hand-built conversation memory — a first-party library feature here instead of a custom dict.

InMemorySaver() + config["thread_id"]

Status Check Against hrb_chatbot_service

What the course pattern needs vs. what already exists here today — status only

Built Partially built / built differently Not built
ConceptStatusWhere this actually stands
Tool-calling agent loop (ReAct) Built The exact loop mechanism already exists and runs live: ai/agents/workflow_agents/orchestration_agent.py :: run_agent(). The course just runs two independent copies of this same idea, one per worker.
LLM-based structured-output router Not built Nothing plays this role today. Phase 49's MCP routing (is_leave_balance_query()) is plain keyword matching, not an LLM call, and single-agentic-rag has no separate routing step at all — the one agent decides everything itself, in its own loop.
Parallel multi-agent dispatch (Send API) Not built Single-agentic-rag always runs exactly one reasoning loop per request — nothing runs concurrently. Worth knowing: langgraph==0.3.21 is already pinned in requirements.txt (pulled in by langchain's own dependency tree) but isn't imported anywhere in src/ today — the library is already present, not a new install, if this path is ever chosen.
Sub-agent-as-a-tool composition Not built None of single-agentic-rag's 3 tools (SearchKnowledgeBase, GetLeaveBalance, GetLeaveHistory) are themselves agents — all three are single-purpose leaf functions.
Synthesizer / fan-in merge step Not built No merge step exists because only one agent ever runs per request today — there is nothing yet to merge.
Concurrent-safe state merging Not built No concept of merging concurrent writes exists, since nothing runs in parallel yet to write concurrently.
Multi-turn conversation persistence Built differently The capability exists — ai/pre_processing/conversation_memory.py (Phase 58), a hand-built in-memory store keyed by conversation_id, verified live on both genai-rag and single-agentic-rag. Same goal as the course's InMemorySaver/thread_id, different (custom, not library) mechanism.

Deep-research sub-agent framework (deepagents) Not built deepagents is not a dependency of this project at all — the course uses it for one worker's open-ended research loop.
