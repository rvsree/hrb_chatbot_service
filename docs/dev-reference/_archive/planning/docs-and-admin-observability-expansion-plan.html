Docs & Admin Observability Expansion

Four asks from one message, turned into a scoped, sequenced plan: a real-feature doc pilot, a DB schema that keeps real version history, an admin CI/CD + eval-score view, and two new interview-focused doc categories. Every fact checked directly against real code before being written here.

all open decisions resolved

Resolving the admin-login question

These documents already only work for the admin role - that's enforced in two places, not one: DocLink on the frontend renders nothing unless identity.role === "admin", and the backend's GET /v1/admin/docs independently enforces require_role(..., Role.ADMIN) before returning anything. The actual file comes back as a short-lived (300s) presigned S3 URL, never a public link.

The claude.ai links shared for review last round are a separate, temporary convenience - private-by-default, never gated by the app's own auth. Decision: kept as a standing convenience alongside the real in-app viewer.

3. DB redesign - real version history

Today's doc_metadata overwrites a row in place when content changes - no way to see an older version from the DB. Proposed split:

doc_catalog (stable identity) doc_versions (append-only history) id, scope, feature_name, id, catalog_id (FK), doc_type, doc_title, version_number, s3_bucket, s3_key, current_version_id (FK) --------> source_local_path, content_hash, created_at

A content change INSERTs a new doc_versions row and repoints current_version_id - old versions stay queryable. Same idempotent migration convention already used for the (feature_name, doc_type) unique-index change.

Decided: Phase 181, after the RAG Ingestion pilot ships on today's schema.

6. Admin CI/CD + eval-score view

Real gap found: scripts/run_release_gate.py only prints to CI logs and exits with a code today - nothing about a release-gate run is persisted anywhere. This has to be built, not just surfaced.

6.1 golden_dataset_items - versioned, categorized

Grounded in the real 26-case shape already in golden_dataset.json (category, query, expected_source_document, expected_answer, expected_keywords, call_type) plus a new feature_name column your "organized by which feature" ask requires, version_number + is_latest for the same append-only versioning as the docs table. A new sync_golden_dataset.py upserts from the JSON (kept as the human-reviewable source) into this table. golden_dataset_harness.py reads WHERE is_latest = true instead of the file directly - the same source serves the admin grid and CI.

6.2 eval_runs / eval_run_results - held

Persists each release-gate run (scores, pass/fail, which golden-dataset version it graded against) so the admin UI has real history to show.

Decided: held until Phase 174 ships DeepEval. Every score the admin view ever shows will be a real DeepEval number, never a hand-written-harness one needing a later relabel. raw_response will be stored in full for real per-case debugging once this starts. Section 6.1 is not blocked by this - it proceeds now as Phase 182.

Ideas beyond what was asked

  • is_latest as a real column, not a derived query - cheap now, annoying to retrofit.
  • eval_runs.golden_dataset_version as a real FK, not just a number.
  • JSON stays the authored source for golden-dataset cases, DB the served copy - edits stay reviewable in a PR.
  • Doc-version history browsing (diff version N vs. N-1) not built yet - schema supports it, UI is real scope on its own, flagged as a natural follow-up.
  • Cross-link relentlessly instead of repeating content between the new deployment doc, the scaling doc, and interview-faq-system.
