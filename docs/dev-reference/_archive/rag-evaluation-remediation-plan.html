RAG Evaluation Remediation Plan

How to close the 6 confirmed gaps between this project's evaluation code and the course's own 5_evaluation/demo.py reference implementation — scoped to the retrieval evaluation pipeline for POST /v1/genai-rag/retrieve-document/query.

Scope: evaluation only Live endpoint impact: none Spec status: not yet written to RAG-ROADMAP.md Code changed so far: zero

Current State — is the retrieval endpoint actually being evaluated?

Yes — the golden-dataset harness is not a separate thing from the retrieval endpoint. It calls the exact same pipeline.py function the live endpoint calls, just offline and manually, with 23 known questions instead of live HTTP traffic. That's the whole reason golden-dataset language shows up when you ask about retrieval endpoint evaluation — it is the retrieval endpoint's evaluation.

The 6 confirmed gaps, mapped to this plan

Two of the six are agentic-loop concerns, not retrieval-evaluation concerns — called out as out of scope for this specific plan rather than silently dropped.

#GapIn scope here?
1Retrieval Precision/Recall/F1 are LLM-judged, not exact expected_source_document ID matching like the coursein scope
2"Completeness" is mapped to AnswerRelevancyMetric — a different concept than the course's reference-coverage checkin scope
3No failure-pattern diagnostics (the course's 4 named root-cause patterns)in scope
4No real A/B testing harness — only a labeled placeholder predating Phase 8in scope
5No keyword/hybrid retrieval (vector-only, despite course calling hybrid the production default)separate phase — a retrieval-architecture change, not an evaluation-harness fix; would need its own spec
6No "Decision: rationale" trace before agent tool callsout of scope — belongs to orchestration_agent.py, the agentic loop, not retrieval evaluation

Gap-by-gap remediation

GapFixWhereSize
#1 — retrieval metrics Add a deterministic scorer: compare response.retrieval_info.sources[].document_id against each case's expected_source_document, compute Precision/Recall/F1 exactly like the course's calculate_retrieval_metrics(). Report it alongside the existing DeepEval contextual metrics, not instead of — the two catch different failure modes (exact source vs. paraphrase-level relevance). golden_dataset_harness.py — new function Small
#2 — completeness Replace AnswerRelevancyMetric for the "completeness" slot with a metric that actually checks fact coverage against expected_answer / expected_keywords — DeepEval's GEval with a custom rubric mirroring the course's evaluate_completeness() prompt is the direct match. golden_dataset_harness.py — build_metrics() Small
#3 — failure patterns Port the course's 4 named patterns (A: high-precision/low-recall, B: low-precision/high-recall, C: strong-retrieval/weak-generation, D: low-groundedness) into a new function that runs against the aggregated scores whenever the gate isn't PASS. golden_dataset_harness.py — new diagnose_failure_patterns() Small
#4 — A/B harness Real config comparison — k=3 vs k=5, similarity vs MMR, chunk size — reusing the same scoring functions from #1/#2 so a config change is measured on the same metrics as a release gate, not a separate toy metric. Open decisions — need your call before this becomes a real spec

Per this project's own SDD process, none of this can be implemented until a **Spec:** block exists in RAG-ROADMAP.md and you've reviewed it — the spec_gate.py hook enforces that literally. These are the calls only you can make first.

Keep both retrieval scoring methods, or replace DeepEval's contextual metrics with the deterministic one?
Keeping both is more evaluation coverage but two numbers to explain in an interview or a report. Replacing matches the course exactly but drops the paraphrase-sensitivity DeepEval's LLM-judge gives you.
Should this offline harness get wired into CI as an automatic gate, or stay manual (pytest -m eval)?
Manual matches the course. CI-gated is a real step beyond the course, and directly closes the "is this a CI gate or manual" open item already sitting in the EY interview prep document.
Does gap #5 (keyword/hybrid retrieval) become its own future phase?
It's a retrieval-architecture change, not an evaluation fix — bundling it here would break "one task at a time." Flagging it now so it doesn't quietly disappear.
What this document is not: it is not an implementation, not a merged spec, and no source file under src/ has been touched to produce it. It exists so you can approve, redirect, or reject the plan before any code gets written — matching the spec-first rule this whole conversation started from.
