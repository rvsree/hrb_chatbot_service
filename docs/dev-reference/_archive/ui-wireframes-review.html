UI Wireframes — for review, not yet implemented

Published 2026-10-06 as a visual wireframe set (5 screens) for sign-off before any React build starts. Captures the feature list as the user described it directly — a standard chatbot UI plus feedback, conversation history, an explainability popup, batch document upload, and OAuth/JWT login.

Do not implement from this without explicit sign-off. This page and the linked wireframes are a design artifact only - no React code exists yet. See 07-reactjs-ui.html for the build-plan/architecture side (monorepo decision, Angular/ASP.NET → React concept mapping) once the wireframes themselves are approved.

The 5 screens

#ScreenWhat it captures
1LoginOAuth 2.0/OIDC sign-in (Google Workspace / Microsoft Entra ID shown as examples), with a plain-language note on how the JWT flow would work - this is a wireframe of a feature that doesn't exist yet (see "Open gaps" below, human-to-app OAuth is still design-only).
2Chat (main screen)Conversation history sidebar, user info footer, a real 401(k)-match example thread with inline citations, per-message "Helpful"/"Not quite" feedback buttons, an "Explainability" link per message, and a top-bar link to document upload.
3Feedback popupOpened from a message's "Not quite" button - reason tags, optional free-text, explicit note that feedback is attributed (not anonymous).
4Explainability popupOpened from a message's "Explainability" link - cost, token counts, latency, a numbered call trace (retrieval → embedding → generation, each with real timing), citations with real relevance scores, and guardrail pass/fail status.
5Document upload (batch)Drag-and-drop multi-file PDF upload, optional batch-level metadata override, a per-file queue showing upload/indexing progress and a real rejected-file case (wrong file type).

Direct mapping to real backend contracts

Every number and field shown is traceable to something this project's backend already returns for real, not invented:

  • The chat thread's citations (filename, chunk index) match retrieval_info.sources from POST /hrb-chatbot/v1/genai-rag/retrieve-document/query's real response shape.
  • The explainability popup's cost/token/latency numbers match the shape common/logging/call_logger.py's log_backend_call() already logs per call (model, duration, token counts) - today this is in server logs only, not surfaced to any API response; a real UI would need a new endpoint or response field to carry it, not just a frontend change (see "Open gaps" below).
  • The upload page's per-file states (uploading/indexed/rejected) match DocumentUploadResult.status ("uploaded"/"duplicate"/"rejected") from the real upload endpoint, and the batch-metadata fields match ChunkInfoInput/DocumentMetadataInput.

Open gaps this surfaced - real, not cosmetic

GapWhy it matters for this UI
No real human-to-app OAuth/JWT exists yetapi/gateway/rbac.py's require_role() still reads a self-asserted, unsigned user_profile straight from the request body - a deliberate placeholder (common/clients/auth_client/oauth_client.py is empty). The login screen wireframes the intended flow, not something that exists today - a real login page needs this built first or alongside.
No API surfaces cost/token/tool-call data todayIt's logged, not returned. The explainability popup needs either a new response field on the query endpoints or a new "trace" endpoint keyed by request/conversation id.
Rate limiting is IP-keyed, not identity-keyedOnce real auth exists, this should probably switch to limiting by the authenticated identity, not the caller's IP - flagged in BACKLOG.md, unrelated to this UI work specifically but adjacent.

What was deliberately left out of this round

  • No settings/admin page, no role-switcher, no dark mode - kept to exactly the features named.
  • Single/multi-agentic-rag mode switching isn't shown - the wireframe assumes one chat surface; whether a user ever explicitly picks a "mode" (vs. the backend deciding) is an open product question, not decided here.
  • Mobile/responsive layout not wireframed separately - noted as a build-time requirement, not a separate screen.
