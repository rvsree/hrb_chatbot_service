401(k) Loan Agent — A2A Protocol Design

What it would actually take to let an employee request a 401(k) plan loan through a real Agent-to-Agent (A2A) exchange with a separate "Empower Retirement" agent — grounded in this project's own real plan-loan policy text, the real IK FDE course material on Google ADK + A2A, and the architecture reasoning already recorded in two prior design docs.

00

Summary, up front

Three things this doc answers directly, since they were the actual questions asked:

  • Is this a different project? Yes. Not a style preference — the real A2A wire protocol (Agent Cards, JSON-RPC, a server listening on its own port) only makes sense between separate, independently-deployed services. Nothing in hrb_chatbot_service today is deployed separately from the rest of itself. See §01.
  • Should it use Google ADK? Yes — and this is the first real case where that's actually justified in this project's own history (see the callout in §01). A new, standalone service has no existing agent framework to collide with.
  • Should it follow the IK FDE course material? Yes, directly — github.com/jeev1992/real-estate-negotiation-simulator's m2_adk_multiagents module, re-fetched live via the GitHub API for this doc (not from memory). §03 maps its demos/exercises onto this use case's own design decisions, concept by concept.
01

Why this is a different project, not a new phase

Two decisions already on record in this project — found while researching what "A2A" meant here before writing this doc — both point the same direction.

Decision 1 — the carve-out that applies here

"If a future phase genuinely needs to call a separate, independently-deployed agent service — not a hypothetical today — adopting the real A2A SDK then is the right call, reviewed on its own, not folded into this schema work." — docs/dev-reference/genai-chat-workflow-memory-design.html §04

That doc rejected Google ADK/real A2A for the existing features, because every agent in multi_agent_pipeline.py runs in-process inside one StateGraph.ainvoke() call — no network boundary to protocol over. A 401(k) Loan Agent representing Empower Retirement is exactly the "future phase" that carve-out described: a real, external, separately-administered system (the plan's own KB document names Empower by name — §02 below), not a role this codebase can simulate in-process.

Decision 2 — the one this does not contradict

"Scope decided: deeper internal multi-agent collaboration, not Google's Agent2Agent protocol. Cheaper path — no new wire protocol, just evolving what multi_agent_pipeline.py already does." — docs/dev-reference/planning/upcoming-features-scoping-notes.md, item 4 "A2A communications"

That's a separate, still-open idea about the Planner/domain-agents/Reviewer graph talking to itself more richly — internal collaboration, explicitly not real A2A. This doc doesn't touch that item; a 401(k) loan request never goes through multi_agent_pipeline.py's own internal agents at all — it goes out, to a different organization's system.

Why Google ADK is the right call here, specifically

This is the first scenario in this project's history where ADK doesn't duplicate an existing framework. The Loan Agent is a brand-new service with nothing already built in LangGraph to collide with — ADK's own adk web --a2a is literally how the course module itself stands up an A2A server, so using it here is the direct, intended path, not a workaround.

What "different project" means concretely

  • A new, separately-deployed Python service — its own directory tree (new repo, or at minimum a new top-level folder deployed independently — see §09, open decision), not a module under src/hrb_chatbot/.
  • A new dependency entirely: google-adk — not reviewed or approved for this project before now, per this project's own "no unreviewed libraries without explicit approval" rule. This doc is that review.
  • A new deployable: its own container, its own port, its own health check, its own entry in whatever CI/CD this gets (see §09).
  • hrb_chatbot_service's own change is comparatively small: one new A2A client call-site, most naturally a new tool/domain-agent in multi_agentic_rag (parallel to how MCP tools are wired today) — not a rewrite of anything existing.

The Loan Agent is deployed on its own — own port, own Agent Card, own process. hrb_chatbot_service holds no loan-eligibility logic itself; it only knows how to discover and call the Agent Card's advertised skills, same separation of concerns the course's buyer/seller agents demonstrate.

06

Three-tier governance (Exercise 6 + Exercise 1 patterns)

Every threshold below comes straight from §02's real plan terms, not invented.

Auto-approve

Amount between $1,000 and $50,000/50%-vested, no existing outstanding loan, no hardship flag. The Loan Agent (an ADK LlmAgent) processes and completes the Task on its own.

Human checkpoint

Request sits near the maximum threshold, is flagged as hardship-related, or the employee is near termination. Routes to a human plan specialist — same HITL mechanism Phase 172 already built for leave approval, not a new one.

Hard block

Amount exceeds $50,000/50%-vested, or below the $1,000 minimum, or an existing unresolved default. Enforced in a deterministic before_tool_callback, exactly Exercise 1's pattern — the LLM is never in a position to override it, regardless of how it reasons about the request.

07

Polling vs. streaming vs. push — a real departure from the course demo

The course's buyer/seller negotiation completes in seconds, so Demo 13's choice (buyer polls, seller streams) is really about UX during one live conversation. A 401(k) loan is explicitly a 5–7 business day process (§02) — the employee will not keep a connection open that long, so neither polling nor message/stream fits as the primary mechanism.

Design decision, not yet confirmed

The Agent Card should advertise pushNotifications: true: the client registers a webhook via tasks/pushNotificationConfig/set once the Task enters working, and the Loan Agent calls it back when the state changes — days later, asynchronously — rather than the employee's session polling for a week. hrb_chatbot_service would then need its own durable notification/inbox delivery (something like email, or a dashboard "My loan requests" view) — this is new surface, not reused from anywhere existing.
