GCW-1One combined request, not attach-then-ask
Context
Files and the question could have been two separate calls - upload, get a handle back, then ask.
Decision
One multipart request carries files and the question together.
Why
No server-side temporary storage needed between steps - nothing to leak if a user never follows up, nothing to clean up on a timeout. The simplest shape that could work.
GCW-2DOCX via stdlib zipfile+ElementTree, not python-docx
Context
A real library (python-docx) would read Word files more completely - tables, formatting, headers.
Decision
Extract paragraph text directly from word/document.xml using only the stdlib (zipfile + ElementTree).
Trade-off
Cruder extraction - no tables, no formatting - accepted in exchange for zero new dependency, consistent with this project's "no unreviewed libraries without approval" standard. Flagged as a real future upgrade, not solved here.
GCW-3Open to all 4 roles, not just HR_SUPPORT
Context
Document upload (the main RAG ingestion path) is HR_SUPPORT-only - it writes to shared KB state.
Decision
require_role(EMPLOYEE, MANAGER, HR_SUPPORT, ADMIN) - every role can use this workflow.
Why
This is a personal, ephemeral tool - nothing it does touches shared state the way indexing a document does, so the stricter gate upload-documents needs doesn't apply here.
GCW-4Reuse existing guardrails on file content
Context
Guardrails already screened typed questions; file content was initially exempt - the same gap this project's own document-upload guardrails work had already flagged once.
Decision
Every extracted file's text runs through check_input() independently, same as a typed question.
Why
File content reaches the LLM exactly like typed text does - there's no reason an attacker-controlled PDF should bypass a check a typed message can't.
GCW-5Email recipient is informational, not a directive
Context
Two prior attempts at wiring recipient_email into the agent's prompt both failed, confirmed live. Attempt 1 (unconditional "please email this") leaked into unrelated turns - a user asking "did you send the email?" got an email sent in response, because the instruction was appended to every message regardless of intent. Attempt 2 (a conditional directive re-stating "only if this message asks") overcorrected: 2 of 3 genuine "email it to me" requests silently didn't send, likely because the double conditional (the system prompt's own instruction plus this one re-explaining the same condition) confused the model rather than clarifying it.
Decision
The recipient email is folded into the question purely as reference information ("the user's email address is X, if needed") - no directive at all. The system prompt's own existing instruction ("only call this if the user explicitly asked") is trusted to be the one place that governs the decision.
Why
Removing the second, redundant conditional fixed both failure modes at once - confirmed live, not assumed.
GCW-6Two independent email paths, not one unified path
Context
A checkbox in the UI ("send email on answer") was added later, alongside the agent's own pre-existing in-text email decision.
Decision
The checkbox-driven path is separate code in the route itself, deliberately not merged into the agent's own SendEmailWithAnswer tool-call logic. Both can legitimately fire in the same turn - accepted as a known edge case, not prevented.
Why
Keeps the single-turn "summarize this and email it to me" case working through the agent's own reasoning, regardless of whether the checkbox path exists at all - the two paths don't need to know about each other to both work correctly.
GCW-7System-note suffix for stored history
Context
Session memory originally stored only the plain answer text - so a later turn's "did you send it?" had no way to know an earlier turn's email actually succeeded, and the model answered "I have not sent any email yet" even when it had. This was the exact bug from the original production report, reintroduced by memory itself rather than fixed by it - caught live before shipping.
Decision
The stored (never user-facing) version of each turn's answer gets a [System note: ...] suffix recording the real outcome of any email attempt that turn. GET /sessions/{id} strips this suffix before returning turns to the UI.
Why
A future turn's chat_history now actually knows what happened, not just what was said - without ever surfacing internal bookkeeping text to a person.
