A Dedicated Auth Server Project

One small, standalone service whose entire job is identity and access - separate from hrb_chatbot_service and hrb_lms_mcp so it can be extended and experimented on without touching either of them.

hrb_auth_server (recommended)matches the existing hrb_chatbot_service / hrb_lms_mcp naming, says exactly what it does
hrb_security_labframes it explicitly as the learning sandbox it's really for
hrb_identity_hubemphasizes "one identity source for everything," if that framing lands better
Objective Give hrb_chatbot_service and hrb_lms_mcp real, simulated security (not a token gesture) with almost no added complexity in either project - and give this project a dedicated place to build the security depth that's been thin in interviews, one real feature at a time.

03
What to add next, to actually build the skilleach one is a real, common interview topic - plain-language version of what it does and why it's asked about
1

Refresh tokens

Today a token just expires and you start over. Real systems hand out a short-lived "access token" (minutes) plus a longer-lived "refresh token" (days) - so a user isn't re-typing a password every 30 minutes, but a stolen access token still dies fast."how do you handle token expiry without annoying users"

2

Token revocation

A JWT is normally impossible to "cancel" before it expires - it's just a self-contained signed piece of paper. Real systems keep a small denylist ("these token IDs are dead now") for the one case that matters: someone's laptop got stolen."JWTs are stateless - how do you log someone out immediately"

3

Scopes, not just roles

Today it's "you're an employee, you can query" - all-or-nothing per role. Scopes let a token say "this one can only read leave balance, nothing else" - the same idea already used for the app-to-app side (mcp:get_leave_balance), extended to humans too.RBAC vs. scope-based access control

4

Asymmetric signing (a key pair, not a shared secret)

Today, anything that can check a token could also forge one (same secret does both jobs). The fix: the Auth Server keeps a private key, everyone else only ever gets the public key - they can verify, but never forge.HS256 vs. RS256, why it matters at scale

5

Audit logging

Who logged in, when, from where, which token did what. Not fancy - just a table that gets written to on every login/token issuance. The first thing any real security team asks for after an incident."how would you investigate a suspected breach"

6

Login rate limiting / lockout

Stop someone from trying a million passwords against one account. A simple counter (N failed attempts -> locked for M minutes) demonstrates the concept without needing a real fraud-detection system.brute-force protection

7

Secrets out of .env

Today the JWT signing key lives in a plaintext .env file. A real deployment keeps it in something like AWS Secrets Manager and fetches it at startup - ties directly back to the IAM conversation: the Auth Server's own AWS role would be what's allowed to read that secret.secrets management, why .env doesn't scale to production

8

MFA, simulated

Even a fake "enter this 6-digit code" step (no real SMS/email needed) teaches the actual pattern - a second, independent factor beyond the password."why isn't a password alone enough"
