OAuth2 Authentication Architecture

Who's calling this project's endpoints, and who this project calls in turn. Human-to-app (a person logging into hrb_chatbot_service) is still a design, unchanged since the original feasibility pass. App-to-app (hrb_chatbot_service calling hrb_lms_mcp as itself) went from a dead, unenforced API key to a real, live-verified OAuth2 client-credentials flow in the same session.

Deliberate simplification: client secrets are SHA-256, not bcrypt/passlib. A machine-generated high-entropy secret doesn't carry the brute-force-by-guessing risk a human password does, so slow password-grade hashing wasn't worth a second repo taking on a new dependency for. Scope enforcement (checking the JWT's scopes claim against which tool is being called) is also not built yet - this phase is authentication only, not authorization.

Today Every request carries an unsigned user_profile JSON object, read as-is by resolve_user_from_profile() - trivially spoofable, a deliberate placeholder (Phase 45), not a real control.
Proposed POST /oauth/token (password grant) checks credentials against real rows in hrb_chatbot_service_core.employee_roles (already real, live, populated - see docs/dev-reference/db-model-overview.html), issues a JWT; routes verify the signature instead of trusting the payload.

Why this stayed on paper while app-to-app got built: app-to-app was the immediate, concrete need (a real MCP integration that had to actually work). Human-to-app touches this project's own request/response contract on every endpoint - a bigger, more disruptive change, deliberately sequenced after.
