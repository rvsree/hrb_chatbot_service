Production Troubleshooting FAQ

Every entry below is a real incident from this project's own history, documented in RAG-ROADMAP.md/BACKLOG.md/AWS-DEVOPS-RUNBOOK.md - symptom, root cause, the actual fix, and how to catch it faster next time. Used as worked examples, not a generic ops checklist.

Docker image builds but App Runner won't run it
CREATE_FAILED, image "pulled successfully," zero application logs anywhere
cause

BuildKit's default docker build wraps the real image in an OCI image index plus a provenance/SBOM attestation manifest - App Runner pulls it "successfully" and then never actually runs the real layer underneath.

fix

Build with docker buildx build --provenance=false --sbom=false --output type=image,...,oci-mediatypes=false,push=true - never a bare docker build -t ... ..

avoid next time

Before pushing, run docker manifest inspect <image> and confirm mediaType: "application/vnd.docker.distribution.manifest.v2+json" - catches this before App Runner ever sees it.

Same CREATE_FAILED symptom, different real cause - a hand-typed secret ARN
cause

AWS Secrets Manager appends a random suffix to every secret's ARN (e.g. hrb-chatbot/OPENAI_API_KEY-LdC1Q6) - a hand-typed ARN without that suffix looks plausible but is wrong.

fix

Always resolve the real ARN via aws secretsmanager list-secrets at deploy time, never type one from memory.

avoid next time

The exact same generic symptom (image pulled, zero app logs) had two unrelated root causes - don't assume the first fix found is the only one; check both independently.

Container never starts at all, and CloudWatch has no app-level log group to even check
cause

When the container fails before the app's own logging ever initializes, only the generic App Runner /service log group exists - no separate application log group is ever created.

fix

Treat "zero app-level logs + generic pull/deploy failure message" as a signal to check the image itself (manifest format, architecture) before debugging application code that never even ran.

avoid next time

Confirmed the hard way this session while building the developer-onboarding guide - worth remembering as a pattern, not just a one-off.

A sibling MCP service that looks down but isn't
Leave-balance questions silently fall back to a generic "connection issue" answer
cause

Two independent causes found in sequence: first, HRB_LMS_MCP_URL was simply never configured in production App Runner, so the container tried to reach 127.0.0.1:8190 on itself. After fixing that, a second bug surfaced - hrb_lms_mcp's own server defaulted to DNS-rebinding Host-header protection, rejecting every real (non-localhost) hostname with a 421.

fix

Deploy hrb_lms_mcp to its own real App Runner service with the real URL/OAuth2 credentials wired in; add exc_info=True to the generic exception logging that had been masking the 421 as an unhelpful ExceptionGroup.

avoid next time

A graceful "MCP unreachable" fallback (correct behavior) can also hide a config bug that should be loud, not quiet - log the specific failure type even when the user-facing fallback stays smooth.

RAG-ROADMAP.md Phase 118
"It works on my machine" - config pointing at the wrong place
Admin docs sync reports "updated" every run, but the live site never shows the new content
cause

POSTGRES_DB_HOST=localhost in .env pointed at a genuinely separate local Postgres process, not a tunnel to the shared production database - every sync run wrote to the wrong database entirely.

fix

Confirmed via netstat/tasklist that local Postgres was a real, separate process; temporarily pointed .env at the real Neon connection string, ran the sync, reverted .env byte-for-byte afterward.

avoid next time

A script reporting success tells you it ran, not that it ran against the right target - verify the actual destination, not just the exit code.

Frontend calls fail with connection errors even though the backend is clearly running
cause

hrb_chatbot_ui/.env's VITE_API_BASE_URL pointed at port 8299; the real backend was running on 8093.

fix

Matched the port in .env to the real running uvicorn process.

avoid next time

When a frontend/backend pair reports a generic connection failure, check the configured port against the actually-running process's port before assuming the server itself is broken.

Frontend state bugs that look like backend bugs
Admin dashboard shows (0) on every single tab, even ones with real data
cause

Promise.all([...5 fetches...]) fails fast - one rejected promise (e.g. leave requests when the MCP server is down) discards the results of every other already-successful fetch too, not just the failing one.

fix

Switched to Promise.allSettled, applying setState() only for each individually-fulfilled result, with a per-fetch failure message instead of one blanket error.

avoid next time

Any dashboard combining multiple independent data sources in one Promise.all has this exact failure mode waiting - prefer allSettled by default whenever the sources are allowed to fail independently.

Local tooling getting in its own way
A deck-building script silently writes to a "_wip" copy instead of the real file
cause

The canonical .pptx was open in PowerPoint at the time - python-pptx can't write to a file locked by another process, so the save script's own fallback kicked in.

fix

Close the file in PowerPoint, then simply re-run the same build script - it adds the new slides cleanly since the canonical file was never actually touched.

avoid next time

A script that silently falls back to a different output path on a lock conflict is doing the right defensive thing - but always check for a stale lock file (~$filename on Windows) before assuming a build script failed outright.
