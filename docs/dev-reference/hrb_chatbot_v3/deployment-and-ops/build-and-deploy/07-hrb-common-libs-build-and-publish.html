Build and Publish — hrb-common-libs

The one repo in this system that isn't a running service. A shared connector library, consumed by all 5 Python backends via a git-tag-pinned requirements.txt line - not Docker, not App Runner, and deliberately not ~10 separate PyPI packages.

1What it actually is

One repo, pip extras instead of separate packageshrb-common-libs[llm], [vectordb], [metadata] etc. - a consumer installs only the extras it needs, but there's one version number and one git history, not ten packages to keep in sync

2Build and release process

1. Change lands on a feature branch, PR'd to mainSame repo as the Base*Client ABCs/*Gateway classes documented in hrb_chatbot_service's own CLAUDE.md
↓
2. pytest runs in CI on every PRNo Docker build - this repo produces a Python package, not a container
↓
3. A real version bump gets a git tage.g. v1.4.0 - this tag is the actual release artifact
↓
4. Consumer's requirements.txt pins that taghrb-common-libs[llm,vectordb] @ git+https://github.com/rvsree/hrb-common-libs.git@v1.4.0 - this is why every other service's Dockerfile builder stage needs git installed
↓
5. pip install clones that exact tag during each service's own Docker buildNo separate publish step, no private PyPI index to run - the git tag itself is the distribution mechanism

4Why a tag pin, not a floating branch

ApproachWhy not used here
Pin to main branchA new commit to hrb-common-libs would silently change what every consumer builds on its next Docker build - no coordinated rollout, no way to roll back one service without affecting the rest
Separate PyPI packages per extraTen packages means ten version numbers to keep compatible with each other - rejected for the same reason the gateway/enum pattern exists elsewhere in this system: one source of truth beats several that can drift
Pin to an exact git tag (actual choice)Every consumer's build is reproducible and explicit about which version it's on; bumping is a one-line requirements.txt change per service, done deliberately
