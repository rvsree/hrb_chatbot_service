Build Process — rag_ingestion_service

The only service in this system with TWO real, independently deployed build artifacts from the same source code: a container image (Dockerfile) for the sync admin-triggered path, and a separate Lambda package (Dockerfile.lambda) for the async S3-triggered path.

1Sync path - container image Dockerfile - same 2-stage shape as hrb_api_gateway_service's own

builder stageapt-get git (for the hrb-common-libs pin) → pip install -r requirements.txt into /opt/venv
↓
runtime stagenon-root user hrbingest (uid 10001) → COPY --from=builder /opt/venv → COPY src ./src → EXPOSE 8300
↓
CMD uvicorn rag_ingestion.main:app --app-dir srcbare from rag_ingestion... import convention, same as the Gateway's own

2Async path - Lambda package Dockerfile.lambda - a different base image, different runtime shape entirely

AWS Lambda Python base imagednf install git (not apt-get - this base is RPM-based, not Debian) - a real bug found live: the base image has no git by default, needed for the same hrb-common-libs pin
↓
pip install -r requirements.txt into the Lambda task rootNo spacy/presidio model download here - this repo's own pipeline never imports guardrails code (that stayed retrieval-side)
↓
CMD lambda_handler.lambda_handlerReads one SQS batch (each message wraps an S3 ObjectCreated event), downloads to /tmp, calls the same pipeline.index_document() the sync path uses, reports per-message failures via batchItemFailures
⚠
Second real bug found live: indexing.py's LlamaIndex call fell back to its own default embed-model resolution, which reads OPENAI_API_KEY straight from os.environ - bypassing this service's own Secrets-Manager-only convention entirely. Worked by accident in hrb_chatbot_service's own container (where that var genuinely is a plain env var) but not here. Fixed by constructing the embedding client explicitly with read_secret().

3Real CI/CD two independent workflows, one repo

deploy.yml - the sync container pathSame 7-step ECR/App Runner pipeline every containerized service uses
deploy-lambda.yml - the async pathBuilds Dockerfile.lambda, pushes to its own ECR repo, updates the Lambda function's image - a genuinely separate pipeline, not a variant of the same one
