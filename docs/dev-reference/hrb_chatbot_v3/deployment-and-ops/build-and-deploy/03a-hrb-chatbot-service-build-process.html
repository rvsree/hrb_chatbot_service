Build Process — hrb_chatbot_service

Third in the sequence - the pre-split monolith, still the real production retrieval backend behind the Gateway. The most complex Dockerfile of the 6: a real ML model download and a real file-permissions fix, both found the hard way in production.

1Docker image - 2-stage build python:3.12-slim exactly - chromadb depends on Pydantic v1 internals Python 3.13 removed

stage 1 — builder
pip install -r requirements.txt into /opt/venvStandard dependency install, cached as its own Docker layer
↓
python -m spacy download en_core_web_lgPresidio's analyzer needs this model for the "mask sensitive data" guardrail. Missing once in production (Phase 82) - "every query was blocked" until this line existed. The exact same bug reappeared in rag_retrieval_service's own port, found and fixed live this session.
stage 2 — runtime
↓
FROM python:3.12-slim AS runtime, non-root user hrbchatFresh base, no build tooling carried over
↓
mkdir data && chown hrbchat:hrbchat dataChromaDB's persistent store, the SQLite metadata file, and uploaded PDFs all write under data/ - without this line the app fails at startup with a confusing "unable to open database file," actually a permission error (/srv itself is root-owned)
↓
COPY src ./src, EXPOSE 8093
↓
CMD uvicorn src.hrb_chatbot.main:appNo --app-dir flag - this repo's own modules import as from src.hrb_chatbot..., the opposite convention from the newer split services

2Real CI/CD pipeline the original pattern every other service's workflow was copied from

Real incident, 2026-10-23: a Postgres search_path connection-option change (Phase 251) shipped to production independently of the schema migration SQL it was meant to support - Neon's pooled connection endpoint rejects that option outright, breaking every production query for several minutes before being hotfixed (commit 2293fa2). Unrelated to the build/deploy pipeline itself, but it's this service's own most recent real production incident.
