Build Process — hrb_chatbot_ui

First in the sequence - what the end user's browser actually loads. No Docker image, no JVM, no App Runner: a static Vite/React build, synced directly to S3 behind CloudFront. Written so every step below is something you could type yourself in a terminal, not just a description of what CI does.

⇄ If you've built Java/Spring Boot before, here's the mapping
This projectClosest Java/Spring Boot equivalent

tsc -bmvn compile (fails the build on a type error, before packaging)
vite build → dist/mvn package → target/*.jar - except the output is static HTML/JS/CSS, not a runnable artifact
aws s3 sync dist/ + cloudfront invalidateno real equivalent - a Spring Boot app ships a JAR to a server that runs it; this ships files to a CDN that just serves them. There's no "app server" here at all.

1Do this yourself, step by step exactly what you'd type from a clean checkout - this is what CI also runs

1Install dependencies, exactly as locked≈ mvn dependency:resolve
Not npm install - npm ci deletes node_modules first and installs strictly from package-lock.json, so a build can never silently drift onto a newer dependency version than what's committed.
$ npm ci
2Type-check the whole app≈ mvn compile
Runs before any bundling starts. A type error here stops the build cold - the same role a compile error plays in a Java build, just checked by tsc instead of javac.
$ npx tsc -b
3Bundle and minify≈ mvn package
Vite bundles every import graph into a handful of files under dist/, with content-hashed names (e.g. index-n46-X6h8.js) so a new deploy's filenames never collide with a browser's cached copy of the old build.
$ npx vite build
# → dist/index.html, dist/assets/*.js, dist/assets/*.css
4Which backend URL got baked in≈ an application.properties profile
Vite inlines VITE_API_BASE_URL at build time, not read at runtime like a Spring application-prod.properties would be - there's no config file in the shipped image to override later; a different backend means a different build.
# .env.production, read automatically by step 3 above
VITE_API_BASE_URL=https://necxf9n7mv.us-east-1.awsapprunner.com

2What CI automates on top of that .github/workflows/deploy.yml - triggers on push to master, same stage shape as a Jenkinsfile

5Checkout + Node 20 toolchain≈ Jenkins SCM checkout + Tool install
actions/checkout, actions/setup-node with npm's own cache wired in - the GitHub Actions equivalent of a Jenkins agent pulling the repo and provisioning its JDK/Maven.
runs steps 1-4 above, unchanged↓
6Assume a scoped deploy identity≈ Jenkins Credentials Binding plugin
IAM user hrb-chatbot-ui-github-actions-deploy - permissions limited to this one S3 bucket and this one CloudFront distribution, nothing else in the account.
↓
7Upload the hashed assets, cached forever
Every hashed file under dist/assets/ gets Cache-Control: public, max-age=31536000, immutable - safe only because step 3's content hash guarantees a changed file always gets a new name.
$ aws s3 sync dist/ s3://hrb-chatbot-ui-rvsree/ --cache-control "public, max-age=31536000, immutable" --exclude index.html
↓
8Upload index.html separately, never cached
It references those hashed filenames by name, so it must never be served stale - the opposite caching policy from step 7, on purpose.
$ aws s3 cp dist/index.html s3://hrb-chatbot-ui-rvsree/index.html --cache-control "no-cache, no-store, must-revalidate"
↓
9Invalidate the CDN edge cache
Without this, CloudFront's edge locations could keep serving yesterday's index.html out of cache for up to its configured TTL.
$ aws cloudfront create-invalidation --distribution-id E1CBYCM65AXV9Y --paths "/*"
≈ Jenkins post-deploy smoke-test stage↓
10Smoke test the live site
The job fails loudly if the real production URL doesn't actually answer - CI never reports success on a deploy nobody can reach.
$ curl --fail https://hrb-chatbot-ui.rvsree.dev/
