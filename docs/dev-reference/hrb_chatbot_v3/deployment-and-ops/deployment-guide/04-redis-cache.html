Redis Cache

Decided: Redis is the caching layer for this project's production architecture — chosen because it's the correct, industry-standard tool for this job, not because it's convenient. This page is the implementation plan.

Why Redis, stated plainly: a relational database (Postgres included) is built for durable, transactional, relational data. A cache needs native TTL/expiry, sub-millisecond in-memory reads, and purpose-built eviction policies — none of which a SQL database provides without being bent out of its intended shape. Redis is the standard tool for this job across the industry, and this project's architecture should reflect that standard, not a workaround. Postgres-backed caching (Phases 77-78) was always the interim step, not the destination.

Current state — what Redis replaces

Two Postgres-backed caches exist today (see the Neon Postgres page): answer_cache and embedding_cache, both built on the same psycopg-via-asyncio.to_thread() pattern as every other Postgres client in this project. Both move to Redis. Conversation history (conversation_turns) stays on Postgres — it's durable application data, not a cache, and doesn't belong on Redis.

Gap in the current Postgres implementationWhat Redis provides natively
No TTL — rows only disappear via a blunt clear_all() on any document changePer-key expiry (SET key value EX seconds) — standard cache semantics, no custom cleanup logic needed
Every cache hit pays a full SQL connection + query round-trip to NeonSub-millisecond in-memory lookups — the entire reason caching layers don't normally sit on a relational database
No eviction policy — unbounded growth until clear_all() firesConfigurable eviction (allkeys-lru, etc.) — bounded memory by design

Architecture fit

This follows the exact pattern already established for every other backend in this project — one client class, one gateway, callers never branch on provider:

common/clients/cache_client/
    base_cache_client.py      # ABC: get(key), set(key, value, ttl), delete(key), health_check()
    redis_cache_client.py     # RedisCacheClient implementing the ABC via redis-py / Lettuce-equivalent

common/clients/cache_client/cache_gateway.py   # singleton, same lazy-build pattern as DBGateway

pipeline.py's call sites (get_db_gateway().answer_cache().get(cache_key) / .set(...)) change to get_cache_gateway().answer_cache().get(cache_key) / .set(..., ttl=...) — the call shape barely moves, matching how swapping a Spring CacheManager implementation never touches a single @Cacheable annotation.

Implementation plan

  • Write the Phase spec first (per this project's own spec-first convention) — scope: answer_cache and embedding_cache move to Redis; conversation_store stays on Postgres; rate_limiter.py is now in scope too — its own docstring already names Redis as the fix, so bring it along in the same migration rather than a separate follow-up
  • Add redis==<pinned version> to requirements.txt (the official redis-py client, async-capable — no separate driver needed, unlike psycopg's sync-then-to_thread wrapper)
  • Build base_cache_client.py (ABC) + redis_cache_client.py, following base_metadata_client.py's existing shape
  • Add a CacheGateway (cache_gateway.py) — singleton, lazy client build, same convention as DBGateway/ClientGateway
  • Port build_cache_key() and hash_text() unchanged — the key-construction logic isn't backend-specific
  • Set real TTLs: answer cache entries expire on a short-to-medium window (minutes-to-hours — answers can go stale when a document updates); embedding cache entries can live much longer (an embedding for the same content hash never changes)
  • Replace the blunt clear_all() invalidation in documents_service.py with either a shorter TTL (simplest) or targeted key deletion if per-document cache keys become trackable later
  • Add a FakeCacheClient to tests/conftest.py, matching the existing FakeAnswerCache/FakeEmbeddingCache pattern — zero real Redis calls in the default test suite, same guarantee every other backend already has
  • Provision AWS ElastiCache for Redis (the managed option — same relationship to self-hosted Redis as Neon has to self-hosted Postgres) for the AWS environment
  • Local dev: Redis via Docker (docker run -p 6379:6379 redis) or Docker Compose — a one-line addition, not a new ops burden
  • Update docs/agent-reference/AWS-DEVOPS-RUNBOOK.md and the "Status at a glance" table in RAG-ROADMAP.md once live
  • Run the golden-dataset release gate (eval-gate.yml) after the swap, same as any other feature — confirms answer quality is unaffected by the caching-layer change

Ideal timing: right after Pinecone, before batch ingestion

Confirmed and revised 2026-10-05 — Redis moves earlier than originally sequenced, right after the Pinecone fix and before the S3+Lambda build. Two separate justifications, not one:

Your reasoning, validated with a caveat

Treating Redis as a prerequisite to settle before the big ingestion build, to avoid rework — this holds, but precisely: Redis is not a hard technical blocker for Lambda the way Pinecone is (Postgres-backed caching works fine from Lambda too — it's a network call, not a local file, so it doesn't hit the ephemeral-filesystem problem). The existing gateway/client-abstraction pattern (same one documented in the architecture fit above) already isolates every call site from which cache backend is behind it, so swapping Postgres → Redis later would touch very little call-site code regardless of when it happens. The "avoid rework" risk is real but smaller than Pinecone's.

A second, independent, and stronger reason — found during this review

The rate limiter is already broken at scale, right now, independent of caching. rate_limiter.py's own docstring says it plainly: "In-memory, fixed window — single-process only, Redis is the fix once this scales out." Confirmed live: App Runner's auto-scaling config allows up to 25 instances (MaxSize: 25). Each instance tracks its own request count independently — so the configured limit (100 requests/30s) doesn't hold across instances; it effectively multiplies by however many instances are running at the time. This isn't a future risk, it's a present gap that happens to have the same fix as the caching work.

Doing Redis here fixes two already-existing gaps in one migration (cache TTL/performance, and rate-limiter correctness under App Runner's real auto-scaling), and — matching your reasoning — finishes the smaller, well-understood infrastructure work before the much larger, higher-risk S3+Lambda build, rehearsing the full CI/CD + golden-dataset gate on lower-risk changes first.

Revised order: Pinecone fix → Redis → S3+Lambda batch ingestion → React UI (last). See the milestone plan for the full picture.
