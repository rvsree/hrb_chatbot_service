Non-Functional Requirements: Reliability & Resilience

A whole-system gap-check — scalability, reliability, resilience, logging/monitoring, error handling, retry, rate limiting, load balancing. Every finding below was verified against the real code or the live AWS account on 2026-10-05, not assumed.

Verified findings

✗ No retry/backoff on any LLM call — checked openai_client.py, anthropic_client.py, bedrock_client.py, open_router_client.py: zero retry logic. Only tavily_client.py has it (hand-rolled exponential backoff, no external library — the pattern to replicate, not something to introduce fresh with a new dependency).

✗ No explicit timeout on the primary LLM ask() calls — relying entirely on each SDK's own default (OpenAI's default is generous, not something this project has deliberately tuned). Timeouts exist elsewhere (Postgres connect_timeout=5, Tavily's configurable timeout, OAuth's httpx client) but not on the calls that matter most for request latency.

✗ Rate limiter is broken across multiple instances, right now — rate_limiter.py's own docstring: "in-memory, fixed window, single-process only." Confirmed live: App Runner's auto-scaling config allows up to 25 instances (MaxSize: 25, MaxConcurrency: 100 per instance before scaling triggers). Each instance counts independently, so the configured 100-requests/30s limit doesn't actually hold once App Runner scales past one instance. Fix: Redis — already the documented intended fix, now scheduled.

✗ Zero CloudWatch alarms configured — confirmed via aws cloudwatch describe-alarms: empty list. No alerting today on error rate, latency, or anything else — a failure has to be noticed by a human checking manually.

○ Logging is plain text, not structured — logger.py's format is "%(asctime)s | %(levelname)-8s | %(name)s | %(message)s". Fine to read directly, but CloudWatch Logs Insights queries need regex against free text instead of querying structured fields (e.g., "every ERROR for employee_id=X" isn't a clean query today).

✓ Load balancing is already handled — nothing to build — App Runner provides a managed load balancer in front of however many instances are running, automatically. Worth knowing this explicitly so it's not mistaken for a gap: there's no ALB/NLB to configure by hand, no Spring Cloud LoadBalancer-equivalent code to write. This is managed infrastructure, invisible by design.

✓ Rate limiting and CSRF exist and are correctly wired — just not scaling-aware yet (see above). The feature itself (api/dependencies.py, APP_RATE_LIMITING/APP_RATE_LIMIT_REQUESTS) is real, tested, and on by default.

Recommended sequencing for these fixes

Not a new standalone milestone — these fold into the milestones already planned, at the point each becomes relevant:

  • Rate limiter fix — folds into Milestone 2 (Redis), already updated to include it
  • Retry/backoff on LLM clients — small, isolated, low-risk — a good candidate to slot in alongside Milestone 2 (Redis) or as its own quick pass before Milestone 3 (batch ingestion), since Lambda invocations specifically benefit from not failing an entire document's indexing over one transient API hiccup
  • CloudWatch alarms (DLQ depth, Lambda error rate) — introduced as part of Milestone 3 (batch ingestion) by design, since that's the first place in this system using SQS/Lambda at all
  • Structured JSON logging — worth starting with the new Lambda handler in Milestone 3 (clean slate, no existing format to migrate), then backfilling the rest of the app later as a separate, explicitly-scoped cleanup — not bundled into any feature milestone silently
  • Postgres connection pooling — not urgent at current traffic; worth revisiting once real production usage data exists, not before
  • Circuit breakers — lowest priority of this list; the existing timeout+retry combination covers most of the same real-world failure modes at this project's current scale
