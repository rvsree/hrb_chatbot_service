Milestone Plan & Golden Dataset Gate

The incremental, MVP-based delivery order for everything in this guide, and the one quality gate every milestone must clear before touching master.

Direct answer to "did you cover golden dataset testing": no — it was a real gap in the first pass of this guide. This page fixes that, and makes the gate a standing rule for every milestone below, not a one-off from Phase 80.

The golden dataset gate, explained

This already exists and has already run successfully once (Phase 80) — it's not new work, just not previously documented here.

Java / Spring Boot analogyThis project
A SonarQube quality gate, or a contract-test suite, blocking a merge/release pipeline on failureeval-gate.yml — a GitHub Actions workflow that scores the app's real answers against a labeled dataset and fails the job on a bad verdict
A curated regression test suite with expected outputsresources/golden_dataset/golden_dataset.json — 24 real HR-benefits questions, each with an expected source document and expected answer characteristics
Fails the build if coverage/quality drops below a thresholdscripts/run_release_gate.py computes recall, groundedness, completeness per case, averages them, and calls get_release_decision() — BLOCK fails the job (exit 1)

How to run it

# Manual trigger only — real LLM calls, real cost, never on every push
gh workflow run eval-gate.yml
gh run watch                       # follow it live
gh run view <run-id> --log-failed  # if it fails, see exactly why

What it does, end to end: spins up a fresh Postgres service container, starts the real app, ingests every PDF in resources/kb_docs/ through the real upload endpoint, runs all 24 golden-dataset questions through the real pipeline, and prints a per-case and aggregate score before passing/failing the job.

Current scope limit, worth knowing: the gate only scores genai-rag (POST /v1/genai-rag/retrieve-document/query). Single-agentic-rag and multi-agentic-rag aren't gated yet — a natural, same-shape follow-up, not yet built. If a milestone below changes retrieval behavior for those endpoints, treat the genai-rag gate as a partial signal, not full coverage, until that follow-up lands.

The gate every milestone must clear

Applied uniformly to every feature below before it's considered done:

  1. Implemented and tested locally — full suite green: pytest -v
  2. Manually verified end to end locally (the feature actually works, not just "tests pass")
  3. Feature branch → develop, tests still green on develop
  4. develop → master (fast-forward where possible, matching this project's established pattern)
  5. deploy.yml fires automatically on the push to master — confirm it reaches RUNNING and the smoke test passes
  6. Post-deploy live check: hit /health and the specific new/changed endpoint(s) against the real AWS URL
  7. Run eval-gate.yml — require a PASS verdict before considering the milestone closed, not just before merging code
  8. Update docs/agent-reference/RAG-ROADMAP.md's phase entry (spec + verified notes) and this guide if anything here is now stale

Incremental milestone order — revised 2026-10-05

Reordered from the original draft: Pinecone and Redis both move before the big ingestion build — Pinecone because it's a hard technical prerequisite (Lambda can't use ChromaDB's file-based mode), Redis because it independently fixes an already-broken rate limiter at App Runner's real scale, not just because it's convenient to settle first. See doc 3 and doc 4 for the full reasoning on each.

Milestone 1 — Pinecone as the standing AWS vector store

Smallest, fastest milestone, and a hard prerequisite for Milestone 3 — fixes the ACTIVE_VECTOR_DB/RAG_VECTOR_DB env var mismatch, confirms Pinecone is genuinely live, runs the full endpoint test matrix. See doc 3. Good first milestone — proves the gate process end to end on something small before the bigger work ahead.

Milestone 2 — Redis cache migration

Moves answer_cache, embedding_cache, and the rate limiter onto Redis. See doc 4 for why this comes before ingestion rather than after. Also the slot where retry/backoff on the 4 LLM clients is worth adding (see doc 6) — small, isolated, benefits every later milestone.

Milestone 3 — S3 batch ingestion + Lambda

The biggest piece — presigned uploads, Lambda-driven indexing, SQS DLQ, CloudWatch alarms. Full architecture, NFR considerations, and testing plan in doc 5. Recommend breaking this into its own sub-phases (spec'd individually): (1) S3 bucket + presigned URL endpoint, (2) Lambda handler + event wiring, (3) DLQ + status-machine wiring + CloudWatch alarms, (4) end-to-end test with a real batch upload bypassing the API.

Milestone 4 — React UI (last)

Per doc 7 — explicitly sequenced after Milestones 1-3 are all complete and deployed. Same repo, frontend/ folder, its own SDD setup. CORS middleware is a small prerequisite inside this milestone, not a separate one.

Each milestone is its own MVP: smallest working version first (e.g., Milestone 3's MVP is "one document, uploaded via presigned URL, successfully indexed by Lambda" — before batch/retry/DLQ polish), verified through the full gate above, then the next layer of polish within that same milestone, re-gated again if the change is substantial enough to warrant it.
