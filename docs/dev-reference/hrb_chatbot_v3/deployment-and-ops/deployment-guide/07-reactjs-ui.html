Same repo or separate repo?

Recommendation: same repo, a frontend/ folder. Not the "easier" choice made for convenience — the reasoning:

  • A monorepo doesn't actually bloat. Git handles folders natively; node_modules/ and dist/ are gitignored exactly like .venv/ already is for the backend. The repo doesn't grow meaningfully from adding source files in a sibling folder.
  • CI/CD stays cleanly separated anyway — GitHub Actions supports path-scoped triggers (on.push.paths: ["frontend/**"]). A frontend-only commit never runs the backend's test suite/Docker build, and vice versa. Same isolation a separate repo gives you, without the separate-repo overhead.
  • A separate repo's upfront cost is real, not nominal: its own CI/CD workflow files from scratch, its own AWS deploy credentials (S3/CloudFront, separate from the backend's ECR/App Runner ones), its own branch-protection/default-branch setup (the exact kind of misconfiguration this project's own backend hit and had to fix manually), and cross-repo coordination any time an API contract changes on one side.
  • For interview/portfolio presentation, a well-organized monorepo is a normal, well-regarded structure — it demonstrates the ability to manage a cohesive full-stack system with clear internal boundaries, which is exactly what gets evaluated. Separate repos are typically chosen for organizational/team-scaling reasons (independent release trains, separate ownership) that don't apply to a solo project at this stage — splitting now would be optimizing for a problem that doesn't exist yet.

What's missing on the backend before a UI can call it

CORS is not configured. Confirmed — no CORSMiddleware exists in main.py. A React dev server (localhost:5173) calling this API directly will be blocked by the browser until this is added. One small, standard FastAPI addition — not a redesign.
Auth is still a placeholder. The gateway's RBAC reads an unsigned user_profile straight from the request body — a UI makes this limitation much more visible to an actual user than Postman testing did (there's no login screen to back it, so the UI would need to let the user "claim" an identity, which is awkward for anything beyond a demo).

  • Deployment (real, done): a static React build (npm run build → plain HTML/JS/CSS) is not an App Runner container — it deploys to S3 (hrb-chatbot-ui-rvsree bucket, static hosting) + CloudFront instead, the standard AWS pattern for a single-page app. Different pipeline from the backend's Docker/ECR/App Runner one, and - unlike the backend - no GitHub Actions workflow exists for it: every deploy is 3 commands, run by hand.
