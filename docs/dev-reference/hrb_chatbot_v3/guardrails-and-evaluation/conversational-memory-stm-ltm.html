Conversational Memory: STM vs LTM

This project has two genuinely different mechanisms both called "STM/LTM" - built in different phases, for different reasons, never connected to each other. This page exists to keep them straight. See state-management-diagram.html for where each one physically lives, and testing-strategies.md for how (B) relates to the golden/synthetic dataset story.

(A) · Phase 247, pre-existing

Conversation memory tiers

What it means here: how much of a conversation's own history gets loaded back into the prompt. STM = recent turns, short Redis TTL. LTM = older turns, longer TTL. Both are about continuity within one conversation - does the bot remember what you said 3 turns ago.

Where: Redis, split by key prefix. Assembled by assemble_context() before every genai-rag / single-agentic-rag / multi-agentic-rag answer.

Unaffected by this session's work. No code in Phase 256-260 touches this mechanism.

(B) · Phase 257, built this session

Live-query quality gate

What it means here: a label on a captured, already-answered question - does this one specific Q&A pair clear a groundedness bar. Nothing to do with conversation continuity; a single-turn genai-rag query with no conversation history at all can still be flagged is_ltm = true.

Where: Postgres, hrb_query_capture.live_queries.is_ltm column. Threshold (default 0.6) is itself a dynamic app_settings value, editable from the UI.

Purpose: curate a pool of real, already-well-answered questions - a dataset-quality concept, not a memory concept. See the dataset comparison table below.
