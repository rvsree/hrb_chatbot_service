Common-Libs Connectors — Decisions

Why one package with extras, not ten repos or one grab-bag. What success looks like.

Overview Spec Architecture Design Decisions
1One package with extras, not ten repos
If UI/BFF shouldn't need the LLM or MCP connector, why not just give each its own repo entirely? Ten tiny repos for a solo developer is real overhead for no real benefit: ten sets of CI config, ten places a shared bugfix (e.g. to the observability base) has to be re-published, ten version numbers to track. Python's own extras_require mechanism already solves "install only what you need" without needing ten repos - pip install hrb_common_libs[db,cache] never touches llm's dependencies at all. One repo, real install-time isolation, a tenth the repo-management overhead.
2Corrects an earlier mistake in this planning
Why does this doc exist at all, separate from the earlier rollout plan? The rollout plan originally proposed one monolithic hrb_common_libs with everything bundled - wrong, and worth saying so plainly rather than quietly fixing it. Checked the real common/clients/ folder structure before writing this doc instead of re-guessing, and it already has the right boundaries; extras formalize what the folder names already express.
