AWS Pause/Resume Lifecycle

How the 6 demo AWS App Runner services fall asleep to save money, and how they wake back up - written for an engineer who knows the business logic of this project well, but hasn't worked with App Runner, Lambda, or IAM before. Covers hrb_chatbot_service's own Phases 261/262/284/286/287/288.

AWS App Runner AWS Lambda Function URLs IAM least-privilege FinOps cost control
1Why this exists

This project runs 6 separate backend services on AWS App Runner (hrb-chatbot, hrb-api-gateway, hrb-lms-mcp, rag-retrieval-service, rag-ingestion-service, hrb-platform-components). App Runner bills for compute time while a service is RUNNING - whether or not anyone is actually using it. This is a personal/demo project with sporadic visitors, not 24/7 real traffic, so leaving all 6 running around the clock burns real money for nothing.

The fix: let every service pause itself when nobody's been active for a while, and wake back up automatically the moment someone actually shows up - without the visitor ever having to know any of this happened. Everything on this page exists to make that handoff reliable.

2Glossary - the AWS pieces this system is built from
App Runner
AWS's "just run my container" service. Each of the 6 backends is one App Runner service. A service is either RUNNING (billed, reachable), PAUSED (not billed, not reachable - its own front door answers everything with a bare 404), or OPERATION_IN_PROGRESS (transitioning between the two, takes 30-90 seconds).
Lambda
A small function AWS runs for you on demand - no server to keep running. Billed per invocation (a few milliseconds of compute), not per hour. This project uses 2 Lambdas for this system: hrb-idle-auto-pause and hrb-wake-up.
Function URL
A public HTTPS address AWS gives a Lambda directly, with no separate API Gateway needed. hrb-wake-up's Function URL is what the login page calls - it works even while hrb-chatbot itself is fully paused, because a Lambda has no "paused" state of its own.
IAM role
The specific list of AWS actions a Lambda (or any AWS identity) is allowed to perform. Each Lambda here gets its own narrow role - hrb-wake-up's role can only DescribeService/ResumeService on hrb-chatbot specifically, nothing else.
EventBridge
AWS's scheduler - "run this Lambda every N minutes," like a managed cron job. hrb-idle-auto-pause runs on an EventBridge schedule, roughly every 15 minutes.
Secrets Manager
Where real credentials (Postgres password, Redis URL) are stored - Lambdas fetch them at runtime via the AWS SDK, never as plaintext environment variables, so a leaked Lambda config never leaks a password.

Important nuance: a PAUSED service doesn't time out or error when you hit it - its own AWS front door (the "envoy" proxy in front of every App Runner service) answers instantly with a plain, empty 404, before your request ever reaches the actual container. That's by design, but it means a 404 here can mean two very different things: "this route doesn't exist" vs. "this whole service is asleep" - this system exists partly so a visitor never has to tell the difference.

4What can PAUSE a service
⏳ Idle-auto-pause Lambda
Runs on its own EventBridge schedule (~every 15 min). Checks a Postgres timestamp ("when did anyone last do anything?") and pauses any of the 6 services still RUNNING if that timestamp is older than the configured threshold (default 60 minutes, now editable from Settings → Resiliency - Phase 288). Fails safe: any read error means "do nothing," never "pause by mistake."
🚪 Sign-out accelerant
Fires the instant someone clicks Sign Out, but only if the backend confirms zero other browser tabs/sessions are still active (tracked per-tab in Redis). Skips straight to "do nothing" otherwise - never pauses out from under someone else's live session.
👤 Manual admin action
The Settings → AWS Demo tab lets an admin pause/resume any of the 6 services by hand, for demos or debugging. Same underlying AppRunnerClient code path as the two automatic triggers above.
5What can RESUME a service
🔌 Wake-up Lambda (hrb-chatbot + hrb-api-gateway)
A standalone Lambda, its own public Function URL, called by the login page the instant "Sign In" is clicked - before any credential check. Resumes both hrb-chatbot and hrb-api-gateway, whichever of the two is actually PAUSED, rate-limited per visitor IP (default 10/day, Settings → Resiliency, one check per invocation, not per service). Phase 287 shipped with just hrb-chatbot; Phase 289 widened it to the gateway too - see the 2nd incident below for why.
✅ Backend-activation flow (the other 4 - non-blocking)
Lives inside hrb-chatbot itself (route POST /v1/auth/backend-activation/resume). Fired immediately after a successful login, in the background, fire-and-forget (Phase 26, 2026-11-01) - the chat page no longer waits on it. Resumes hrb-lms-mcp and the 2 standalone RAG services (confirmed, by reading the actual pipeline code, that none of the 3 are needed for a basic first chat message - only specific questions/pages touch them). The old pre-check (GET /backend-activation/status) was removed entirely as dead code once nothing blocked on its answer anymore.
👤 Manual admin action
Same AWS Demo Settings tab as above, in reverse.
⚠ The real incident this system had to be redesigned around

Early versions of the idle-auto-pause Lambda and the sign-out accelerant treated all 6 services identically - including hrb-chatbot itself, the one service that hosts every route that could ever trigger a resume (login, backend-activation, the AWS Demo tab). The result, confirmed live in production:

hrb-chatbot RUNNING → idle timer fires → hrb-chatbot PAUSED → no route left to resume it → 🚫 stuck

Every door out of the house was on the inside of a door that had just locked itself. The only way out was a human running aws apprunner resume-service directly from a terminal - not something a real visitor could ever do.

✅ The fix (Phase 287) - move the "spare key" outside the house

The standalone hrb-wake-up Lambda has no "paused" state of its own - it isn't an App Runner service, it's a Lambda, so it's always reachable regardless of what state hrb-chatbot is in. It holds exactly one key: permission to describe/resume hrb-chatbot specifically. hrb-chatbot went back to being a perfectly normal, auto-pausable service - the fix wasn't "stop pausing it," it was "make sure something outside it can always let it back in."

hrb-chatbot PAUSED → visitor clicks Sign In → hrb-wake-up Lambda (always reachable) → hrb-chatbot RUNNING → login proceeds normally

This isn't hypothetical - the exact failure mode above happened again for real on 2026-11-01, during this feature's own rollout (a config fix to the idle-pause Lambda caused it to genuinely pause hrb-chatbot for the first time in its life). The new wake-up Lambda resumed it cleanly with no human intervention - the first real proof the fix works, not just a unit test.

⚠ The 2nd incident - the same deadlock, one layer higher (Phase 289)

The fix above shipped, got tested, and then a real visitor hit the exact same symptom again on a Sunday: "Waking up the chatbot service" hung for 2-3 minutes, then "Continue anyway" led straight to "Something went wrong reaching the backend." Phase 287's own live verification had curled hrb-chatbot.rvsree.dev directly to confirm the fix - but that's not what the real frontend actually calls. Checking the real deployed JS bundle found VITE_API_BASE_URL was hrb-api-gateway's own App Runner URL, not hrb-chatbot.rvsree.dev. Every request - login, the wake-up Lambda's own /ping poll, everything - was actually going through the gateway first.

hrb-wake-up resumes hrb-chatbot → /ping still routes through hrb-api-gateway → gateway is PAUSED too → nothing had permission to wake it → 🚫 stuck again

Two fix options were weighed, not assumed: bypass the gateway (point the frontend straight at hrb-chatbot.rvsree.dev - hrb-chatbot's own CORS already allows it, zero AWS change needed) vs. widen the wake-up Lambda to also resume the gateway. The bypass was rejected on purpose - the gateway is this project's intended long-term single entry point (RBAC/CORS/rate-limiting, for when more services sit behind it), and routing around it would have been a working shortcut that fights that direction rather than a real fix.

✅ The fix (Phase 289) - the Lambda gets a second key, not a detour

hrb-wake-up's own code was rewritten to target both hrb-chatbot and hrb-api-gateway - still just those 2 ARNs once its IAM role and AWS config catch up, still least-privilege, still nothing to do with the other 4 services. One rate-limit check per invocation either way, not doubled. The architecture stays exactly what it was designed to be; the Lambda just needs to hold the right number of keys for what the real frontend actually calls.

Status, 2026-11-01: code written and fully tested (15 unit tests, full suite green); the IAM role widening, the Lambda's own AWS config, and the image redeploy are confirmed but not yet applied in AWS, held deliberately until a full cleanup/testing pass is done first - this page will be updated again once it's actually live.

6End-to-end sequence - a visitor arrives at a fully paused site
  1. 1. Browser loads the login page. Nothing AWS-related happens yet - this is just static files from CloudFront/S3.
  2. 2. Visitor clicks Sign In. The page shows "Waking up the chatbot service, please wait" and, in the background, POSTs to the hrb-wake-up Function URL - before checking the typed-in credentials at all.
  3. 3. The Lambda asks App Runner (DescribeService) what state both hrb-chatbot and hrb-api-gateway are in. If both are already RUNNING, the Lambda does nothing else and returns immediately - this is the common case, and it resolves in well under a second.
  4. 4. For whichever of the two is PAUSED: the Lambda checks this visitor's IP against today's rate limit (once, not per service), then calls ResumeService on just the paused one(s). App Runner starts transitioning to RUNNING (30-90 seconds, in parallel if both needed it).
  5. 5. The browser polls GET /ping every few seconds through VITE_API_BASE_URL (the gateway, which proxies to hrb-chatbot) - a tiny, no-login-needed "are you alive yet" check - until it finally answers 200, meaning both services are actually up, not just one.
  6. 6. Now the browser sends the actual login request (employee_id/full_name/role/secret code), which is now guaranteed reachable end to end.
  7. 7. If login succeeds, the frontend fires the backend-activation resume call for the other 4 services in the background (Phase 26) and goes straight to the chat page without waiting for it - no second wait screen anymore.
  8. 8. Chat page loads. From the visitor's point of view, none of the above was visible except one brief loading message.
7Why a Lambda, and not just "keep hrb-chatbot always on"?

That was the first fix tried for the 1st incident above - exclude hrb-chatbot from both pause triggers, so it never sleeps. It worked, but it defeated the whole point: App Runner bills for provisioned compute the entire time a service is RUNNING, even completely idle. Keeping one of the 6 services on 24/7 is a real, ongoing cost - exactly what this whole feature line exists to avoid.

A Lambda's billing model is the opposite: you pay for the few hundred milliseconds it actually runs, essentially nothing while nobody is logging in. That's the actual reason the fix is "add a tiny always-reachable Lambda," not "keep the big service always-reachable."

Other options considered and rejected (recorded in RAG-ROADMAP.md Phase 287): routing all traffic permanently through hrb-api-gateway and keeping that one service always-on instead - rejected for the same 24/7-cost reason as above. Correction, 2026-11-01: this page previously also claimed the gateway "isn't even wired into real traffic today" - that was wrong, confirmed by inspecting the real deployed frontend bundle (see the 2nd incident above) - it's actually in front of every request. CloudFront + Lambda@Edge intercepting failed requests - rejected as disproportionate (this project has never used CloudFront on the backend side). A scheduled "always on during business hours" window - rejected, traffic here is sporadic and on-demand, not a predictable 9-to-5 pattern.

Neither role can touch anything the other one can't already justify needing - least-privilege per function, not one shared "Lambda admin" identity.

9Nuances worth remembering
  • A RESUME_SERVICE/PAUSE_SERVICE call succeeding doesn't mean traffic is routable yet - there's a short warm-up window right after App Runner reports RUNNING where a request can still bounce with a 404 from the front-door proxy. This is normal, not a bug; it's why the frontend polls /ping in a loop instead of firing one request and giving up.
  • Calling resume on a service that's already RUNNING is harmless (AWS just reports the current state back) - this project relies on that idempotence instead of special-casing "already running" everywhere.
  • Updating a Lambda's environment variables via the AWS CLI replaces the whole variable map, it doesn't merge - a real near-miss during this feature's rollout, where setting one new variable briefly wiped out an existing one until caught and corrected.
  • A public Function URL with AuthType: NONE still needs two separate permission statements to actually allow anonymous calls (InvokeFunctionUrl and a second InvokeFunction permission) - AWS's own CLI doesn't make this obvious, and getting only one of the two still produces a confusing 403.
  • The idle-pause Lambda silently did nothing for a while after it first shipped, because a configuration value it needed was never actually set - no error, no alarm, just an empty list of services to check. Nothing here raises loudly on a missing config by design (fail-safe toward "don't accidentally pause something"), which is exactly why this kind of gap can hide for a while - worth a periodic sanity check, not just trusting "no errors in the logs" as proof something is working.
  • Biggest lesson from the 2nd incident: verifying a fix by calling a backend service directly (curl hrb-chatbot.rvsree.dev/ping) is not the same as verifying the real user path - the live frontend's own VITE_API_BASE_URL turned out to be a different URL entirely. Checking the actual deployed JS bundle for the literal base URL it calls is a cheap, concrete way to confirm what "the real path" even is, rather than assuming it matches what the docs say it should be.
