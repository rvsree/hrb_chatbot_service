The dependency arrow only ever points one way - this layer never calls back up into a service, and never knows which services exist.

2The four components
Observability request_id/response_id generation and propagation, structured JSON logging matching call_logger.py's existing shape, LangSmith trace tagging. precedent: Phase EX-1, call_logger.py
Resiliency Retry/backoff decorator with per-call-site overrides; a consecutive-failure-count + cooldown pre-flight check (not a formal 3-state machine), generalized from the MCP-specific one. precedent: Phase 185, mcp_registry_client.py
Security baseline One settings helper resolving secrets only from Secrets Manager/env; an identity-validation contract every service applies to whatever the Gateway forwards. precedent: existing Secrets Manager convention
Caching primitives Redis connection helper and a shared key-naming convention ({service}:{purpose}:{hash}) so independent services' cache keys never collide. precedent: answer_cache.py, embedding_cache.py
3Request flow with this layer active

A request enters api_gateway_service → Observability assigns a request_id → the Gateway forwards to rag_retrieval_service with that id in a header → Resiliency wraps its calls to Postgres/vector store/LLM provider, each wrapped call logged with the same request_id → if the LLM provider times out repeatedly, Resiliency's circuit breaker opens and the service returns a typed degraded-service error instead of hanging → the whole trace is one LangSmith run, filterable by request_id, regardless of how many services it crossed.
