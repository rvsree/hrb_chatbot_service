NFR Components — Spec

Requirements, acceptance criteria, personas, and constraints for the shared resiliency/observability/security-baseline layer every microservice depends on.

Overview Spec Architecture Design Decisions
1Persona

Not an end user - the person reading this is the future Claude Code session (or the user directly) building api_gateway_service, rag_ingestion_service, rag_retrieval_service, chat_audio_service, or employee_401k_service, who needs to know exactly what this layer already gives them so they don't re-derive it.

2Functional requirements
  • MUSTEvery service's entry point extracts/generates a request_id and makes it available to every log line and outbound call for that request's lifetime.
  • MUSTEvery outbound call to Postgres, the vector store, an LLM provider, or another service goes through a retry/backoff wrapper with documented default max-attempts and backoff curve.
  • MUSTA dependency failing past a configured threshold trips a circuit breaker (consecutive-failure-count + cooldown pre-flight skip, not a formal 3-state machine), generalizing Phase 185's MCP-specific implementation.
  • MUSTEvery secret (API key, DB password, OAuth2 client secret) resolves through one settings helper backed by Secrets Manager/env - never a literal default in code.
  • SHOULDEvery service tags its LangSmith traces with request_id so a cross-service failure is one filtered search, not five separate log greps.
  • SHOULDRedis-backed caches follow one key-naming convention ({service}:{purpose}:{hash}) so cache keys from different services never collide in the same Redis instance.
3Non-functional requirements
  • Latency overhead: the retry/circuit-breaker wrapper itself must add under 5ms to a successful call - this is a safety net, not a performance feature.
  • Default circuit breaker threshold: skip after 2 consecutive failures, 10s cooldown - matching the real, live MCP_CIRCUIT_BREAKER_FAILURE_THRESHOLD/MCP_CIRCUIT_BREAKER_COOLDOWN_SECONDS defaults (Phase 185), verified against the code, not a number invented for this doc.
  • No service-specific logic leaks in: this layer never imports anything from a specific service's business logic - it's a one-way dependency.
4Acceptance criteria
  • A new service that imports hrb_common_libs[observability] gets request_id propagation and structured logging with zero additional code beyond calling the provided middleware/decorator.
  • Killing a dependency mid-request (e.g. stopping local Postgres) trips the circuit breaker within the configured failure threshold and the caller gets a clean, typed error - not a hung connection or a stack trace.
  • Grepping a LangSmith trace by request_id surfaces every service that touched that request, not just the one it originated in.
5Constraints
  • Python 3.12 only, matching every other service in this system (ChromaDB's Pydantic v1 internals rule out 3.13/3.14).
  • No new infrastructure - this is a library, not a deployed service or sidecar. See Decisions for why a service mesh (Istio/Linkerd-style) was considered and rejected.
  • Must not require every consuming service to also depend on hrb_common_db/hrb_common_cache - a service with no DB access still gets retry/circuit-breaker/logging for free.
