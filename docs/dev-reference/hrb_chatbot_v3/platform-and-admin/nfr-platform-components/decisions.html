NFR Components — Decisions

Why a shared library instead of a service mesh, why these defaults, and how success gets measured.

Overview Spec Architecture Design Decisions
1Why a shared library, not a service mesh
Istio/Linkerd-style sidecar mesh would give retry/circuit-breaking/mTLS for free at the infra layer - why not that? Real overkill for this scale: a service mesh needs a Kubernetes cluster (or at least a real container orchestrator) to sit in - this project runs on App Runner, one container per service, no orchestrator. Standing up EKS just to get a sidecar would cost far more in AWS bill and operational complexity than it saves, for a handful of low-traffic services. A library import gets 90% of the resiliency value for near-zero added infrastructure.
2Why circuit breaker defaults match Phase 185's, not new numbers
Why 2 failures / 10s cooldown, specifically? Those exact numbers are already running in production against hrb_lms_mcp (mcp_tools/__init__.py's MCP_CIRCUIT_BREAKER_FAILURE_THRESHOLD/MCP_CIRCUIT_BREAKER_COOLDOWN_SECONDS) and have real operational history behind them - reusing a number nobody's tuned feels careful; inventing a new untested one for every other service's first day in production doesn't. Corrected from an earlier, wrong "5 failures / 30s" in this doc - verified against the real code before writing the spec that follows.
