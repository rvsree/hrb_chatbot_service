Admin Secret Code

A one-time seed code, forced reset, and salted-hash verification - the one real credential check in a system where every other role is self-asserted.

Overview Spec Architecture Design Decisions

Purpose

Every other role in this system - employee, manager, hr_support - is self-asserted: the login form is checked against a known-personas roster, but nothing stops a caller from claiming any role on any later request. Admin is the one exception. Because the admin role gates real capabilities (deleting knowledge-base documents, viewing every employee's leave data, downloading the architecture deck), it's the one identity backed by an actual secret the caller has to prove they know - not just assert.

This feature is that one credential check: how the secret is seeded the first time, how it's verified on every login after, and how an admin changes it.

Scope

Covers the full lifecycle of the admin secret code: a one-time seed value used only the very first time no admin_credentials row exists for an employee_id, salted SHA-256 hashing with constant-time comparison (hmac.compare_digest, avoiding a timing side channel), a forced reset on first login (must_reset_secret_code), and a reset endpoint reachable only by an already-authenticated admin who proves the current code before setting a new one.

Does not cover real OAuth2/JWT session authentication - that's a separate, still-deferred project area (see this project's own BACKLOG.md). This feature closes one narrow, real gap (admin has a secret worth protecting) without pretending to solve the system's broader self-asserted-identity design.

High-level workflow

  1. 1First-ever login - no credential row exists yet; the one-time seed code is hashed and stored, and the login response flags must_reset_secret_code: true.
  2. 2Forced reset - the UI routes a must-reset login straight to the reset page before letting the admin do anything else.
  3. 3Reset - the admin proves the current code, then sets a new one; a fresh salt and hash are stored, must_reset clears.
  4. 4Every login after - the submitted code is hashed with the stored salt and compared in constant time against the stored hash.

Where this fits in the HR Benefits RAG system

This sits in front of every admin-only capability in the app - the Architecture Docs viewer this very page is part of, KB document management, leave-request administration, and the deck download all require passing this check first. It's deliberately narrow: this feature doesn't try to fix the system's documented "role is self-asserted" gap for every other role, only the one role where that gap would matter most.
