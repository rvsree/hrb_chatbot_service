Admin Secret Code

A lightweight extra verification step for the one role that can hard-delete data, layered on top of this project's documented "role is self-asserted" design - not a replacement for it. Pilot document for the Spec / Architecture / Design / Decisions model (Phase 179).

Spec Architecture Design Decisions
1
Intent why this exists, in one sentence

Every other role in this project is selected by the caller and trusted on the spot (documented RBAC-is-a-formality design, api/gateway/rbac.py). The admin role is the one exception worth a speed bump: it can hard-delete conversations, feedback, and leave requests outright. A masked secret-code field, checked server-side against a salted hash, makes picking "Admin" from a dropdown insufficient on its own - without pretending this is real authentication.

2
Scope what this feature covers, and what it deliberately doesn't
In scope
  • A secret_code field on login, read/checked only when role == "admin"
  • Salted-hash storage and constant-time verification
  • A one-time seed code that forces a reset on first use
  • A reset flow reachable only by an already-authenticated admin
Explicitly out of scope
  • Real authentication (OAuth2/JWT/session tokens) - a separate, larger, still-design-only project (docs/dev-reference/auth/oauth2-auth-architecture.html)
  • Multiple admin users / an admin user-management UI
  • Password complexity rules, lockout-after-N-attempts, or anything beyond the existing global Redis rate limiter
  • Changing what require_role() itself does - this only adds a pre-check in front of selecting the role, not a new enforcement mechanism
3
Personas who this feature is for
Admin One named persona today (ADM001, common/known_personas.py) - deliberately not a real hrb_emp_lms.employees row like every other persona, since admin operations never resolve identity through the MCP server the way an employee's own leave-balance lookup does. The project owner's own login, not a demo-able credential.
Everyone else Employee/manager/hr_support logins are entirely unaffected - secret_code is optional on LoginRequest and never read unless the selected role is admin.
4
Acceptance criteria what "done" means for this feature
Masked field, admin-onlymet

The login form's secret-code field renders only when the selected role is admin, as type="password" - never visible on screen during a live demo.

No plaintext storagemet

The code is never stored or compared as plaintext - only a salted SHA-256 hash, compared with hmac.compare_digest() (constant-time, avoids a timing side-channel).

One-time seed forces a resetmet

The very first admin login (no admin_credentials row yet) succeeds with the seed code but returns must_reset_secret_code: true - the seed can never silently become the permanent code.

Reset needs a valid session firstmet

POST /v1/admin/reset-secret-code requires both a valid admin user_profile and the correct current code - resetting isn't reachable from the unauthenticated login screen.

5
Open questions - and how they were actually resolved decisions get their own full doc; this is the short version
"Should this use OAuth2 or a JWT instead?" - No. OAuth2 solves delegated third-party authorization (not this problem - there's no third party here), and a JWT is a session-token format, which is a real but separate gap (this project's own documented "role is self-asserted on every request" limitation) - neither is a storage mechanism for the secret code itself. See Decisions for the full reasoning.
