api_gateway_service

The single public entry point for every browser request - session/state, RBAC, CORS, rate-limiting, and API contract validation, centralized once instead of duplicated across every backend service it fronts.

Overview Spec Architecture Design Decisions

Purpose

Today, hrb_chatbot_service handles RBAC (api/gateway/rbac.py), CORS (main.py's CORSMiddleware), and no rate-limiting worth the name, all inside the one service that also runs RAG retrieval. Once that splits into rag_ingestion_service/rag_retrieval_service, those cross-cutting concerns can't live inside either of them - the Gateway exists to own them once, for every backend service behind it, including ones that don't exist yet (chat_audio_service, employee_401k_service).

Scope

Covers the subset justified now, even with only one real backend to front today: identity validation (absorbing rbac.py's role), CORS (absorbing main.py's policy), rate-limiting (new - today's rate limiter is flagged broken at real scale), and request/response contract validation against each backend's declared schema.

Does not yet cover UI-data aggregation (combining multiple backends' responses into one shaped response for a specific page) - that's classic BFF behavior, and stays out of scope until there are enough real backend services to make aggregation worth it (journey 6/7 in the User Journey Capability Map, not journeys 1-5).

High-level workflow

  1. 1Request arrives from hrb_chatbot_ui over HTTPS.
  2. 2CORS + rate-limit checked first, cheapest rejection path.
  3. 3Identity validated - same contract as today's require_role(), still a self-asserted user_profile until real OAuth2 lands (see Decisions).
  4. 4Contract validated against the target backend's declared request shape before forwarding.
  5. 5Forwarded to the right backend service by path, response passed back unchanged (no aggregation yet).

Where this fits in the microservices rollout

Phase 1 - the first service actually built, after the Phase 0 prerequisites (NFR Components, Common-Libs Connectors, schema migration). Built additive: it fronts the still-undivided hrb_chatbot_service first, proving itself before rag_ingestion_service/rag_retrieval_service even exist as separate things to route between.
