api_gateway_service — Decisions

The rbac.py question, why identity stays self-asserted for now, and KPIs.

Overview Spec Architecture Design Decisions
1api/gateway/rbac.py - absorbed, not duplicated
hrb_chatbot_service already has a package literally named "gateway." Does this new service replace it or live alongside it? Absorbed. Once api_gateway_service is live, require_role()'s logic moves here and src/hrb_chatbot/api/gateway/ is deleted from the (now-split) backend repos - not kept as a second, now-redundant enforcement point. Two places checking the same role claim is how one of them silently goes stale.
2Identity stays self-asserted - deliberately not upgraded here
Building a real Gateway feels like the moment to finally add real OAuth2 human-to-app auth - why not do both at once? Scope discipline: this phase is "move RBAC/CORS/rate-limit to one place," not "also solve real authentication." hrb_chatbot_service_core's employee_roles/oauth_clients tables already exist as a placeholder design for exactly this, unwired - a legitimate next phase once the Gateway itself is proven, not bundled into its first version. Flagging this clearly rather than letting "build the Gateway" quietly become "and also fix auth," which is how one phase becomes three.
3No aggregation yet
Isn't a Gateway that doesn't aggregate just a reverse proxy? Correctly, yes - and that's fine. The value in v1 is centralizing security/contracts, not response-shaping. Aggregation gets added only once there are enough real backends behind it that combining their responses for a specific UI page is worth the complexity (see User Journey Capability Map, journeys 6-7).
