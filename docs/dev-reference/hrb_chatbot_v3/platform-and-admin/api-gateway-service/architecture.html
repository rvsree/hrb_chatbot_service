Internal components, the request-validation pipeline, and the real upstream/downstream picture.

1Upstream / downstream

Upstream (calls it): hrb_chatbot_ui only - this service has exactly one caller.

Downstream (it calls): today, hrb_chatbot_service (the undivided backend). After Phase 2: rag_ingestion_service, rag_retrieval_service. Later: chat_audio_service, employee_401k_service. Never calls hrb_lms_mcp directly - that stays a service-to-service call made by whichever backend needs it.

Each stage can short-circuit the rest - a CORS failure never reaches the rate limiter. Corrected 2026-10-24: this pipeline previously listed an "Identity / RBAC" stage here - verified directly against main.py and it does not exist. The catch-all route's only dependency is the rate limiter; rbac.py is a real file in this repo but is never wired into main.py, confirmed by that function's own comment: "a generic catch-all proxy has no per-path role mapping to enforce yet." Role enforcement happens downstream, per backend service, not at the Gateway.

3Sequence — a successful RAG retrieval request
  1. 1. Browser POSTs /v1/genai-rag-retrieval/query with user_profile in the body.
  2. 2. Gateway's CORS middleware confirms Origin: https://hrb-chatbot-ui.rvsree.dev.
  3. 3. Gateway checks Redis for this employee_id's rate-limit bucket (60/min, fails open if Redis is unreachable) - under threshold, proceeds.
  4. 4. Corrected 2026-10-24 - the Gateway does NOT validate user_profile.role itself; that check happens once the request reaches the backend service, via that service's own require_role(). This step previously claimed otherwise.
  5. 5. Gateway validates the body against RagQueryRequest's schema - real, but only for the 3 endpoints contracts.py names; every other path is a no-op here.
  6. 6. Gateway forwards to the backend named by BACKEND_SERVICE_URL (today: hrb_chatbot_service).
  7. 7. Response passes back through unchanged.

4Failure path — a downstream service is down

Steps 1-5 above happen identically. Step 6's forward call trips the Resiliency circuit breaker (NFR Components) after repeated connection failures - the Gateway returns a typed 503 with a code from error_codes.py, never a bare connection-refused stack trace. The breaker's cooldown (10s, same default as Phase 185 - corrected from an earlier, wrong "30s" in this doc) means the Gateway stops hammering a backend that's already down.
