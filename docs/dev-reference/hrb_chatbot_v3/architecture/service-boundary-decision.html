↳
Original framing, for the record: Classic BFF (data-shaping for one frontend) needs multiple backends to aggregate — that's why it was "defer." But Session/State, RBAC, CORS, rate-limiting, and contract validation are Gateway concerns, not aggregation — those are valid with just one backend behind it. Splitting the name in two: api_gateway_service (promoted, build this sooner) handles the cross-cutting concerns now; the aggregation half stays conditional until rag_ingestion/rag_retrieval/hrb_lms_mcp/chat_audio/employee_401k are all real separate services worth combining for the UI.
✓ Decouples backend services

Backend services stop each owning CORS/RBAC/rate-limit code — they focus on business logic. Each one can lock its own CORS down to only accept traffic from the Gateway, not the public internet.

✓ Statefulness — resolved as recommended

Rate-limit state lives in Redis, not the Gateway's own memory — confirmed via its real Phase 1 build.

api_gateway_service's own Phase 2 absorbed api/gateway/rbac.py's role rather than coexisting with it — one RBAC mechanism, not two.

5How far does this scale? — packages/schemas are necessary, not sufficient

✓ Package/schema growth

A modular monolith holds up to roughly 8–12 cleanly-bounded packages before shared deploy/shared CI starts to hurt. Dozens of Postgres schemas in one database is a non-issue — Neon doesn't care about schema count.

✗ Real bottleneck: connections

Each stateless replica keeps its own pool — replica count × pool size can exhaust Neon's max connections before 1000s of users arrive. Needs PgBouncer/pooling, not a package change.

✗ Real bottleneck: LLM rate limits

Provider concurrent-request caps (OpenAI etc.) hit first, long before app-server or DB scaling matters — independent of how code is packaged.

✗ Real bottleneck: Redis

Already flagged not-live in production. At real concurrency the rate limiter and answer cache need it for real, not as a nice-to-have.

Net: clean up the boundaries because it's good engineering and keeps future splits cheap — but don't expect it alone to unlock 1000s-of-users scale. Those three bottlenecks are a separate, already-identified body of work (NFR/Resilience doc).

7Remaining blind spots — not yet decided, flagging rather than guessing

⚠
  • Schema/service name pairing: rag_retrieval_service pairs cleanly with schema rag_retrieval now — confirm you're OK with "retrieval" over "search" project-wide.
  • "_service" suffix isn't applied consistently: new names get it (rag_ingestion_service), existing ones don't (hrb_chatbot_ui, hrb_lms_mcp) — decide: grandfather the old names, or rename those too.
