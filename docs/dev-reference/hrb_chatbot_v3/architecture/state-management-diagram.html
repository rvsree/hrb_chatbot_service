Redis-backed state

Every Redis-backed mechanism in this service shares one reason for existing: App Runner auto-scales to multiple instances, so anything that needs to be shared across instances can't live in process memory (Phase 84's own lesson, restated in Phase 259's circuit breaker design).

Conversation STM/LTM splitRedis

Short-term (recent turns, short TTL) vs long-term (older turns, longer TTL) conversation memory tiers, assembled into the prompt by the Search Pre-Processing Layer's assemble_context(). Pre-existing (Phase 247), unchanged this session.

ai/rag_core/guarded_pipeline.py (load/save) · ai/search_pre_processing/context_assembly.py

Rate limiter countersRedis

Per-identity request counters with a sliding window, shared across instances for the same reason the circuit breaker below is. Pre-existing (Phase 84).

common/clients/rate_limiter.py

Circuit breaker fail/open stateRedisNew

Two key families per breaker name: circuitbreaker:fail:<name> (consecutive-failure counter) and circuitbreaker:open:<name> (cooldown marker). One breaker each for llm:openai / llm:anthropic. Sync Redis client, not async - the whole ask() call chain it wraps is synchronous.

common/resiliency/circuit_breaker.py

Dynamic-config read path - the pattern Phase 260 generalized

Three independent mechanisms now read their own tunable from app_settings on every call, each falling back independently if that read itself fails:

app_settings.get_setting(key, fallback)
        |
        |-- judge_provider_default -----> golden_dataset_harness.py's 5 judge functions
        |                                  (OpenAI default; "anthropic" routes through
        |                                   anthropic_chat().ask() instead)
        |
        |-- react_loop_max_iterations --> orchestration_agent.py's ReAct loop cap
        |                                  (falls back to DEFAULT_MAX_ITERATIONS = 5)
        |
        `-- llm_{openai,anthropic}_circuit_breaker_{failure_threshold,cooldown_seconds}
                                       --> CircuitBreaker._resolve_failure_threshold() /
                                           _resolve_cooldown_seconds() (own try/except each -
                                           a Postgres hiccup here must never skip recording
                                           the real Redis failure, only fall back to the
                                           constructor-time value)

All 7 keys are editable live from hrb_chatbot_ui's new Settings page (Model / Memory / Resiliency sub-tabs) - see hrb_chatbot_ui's own ROADMAP.md, Phase 1.

Fallback order - same 3-level shape, every dynamic setting

LevelSourceWhen it's used
1app_settings (Postgres)Normal case - the value a human last set via the Settings UI, or never set (store returns the default passed in)
2Constructor-time valueapp_settings read itself raised - env var override, or a hardcoded default, resolved once when the object was built
3Hardcoded defaultEnv var also unset - the literal fallback in code (e.g. failure_threshold=2, cooldown_seconds=10)
