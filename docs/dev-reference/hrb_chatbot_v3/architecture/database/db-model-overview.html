No FK - deliberate. A cross-schema DB-enforced FK is real coupling between two services; a plain value + application-level JOIN keeps them independent. Live: EMP051/EMP052/MGR006 assigned real roles, looked up via subquery, not FK-guaranteed.

client_scopes
id (PK)client_id (matches oauth_clients.id)scope (e.g. mcp:get_leave_balance)
Schema and data are real and live (verified this session) - the OAuth2 token-issuing code (/oauth/token, JWT signing) is still design only. Data exists ahead of the code that would use it, on purpose.
No DB-enforced foreign keys anywhere in this schema - a deliberate choice, made and applied live. A cross-schema FK (employee_roles -> hrb_emp_lms.employees) is real coupling between two independently-owned services - the exact anti-pattern "shared database" designs get criticized for. Referential lookups still work via a plain application-level JOIN; integrity just isn't DB-enforced. Right call for a capstone project, not necessarily for a production one with a real data-integrity SLA.
