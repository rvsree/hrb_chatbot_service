2Common-libs, regrouped — your existing common/clients/ folders already are the right grouping

✓
Checked the real code before designing this: common/clients/ already has 9 separate folders — auth_client, cache_client, ci_client, db_client, email_client, llm_client, mcp_client, storage_client, web_client. That's already the correct grouping. The one earlier mistake was proposing one monolithic hrb_common_libs — it should be ~10 small, independently-installable packages (these 9 plus a new observability one), each a repo folder or its own tiny repo, not one grab-bag.
⚠
Real divergence, 2026-10-23: it shipped as this doc's own earlier mistake, not its correction — one repo, hrb-common-libs, with the 10 areas as pip extras (hrb-common-libs[observability,db,cache,llm,mcp,auth,vectorstore,web,storage,email]) rather than 10 independently-installable packages. Each service's own requirements.txt still only requests the extras it actually needs, so the practical effect (no service pulling in a dependency it doesn't use) is the same either way — but it's one git-tag-pinned repo/version (currently v0.4.0) for everyone, not independently-versioned packages.

3Per-service NFR callouts — security, scalability, resiliency differ by service, not one list for all

api_gateway_service
Security — its whole job: RBAC, CORS, rate-limit, token validation
Scalability — must stay stateless; session state in Redis/Postgres, never in-process
Resiliency — single entry point = single point of failure risk; needs ≥2 replicas from day one
rag_ingestion_service
Security — validate uploaded file type/size before S3 write
Scalability — bursty, admin-triggered; Lambda-shaped, scale-to-zero fits
Resiliency — idempotent re-ingestion already built (content-hash dedup)
rag_retrieval_service
Security — prompt-injection guardrails already built
Scalability — the real 1000s-of-users path; needs connection pooling (§4, rollout-plan)
Resiliency — LLM timeout/retry, MCP circuit breaker already built (Phase 185)
hrb_lms_mcp
Security — OAuth2 client-credentials, Bearer validation, already live
Scalability — low traffic, server-to-server only
Resiliency — caller-side circuit breaker already built
chat_audio_service / employee_401k_service
Security — TBD
Scalability — TBD
Resiliency — TBD — none of this gets guessed; it's part of each one's own HLD before build starts

4HLD/LLD documentation template — the structure every service's docs must satisfy, not pre-written content

HLD must cover
  • Context diagram — this service's row from §1's matrix, drawn
  • Component diagram — internal modules (e.g. rag_retrieval's retrieval/generation/agents/Support sub-packages)
  • High-level data flow — one diagram per key use case
  • NFR summary — this service's own security/scalability/resiliency bullets (§3)
LLD must cover
  • Sequence diagram(s) — for its 1-2 key flows, real components named
  • DB schema detail — tables/columns, this service's schema only
  • API contract — request/response shapes (if any)
  • Deployment diagram — container, env vars, scaling config
  • requirements.txt rationale — each dependency tied to a §2 common-lib package or a direct need
  • .env / .env.example — only what this service reads, nothing copied from another's
  • Failure-mode table — what breaks, what the service returns

Extends the existing docs/dev-reference/<feature>/ Overview/Spec/Design/Decisions tabs — Overview+Architecture stand in for HLD, Spec+Design for LLD. No content gets pre-written for a service that doesn't exist yet; the template is what's ready now, filled in as each service is actually built.

5Platform components — resolved 2026-10-23: the alternative was chosen, not the recommendation

⚠
Real outcome: platform_interview_qa and platform_build_deployment (plus platform_admin_controls-shaped features) did not stay co-located inside rag_retrieval_service's deployable as this section recommended — they became their own fully separate service, hrb_platform_components, built and deployed independently (its own ECR repo, App Runner service, CI/CD). The "stronger isolation" alternative this section offered as a fallback is the one that actually happened, AWS-cost tradeoff accepted. One known gap, flagged not fixed: 3 admin routes (admin-docs-sync-to-S3, request-metrics, FAQ submissions) still have no confirmed home in either hrb_platform_components or rag_retrieval_service.
↳
Original recommendation, for the record: stay co-located inside rag_retrieval_service's deployable (low-traffic admin features, no case for their own App Runner cost) — but get their own HLD/LLD doc pair (§4's template) and their own distinct step in the rollout sequence, not folded silently into "build rag_retrieval_service."
