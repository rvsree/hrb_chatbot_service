RAG Ingestion

PDF text extraction, 6 selectable chunking strategies, embedding, and the vector-store write - the pipeline that turns one uploaded document into searchable, indexed chunks before any retrieval mode can find it.

Overview Spec Architecture Design Decisions Interview FAQ

Purpose

Every retrieval mode (GenAI RAG Chat, Single-Agentic RAG, Multi-Agentic RAG) reads from the same vector index - this pipeline is what writes it. One call (ai/doc_processing/pipeline.py::index_document()) does extract -> chunk -> embed -> index, synchronously, in-request, driven by POST /v1/genai-rag/ingest-document/documents.

Scope

Covers PDF text extraction (pypdf + a separate table extractor, tables kept out of chunking entirely and appended as whole chunks), 6 chunking strategies (fixed, recursive, semantic, markdown, html, none, plus a 7th explicit-only document_structure strategy) behind one CHUNKING_STRATEGIES dict with auto-selection when no strategy is named, embedding generation, and the vector-store write itself (LlamaIndex's VectorStoreIndex, Phase 44). Also covers content-hash deduplication (identical bytes never create a second document) and the supersedes/is_current model for one document replacing another.

Does not cover what happens to a chunk once it's searchable (that's Retrieval Strategies), or how a search result gets reranked/turned into an answer (that's each retrieval mode's own generation step).

High-level workflow

  1. 1Dedup check - a content-hash match against an existing document short-circuits the whole pipeline; no new document, no re-indexing.
  2. 2Extract - PDF text + tables pulled out separately (extract_text_from_pdf()), tables appended as [TABLE]...[/TABLE] markers so a table is never split mid-chunk.
  3. 3Chunk - the named (or auto-selected) strategy splits the table-free text; tables rejoin afterward as their own whole chunks.
  4. 4Embed - one embedding call per chunk batch (generate_embeddings()), computed once here, not inside the indexing write itself.
  5. 5Index - chunks + embeddings written into the active vector store (Chroma/Pinecone) via LlamaIndex's VectorStoreIndex; a re-index deletes the document's old chunk ids first, insert-only otherwise.
  6. 6Metadata - document-level metadata (category/department/description) is extracted and patched onto the just-written chunks, first index only.

Where this fits in the HR Benefits RAG system

This writes the index every retrieval mode later reads from through the shared Retrieval Strategies layer. Gateway-restricted to HR_SUPPORT only - employees/managers never call this directly. Status progresses through parsing -> chunking -> embedding -> indexing -> indexed, each stage written to the document's own metadata row so a stalled/failed upload is diagnosable mid-pipeline, not just pass/fail.
