architecture - request lifecycle, by stage

RAG Ingestion

One synchronous HTTP request, 6 stages, each tracked by its own status field on the document's own metadata row - a stalled upload is diagnosable mid-pipeline, not just pass/fail. Kept deliberately text/table-based, not a diagram - see Decisions on why a per-feature diagram wasn't duplicated here.

Overview Spec Architecture Design Decisions
APIlive

POST /v1/genai-rag/ingest-document/documents - gateway-restricted to HR_SUPPORT only, at the app.include_router(...) level (Phase 23), not a per-route check.

Dedup checklive

Content-hash lookup against every existing document, before any file is even written to disk. A match returns the existing document's id with status: "duplicate" - every later stage is skipped entirely.

Extract (parsing)live

pypdf reads every page's text; a separate table extractor pulls out tables as their own markdown blocks, appended after the page text. Status flips to parsing on the document's metadata row.

Chunk (chunking)live

Tables are pulled back out before any of the 7 chunking strategies run (named explicitly, or auto-selected), then rejoined afterward as whole chunks. Status: chunking.

Embed (embedding)live

One batch embedding call for the whole chunk set (OpenAI by default) - computed once here, passed directly into the indexing write, never recomputed. Status: embedding.

Index (indexing → indexed)live

Chunks + embeddings written via LlamaIndex's VectorStoreIndex into the active vector store (Chroma or Pinecone, same gateway/enum pattern every backend choice in this project uses). A re-index deletes the document's old chunk ids first (insert-only API). First index only: old supersedes target flipped to is_current: false, and extracted document metadata (category/department/description) patched onto the just-written chunks. Status ends at indexed.

Where this sits relative to the rest of the platform

This is the write path into the same index every retrieval mode (GenAI RAG Chat, Single-Agentic RAG, Multi-Agentic RAG) reads from through the shared Retrieval Strategies layer. It's also the one capability in this platform with a genuinely different traffic shape - bursty, write-heavy, triggered by HR uploading a document, not by a chat request - which is why the platform hub page tracks it as its own capability row rather than folding it into "Benefits Q&A."
