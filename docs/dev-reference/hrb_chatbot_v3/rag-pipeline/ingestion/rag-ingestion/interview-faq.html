Chunking Strategy4 cards
Why does chunk size/overlap matter, and how do you pick a starting point?
  • Too small loses context (a sentence makes no sense alone); too large dilutes the embedding (one vector now represents several ideas, matching none of them precisely) and wastes prompt budget. Overlap exists so a sentence split at a chunk boundary still appears whole in at least one chunk. Start around 500-1000 characters with ~15% overlap, then tune against real queries.
built1000-char default, 150-char overlap (DEFAULT_CHUNK_SIZE/DEFAULT_CHUNK_OVERLAP) - overlap is roughly a sentence, chosen so a boundary-split sentence still appears whole somewhere, not tuned against a held-out query set.
Fixed-size vs. semantic vs. structure-aware chunking - what's the real tradeoff?
  • Fixed-size is fast and predictable but blind to meaning - can cut a sentence or table row in half. Semantic chunking (embed each sentence, split where meaning shifts) respects topic boundaries but costs one embedding call per sentence. Structure-aware (split on real headings) is the cheapest "respects meaning" option when the source document actually has consistent structure.
builtAll 3 exist as real, independent functions in the same CHUNKING_STRATEGIES dict - fixed/recursive (fixed-size family), semantic (one OpenAI embedding call per sentence via LangChain's SemanticChunker), document_structure (this project's own "Section N:"/"N.N Subtitle" heading parser, Phase 124).
How should chunking strategy be chosen automatically, when a caller doesn't specify one?
  • Inspect the document's own structure first (does it have real markdown/HTML headings?), fall back to document length (short enough to skip splitting entirely, or long enough that a general-purpose splitter is the safe default), and keep the decision deterministic and logged - never a silent guess.
builtdecide_chunking_strategy() - markdown headings found -> markdown; HTML heading tags -> html; at/under a length threshold -> none; otherwise -> recursive. Every decision is logged with its rationale. Two strategies are deliberately explicit-only, never auto-selected: semantic (cost) and document_structure (would fire on every real KB document today, risking a silent golden-dataset score shift on a routine re-index).
A table in the source PDF keeps getting mangled across two chunks - how do you fix that?
  • Detect and extract tables before running any text splitter, keep each table as its own atomic unit, and reinsert it after chunking rather than letting a generic splitter's size/boundary logic ever see it.
builtPhase 75 - a separate table extractor pulls every table out before any of the 7 chunking strategies run (marked with [TABLE]...[/TABLE]), and each table becomes its own whole chunk afterward, regardless of strategy or chunk size.
Dedup, Versioning & the Write Path3 cards
How do you stop the same document from being ingested twice?
  • Hash the raw content and check that hash against every existing document before anything else runs - filename isn't a reliable signal (same name, different content is common; different name, same content should still be caught).
builtContent-hash dedup, checked first, before extraction/chunking/embedding ever run - a match short-circuits the whole pipeline and returns the existing document's id.
A policy document gets replaced with a new version - how do you make sure search never serves the old one, and there's no window where neither is live?
  • Write the new version's chunks first, confirm the write succeeded, then flip the old version's chunks to not-current - never delete-then-write, which would leave a gap where search returns nothing for that content.
builtsupersedes_document_id + is_current metadata flag - the old document's chunks are only marked is_current: false after the new document's first index succeeds, and only once (never repeated on a later re-index of the new document).
Why index straight into LlamaIndex's VectorStoreIndex instead of LangChain's own indexing API, if the project otherwise prefers LangChain for retrieval?
  • Not every stage of a RAG pipeline has to use the same library - a reasonable team picks the right tool per stage and documents why, rather than forcing one library's abstraction over a process it doesn't fit as well.
differentReal history, not a one-off choice: Phase 3 used LlamaIndex, Phase 17 moved to LangChain's index()/SQLRecordManager for its real skip-if-unchanged/cleanup behavior, Phase 44 reverted back to LlamaIndex per the user's own standing course-fidelity preference. See Decisions (RI-1) for the full trade-off - this project's own is_current/supersedes model now covers what LangChain's index() would have handled natively.
