RI-1LlamaIndex's VectorStoreIndex for the actual write, after a LangChain detour and back
Context
Indexing originally used LlamaIndex (Phase 3, this project's first implementation). Phase 17 moved it onto LangChain's own index() + SQLRecordManager for real skip-if-unchanged + cleanup semantics. That move was never actually settled - the user's standing preference, restated after Phase 17 shipped, was the course's own LlamaIndex-based approach.
Decision
Phase 44 reverted indexing back onto LlamaIndex's VectorStoreIndex - confirmed as the current, live state directly from vector_indexer.py's own imports and docstring (from llama_index.core import VectorStoreIndex), not assumed from an older design note.
Alternative
Stay on LangChain's index()/SQLRecordManager - genuinely gives skip-if-unchanged + cleanup for free, a real capability LlamaIndex's own insert-only API doesn't have natively (this project's is_current/supersedes model is hand-built to cover that gap instead).
Why
Course-ware fidelity was the deciding factor, not a technical regression - the user's own standing preference, not re-litigated here.
Trade-off
LlamaIndex's insert_nodes() is insert-only, so a re-index deletes the document's old chunk ids first (a real two-step, not an atomic upsert) - a genuine gap LangChain's own index() would have closed for free.
Documentation drift found while writing this doc set: CLAUDE.md's own "Three different libraries" section still describes Indexing as LangChain's index()/SQLRecordManager - that's the pre-Phase-44 state. CLAUDE.md's own separate paragraph above that section (the "Indexing moved off LlamaIndex onto LangChain in Phase 17... Phase 44 is reverting" note) already has the correct, current history; only the later bullet-list summary is stale. Flagged here, not edited - CLAUDE.md is this project's core instruction file and a correction there is for the user's own review, not a documentation-sweep side effect.
RI-2Content-hash dedup instead of filename-based dedup
Context
An early version of this pipeline would re-index a file with the same name as a no-op overwrite or a silent duplicate, depending on timing - a real bug, not a hypothetical (Phase 16, CLAUDE.md's own cited example for why the SDD spec-gate exists at all).
Decision
SHA-based compute_content_hash() over the raw uploaded bytes, checked against every existing document before anything else runs. Same bytes, any filename, any time - treated as the same document.
Alternative
Filename + size as a cheaper proxy for "same file" - rejected because two genuinely different documents can share a filename (common with policy-doc revisions saved under the same name), and a renamed-but-identical file would wrongly be treated as new.
Why
Byte-identical content is the only signal that's unambiguous regardless of how the file arrived or what it was called.
Trade-off
A single-byte change (even an invisible one, like a re-saved PDF with different internal metadata but identical visible text) is treated as a wholly new document, not an update - there's no "mostly the same" middle ground, only exact-match dedup or a full re-index.
RI-3Qdrant - planned, not built
Context
Today's vector store choice is a 2-way gateway/enum pattern: Chroma (local, file-based) or Pinecone (managed, remote) - both already wired through VectorDB and this project's own gateway/client pattern.
Decision
No Qdrant client, gateway entry, or enum value exists anywhere in the current codebase - confirmed by reading common/enums.py's VectorDB and common/clients/db_client/ directly, not assumed from the user's own stated intent to add it.
Alternative
N/A - this is a documentation-honesty note, not a design alternatives comparison. The real alternatives analysis belongs to whichever phase actually adds Qdrant.
Why
Flagged here so this doc set doesn't claim or imply Qdrant support exists before it does - the user named it as a near-term direction while this document sweep was in progress.
Trade-off
When Qdrant is added, it should slot into the exact same VectorDB enum + gateway pattern Chroma/Pinecone already use - a 3rd case in an existing dict, not a parallel mechanism - consistent with this project's own "backend abstraction: gateways + enums, not scattered if/elif" convention.
