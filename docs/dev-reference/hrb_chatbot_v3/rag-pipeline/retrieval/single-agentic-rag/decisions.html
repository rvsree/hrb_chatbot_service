SA-1ChatOpenAI directly, not the shared GatewayChatModel adapter
Context
This project has a GatewayChatModel adapter (common/clients/llm_client/langchain_chat_model.py) wrapping its own multi-provider ask() clients for LangChain's own retrieval classes (MultiQueryRetriever/SelfQueryRetriever). This agent could have used it too.
Decision
Uses langchain_openai.ChatOpenAI directly instead, per the module's own docstring note pointing at Phase 55.
Alternative
Route through GatewayChatModel for provider-agnostic tool-calling, consistent with the retrieval classes - would mean every ask_with_tools()-style call going through one more adapter layer.
Why
Not independently re-verified in this pass - recorded from the module's own docstring pointer, not re-derived. Flagged rather than guessed at further.
Trade-off
This agent is tied to OpenAI's own tool-calling API shape specifically, not provider-agnostic the way the gateway-routed retrieval classes are - a real, acknowledged inconsistency across the codebase's own LLM-access patterns.
SA-2A live-data-tool exclusion set, not "any tool use disables caching"
Context
An agentic answer could have used zero, one, or several tools - a blanket "never cache if any tool was used" rule would also exclude SearchKnowledgeBase-only answers, which are exactly as cacheable as genai-rag's own.
Decision
LIVE_DATA_TOOLS = {"GetLeaveBalance", "GetLeaveHistory"} - caching is disabled only when one of these two specific tools appears in tools_used, not for any tool use at all.
Alternative
Blanket "no caching if any tool ran" - simpler, one condition instead of a set membership check - rejected: would silently lose caching for the (likely common) case of a knowledge-base-only agentic answer.
Why
The real risk is per-employee, time-sensitive data (a balance, a history) - not tool use itself. A precise exclusion set captures exactly that risk, no more.
Trade-off
The exclusion set has to be manually kept in sync with the real tool list - a new live-data tool added later that isn't added to LIVE_DATA_TOOLS would silently become cacheable. No test currently enforces this stays in sync.
