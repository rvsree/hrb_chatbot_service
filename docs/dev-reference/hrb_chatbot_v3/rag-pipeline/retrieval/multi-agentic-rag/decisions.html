MA-1Guardrails still called directly, not migrated to the Phase 98 shared core
Context
Phase 98 built a shared run_guarded_pipeline() core specifically because single-agentic-rag once shipped with no guardrails at all. All 3 modes were meant to funnel through it.
Decision
genai-rag and single-agentic-rag both route through the shared core; multi-agentic-rag still calls check_input/check_output directly, its own earlier (and still-correct) implementation.
Alternative
Migrate this mode to the shared core in the same phase - not done; left as a known, explicitly-scoped-out follow-up rather than silently drifting.
Why
Not independently re-derived this round - recorded directly from this project's own CLAUDE.md context, which states this as a deliberate, acknowledged gap, not an oversight.
Trade-off
Two different guardrail-wiring patterns exist side by side in the same codebase - a real inconsistency a future phase needs to close, not a correctness bug today (the guardrails themselves still run, just via a different code path).
MA-2Hierarchical/supervisor LangGraph pattern over independent parallel agents
Context
A multi-agent system can be structured several ways - independent agents each answering separately then merged, a flat round-robin, or a supervisor/planner pattern.
Decision
Hierarchical/LangGraph-supervisor: a Planner node decides dispatch, domain agents run as conditional graph branches, a Reviewer node gates the final output - per the module's own docstring, "per the user's [direction]."
Alternative
A flatter fan-out-to-all-agents-always pattern - simpler routing logic, but wastes real LLM calls on agents irrelevant to a given query (e.g. running web_search_agent on a pure internal-policy question).
Why
Conditional dispatch means only the agents a query actually needs run at all - directly cheaper and faster than an always-fan-out design, at the cost of needing a real Planner step to get routing right.
Trade-off
The Planner's own routing decision is itself an LLM call that can be wrong - a misrouted query either runs an irrelevant agent (wasted cost) or skips a relevant one (an incomplete answer), a failure mode the simpler always-fan-out design wouldn't have.
MA-3The Reviewer node is a merge/synthesis step, not a Critic
Context
The Planner-Executor-Critic pattern (domain agents = executors, Reviewer = critic) implies the final node judges the executors' work and can reject or send it back. reviewer_agent.py's own docstring already calls it "multi-agentic-rag's merge step."
Decision
review() (reviewer_agent.py:23-68) always combines every domain agent's result into one final answer via a single LLM call - there is no accept/retry/reject verdict, no quality score, and nothing it can send back to a domain agent or the Planner. It runs unconditionally, even for a single agent result, because a domain agent's raw output isn't presentable on its own.
Alternative
A real critic step that can reject a domain agent's result and trigger a retry or replan - not built. The graph (multi_agent_pipeline.py:179-194) has no edge back from reviewer to any domain agent or to planner; every domain agent always flows straight to reviewer, which always flows to END.
Why
Following the course's Travel Planner reference notebook's own synthesizer_node() pattern (cited directly in the module docstring) - that reference implementation merges, it doesn't critique either.
Trade-off
A domain agent that fails or returns a wrong/empty result still gets merged into the final answer by the LLM as best it can, rather than being caught and retried. See MA-4 for the related failure-handling gap this leaves open.
MA-4No retry/replan/fail-fast policy for a failed domain agent
Context
A domain agent can fail (e.g. lms_ops_agent.py:10-11 returns "Error: no employee ID available for this request." instead of raising, when it's dispatched without one). Interview-prep material frames this as a design choice between retry, degrade, replan, and fail-fast per step.
Decision
None of the four is implemented at the graph level. A failing domain agent returns its own error string inside the normal agent_results shape; the graph (multi_agent_pipeline.py:190-193) routes it straight to reviewer exactly like a success. The only place this is visible downstream is tools_used[].success, computed post-hoc by checking whether the result text starts with "Error:" (line 283) - informational only, not acted on.
Alternative
A conditional edge after each domain agent node that retries on a transient failure, replans when a task was misrouted, or fails the whole run fast for a critical step - none built; every path is effectively "degrade and continue," the one option the interview-prep material calls safe only for non-critical steps.
Why
Not independently re-derived - this is the real behavior found by tracing the code, not a decision recorded elsewhere at the time it was built. Flagging it here closes the documentation gap; it does not mean the gap in the behavior itself is closed.
Trade-off
A single misrouted or failing domain agent degrades answer quality silently rather than being retried, replanned, or surfaced as a partial result - acceptable for a capstone project's current traffic, worth a real policy before this pattern sees production load from more agents.
MA-5Planner output has no depends_on or success_criteria fields
Context
A typical Planner-Executor-Critic design gives each planned step an ID, inputs that can reference an earlier step's output, a depends_on list for ordering, and success_criteria a critic checks against.
Decision
PlannerOutput (planner_agent.py:23-29) is just {tasks: [{agent, focus}]} - a flat classification list, no dependency graph, no success criteria. This matches the real shape of the problem: all dispatched domain agents run in parallel via Send() (dispatch_to_agents(), line 90-96), with no step ever depending on another step's output.
Alternative
The fuller schema (IDs, depends_on, success_criteria) - not needed today because this graph has exactly 2 levels (dispatch, then merge), not a multi-step sequential plan. Adding those fields now would be speculative, not load-bearing.
Why
The Planner's one real job today is classification/routing (which agents, what focus for each), not sequencing - a narrower, genuinely simpler problem than the general pattern, built to match.
Trade-off
If a future query genuinely needs one domain agent's output before another can run (a real multi-hop case), today's flat PlannerOutput can't express that - it would need a real schema change, not just a bigger prompt.
