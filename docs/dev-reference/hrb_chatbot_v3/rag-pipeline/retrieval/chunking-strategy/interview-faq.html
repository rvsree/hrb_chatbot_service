Why split documents into chunks at all?
  • A whole document is too big for one prompt, and one embedding for a 50-page document is too blurry to match a specific question well. Smaller pieces give precise matches and send only the relevant part - the real trade-off is too small loses context, too big loses precision.
builtTable-aware chunk sizing via decide_chunk_size() (Phase 37) picks the trade-off automatically per document rather than using one fixed size everywhere.
Fixed-size vs. semantic chunking - what's the real difference?
  • Fixed-size splits every N tokens regardless of content - simple, fast, can cut a sentence or table in half. Semantic chunking splits at natural boundaries (headings, topic changes) - stays meaningful, costs more to build. Splitting on headings is usually the best value for effort on real documents.
builtBoth exist as real, selectable strategies - chunk_fixed() and chunk_semantic() in CHUNKING_STRATEGIES, plus chunk_recursive() (LangChain's own recursive splitter) as the auto-selected default when neither is explicitly requested.
What is chunk overlap, and why use it?
  • Each chunk repeats the tail of the previous one (typically 10-20%) so a sentence sitting right on a split point doesn't get lost to either chunk. Cost: the index gets bigger from storing some text twice - helps answers spanning two chunks, not five.
builtReal overlap parameter on the fixed/recursive splitters, sized together with chunk size by decide_chunk_size(), not a separate hardcoded constant.
Write a chunker for markdown docs that respects headings.
  • Split on heading lines; keep a section as one chunk if it fits the limit, otherwise split it with fixed-size + overlap inside that section only - never split across a heading. Add the heading path to the top of each chunk (e.g. "Setup > Authentication") so a retrieved chunk is understandable on its own.
builtchunk_markdown() / chunk_html() - LangChain's own header-aware splitters, matching this shape; real document structure (headings/tables/lists) is preserved via a separate document_structure strategy too, for ingestion sources that need it.
What is parent-document retrieval, and is it worth building?
  • Search using small chunks (precise matches) but send the model the larger parent section they came from (enough context) - each small chunk stores a pointer back to its parent, fetched on a match. Cost: the prompt gets bigger, so it's a real token-budget trade-off, not free.
noneNot built - confirmed via a direct course-topic-coverage check this project ran. Chunk size is tuned per-document instead (decide_chunk_size()) as the simpler lever for the same underlying precision-vs-context trade-off.
Your corpus has the same policy in 5 slightly different versions - what goes wrong, and how do you fix it?
  • Near-duplicates fill the top results with one fact repeated 5 times, pushing out genuinely different chunks, and if the versions disagree the model has no way to know which is current. Fixes: detect near-duplicates at ingestion and keep only the canonical version, use MMR to reward chunks that add something new, and store an effective_date to filter to the current version by default.
differentThis project's real fix is upstream, at the document level, not the chunk level: content-hash dedup on upload plus an explicit is_current/supersedes model (Phase 16/44) - a newer upload of the same policy supersedes the old one outright rather than both coexisting for MMR to sort out at query time. No MMR-based near-duplicate detection exists at the chunk level specifically.
Someone says long-context models make RAG unnecessary - what's your answer?
  • Works for small document sets, breaks down at real scale - you pay for every input token on every request, longer prompts take longer, and models miss facts buried in the middle of very long context. You still need per-user filtering, which means selecting documents anyway. Fair point though: a bigger context window does mean chunking can afford to be less perfectly precise.
noneNot a live concern - this project chunks and retrieves selectively by design (top_k-bounded), never considered dumping a whole knowledge base into one prompt.
