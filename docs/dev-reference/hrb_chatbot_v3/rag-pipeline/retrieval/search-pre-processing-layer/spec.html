Search Pre-Processing Layer — Spec

Requirements, personas, acceptance criteria, constraints.

Overview Spec Architecture Design Decisions
1Personas

Employee/Manager/HR Support - never see this layer directly; it should make their answers faster (cache hits) and more consistently routed (no more manually guessing Reflex vs. Agentic Workflow). A future service builder - once the split happens, this is the one file/package in rag_retrieval_service that owns "what do we know before we start answering."

2Functional requirements
  • MUSTCheck CAG (exact-match answer cache) before any pipeline runs, for cacheable modes only (never for a request that could depend on live tool data).
  • MUSTOn a cache miss, classify the query and route to Reflex Agent or Agentic Workflow per Phase 240's contract (resolved_mode in the response).
  • MUSTAssemble STM (this conversation's recent turns) before handoff - the chosen pipeline must not have to re-fetch it itself.
  • SHOULDSurface the most recent feedback signal (if any) on this conversation as part of the assembled context - available to a future routing refinement (escalate-on-negative-feedback), not acted on automatically in this first version.
  • SHOULDFall back to Postgres (full history) when Redis (STM cache) misses or is unavailable - never fail the request because the cache layer had a problem.
3Non-functional requirements
  • Added latency: context assembly (STM fetch) should add single-digit ms on a cache hit - it's an in-memory lookup, not a classification LLM call.
  • Failure isolation: a Redis outage degrades to Postgres-only (slower STM reads, no data loss) - never a 500.
4Acceptance criteria
  • A repeated identical query (same user, same question) within the cache TTL returns the cached answer with no pipeline invocation at all.
  • A genuinely new, simple question resolves to Reflex Agent; a multi-domain question resolves to Agentic Workflow - both observable via resolved_mode in the response and the Explainability modal's Retrieval Strategy tab.
  • Stopping Redis entirely does not break a conversation - STM falls back to a direct Postgres read of the same conversation's recent turns.
5Constraints
  • No new business logic duplicated from the pipelines themselves - this layer decides and assembles, it doesn't generate answers.
  • Depends on the existing Redis instance (answer cache/embedding cache already use it) - no new infrastructure.
  • True cross-conversation long-term memory (recalling facts from a different conversation) is explicitly out of scope - see Decisions.
