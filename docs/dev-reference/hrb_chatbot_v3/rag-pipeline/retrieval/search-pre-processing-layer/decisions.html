Search Pre-Processing Layer — Decisions

Why cache-aside STM, why not real cross-conversation memory yet, KPIs.

Overview Spec Architecture Design Decisions
1Cache-aside STM, not Redis-only
Why not just move conversation history to Redis entirely? Postgres stays the durable system of record - Redis is a performance cache on top, not a replacement. A Redis flush/restart must never lose a real conversation; it should only make the next read briefly slower (falls back to Postgres) while the cache rebuilds.
2True cross-conversation LTM - deliberately not this phase
Isn't "LTM" supposed to mean remembering facts across different conversations, not just one? Correct, and worth being precise about: what this design calls "LTM" is really "durable history of this conversation" (Postgres, already real). Actual cross-conversation memory - recalling a fact an employee mentioned weeks ago in a different conversation - needs a genuinely different mechanism (an embedding-indexed fact store, or a user-profile summary updated over time) and is a real, separate, bigger feature. Named honestly here as out of scope rather than implied as already solved.
3Feedback surfaced, not acted on - yet
Why gather the latest feedback signal if nothing uses it to change routing this phase? Assembling it now and wiring the auto-escalation logic later is lower-risk than bolting feedback-driven routing on as an afterthought - the data's already in RequestContext when that phase is ready to use it, no re-plumbing needed.
