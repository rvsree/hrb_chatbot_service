Reading the diagram

  • Six steps, left to right, all in one process - no separate services, no message queue between any of them.
  • A cache hit on step 2 returns immediately; everything from step 3 onward only runs on a miss.
  • Step 4 is per sub-question (a compound query decomposes into more than one) - each sub-question independently either hits an MCP tool (live data) or the vector store, never both.
  • The bottom row is every real external system this pipeline touches - Redis, Postgres, the vector store, and the LLM provider (including hrb_lms_mcp for live leave data). No other infrastructure is involved.
  • Slide 8's own target-state design (separate Chat Gateway/Conversation/Knowledge Retrieval/Agent Orchestrator services, LangGraph, SQS-queued writes) is kept in the deck as a historical reference, not shown here - see Decisions GR-1 for exactly why it was never corrected in place.
