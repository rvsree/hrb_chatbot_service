The core mapping tableread the "where it surprises a Spring dev" column first
Spring Boot / JavaThis project's real equivalentWhere it diverges - the part that would surprise you
@SpringBootApplication + embedded Tomcat, main() starts the server src/hrb_chatbot/main.py builds a module-level app = FastAPI(...) object main.py never starts anything. There's no embedded server and no main() entry point at all - uvicorn src.hrb_chatbot.main:app --reload --port 8093 is a separate process that imports the module and serves whatever object it finds named app. Running python main.py directly does nothing useful.
pom.xml + Maven's dependency-resolution graph requirements.txt, flat pinned versions, installed with pip Maven resolves transitive conflicts and shows you the tree. pip mostly just refuses to install if two pins are incompatible, with no equivalent of mvn dependency:tree baked in - this file's own comments are the resolution history by hand (e.g. the pinecone==7.3.0 comment walks through two prior versions pip's resolver rejected, and langchain-chroma==0.2.6/langchain-pinecone==0.2.13 are pinned below 1.0 specifically to stay on the same langchain-core line as langchain==0.3.20). Nothing stops two packages from silently fighting over a shared dependency until someone notices at runtime.
@RestController / @GetMapping, classpath component scanning finds controllers automatically one router file per resource under api/ (e.g. api/rag/retrieve_document.py), each an APIRouter, mounted explicitly in main.py There is no scanning. main.py has ten separate app.include_router(..., prefix=...) calls, one per router - write a new router file and forget that line, and the routes inside it simply never exist, with no startup error telling you so. The URL prefix also lives at the include_router call, not on the router's own file, so the route's full path isn't visible from the router file alone.
@Autowired / @Service / @Component, a DI container builds the object graph for you common/clients/llm_client/client_gateway.py's ClientGateway / common/clients/db_client/db_gateway.py's DBGateway - hand-written lazy singletons There is no container, no annotations, no autowiring at all. get_client_gateway()/get_db_gateway() are plain functions holding a module-level global (_shared_gateway) that gets built once on first call and reused - the comment in client_gateway.py calls this out directly: "Module-level singleton, not a DI container... same effect as a Spring singleton bean." Swapping a real client for a test double isn't a @MockBean - it's tests/conftest.py's FakeClientGateway/FakeDBGateway classes, constructed by hand and passed in wherever a test needs one.
JPA/Hibernate @Entity, a session manages dirty-checking and lazy loading common/clients/db_client/admin_credential_store.py (and every other store in that folder) - raw psycopg, hand-written SQL strings Confirmed by reading the file, not assumed: this project uses no ORM anywhere. admin_credential_store.py builds its own connection with psycopg.connect(...) and runs literal SQL (CREATE TABLE IF NOT EXISTS, hand-written UPDATE ... SET failed_attempts = failed_attempts + 1) wrapped in asyncio.to_thread() since psycopg's sync driver is used from async route handlers. There's no entity graph, no cascade, no N+1 problem to worry about - and no schema migration tool either: ADD_LOCKOUT_COLUMNS's two ALTER TABLE ... ADD COLUMN IF NOT EXISTS statements run at every call, standing in for what Flyway/Liquibase would do as a tracked migration.
application.yml + Spring profiles (dev/test/prod) .env + common/config/settings.py's read_setting() No profile concept exists in the framework at all. read_setting(passed_in_value, env_variable_name, default_value) is a plain three-way fallback (explicit argument, then .env/OS environment, then a hardcoded default) - and .env is loaded with override=True specifically so a stale value already sitting in your shell/Windows environment loses to whatever's in the checked-out .env file, the opposite of python-dotenv's own default. "Which environment am I in" is just a plain string, get_app_environment() reading APP_ENVIRONMENT ("production" in AWS, "development" otherwise) - checked by hand-written if statements in db_gateway.py (blocking the local-disk ChromaDB/SQLite stores in production), not a Spring-style profile-activated bean graph.
@ExceptionHandler, scoped per @ControllerAdvice or controller class main.py's three @app.exception_handler(...) registrations (RequestValidationError, HTTPException, bare Exception) These are global for the whole app by exception type, not attachable per-controller the way @ControllerAdvice can be scoped. The catch-all Exception handler is the only thing standing between an unhandled bug and a raw, unformatted 500 reaching the caller - it logs the real exception server-side (exc_info=exc) and always returns the same generic {"error": "An internal error occurred...", "code": "INTERNAL_ERROR"} shape via json_error(), never leaking a stack trace into the response body.
JUnit + Mockito, @Mock/@InjectMocks, a mocking framework generates the double pytest + hand-written fake classes in tests/conftest.py (FakeChatClient, FakeVectorStore, FakeMetadataStore, ...) No framework generates these - each fake is a real Python class someone wrote, matching the real client's method signatures by hand (the file's own docstring: "these fakes match every real client's method signatures exactly"). monkeypatch (a built-in pytest fixture) swaps a name for the duration of one test and restores it after - comparable to Mockito in effect, but there's no annotation doing it; you call monkeypatch.setattr(...) explicitly. pytest.ini's asyncio_mode = auto also means an async def test_... needs no @pytest.mark.asyncio decorator - closer to JUnit 5's reactive support than JUnit 4.
Spring Boot Actuator's /actuator/health, one endpoint with pluggable indicators two separate endpoints: GET /ping and GET /health (api/admin/routes_health.py) Deliberately not Actuator's "one endpoint, many indicators" shape. /ping never touches a network call - it's what Docker's HEALTHCHECK and App Runner's own health check point at, so a probe firing every 30 seconds can never cost money or fail because a vendor API is down. /health always makes one real, free call per backend (GET /models, list_collections(), never a paid completion). A single endpoint toggled by a ?deep=true query param existed once and was removed - see docs/agent-reference/CODING-STANDARDS.md's "Health checks" section.
Checked exceptions (throws IOException), the compiler forces you to declare or catch them Python has no checked/unchecked distinction at all - every exception is effectively a RuntimeException Nothing enforces error handling at compile time, so this project replaces the compiler's guarantee with a written convention: client code (common/clients/**) returns errors as data from health_check() and never raises; service/business logic raises; route handlers (api/**) catch and translate into json_error()'s consistent {"error", "code"} shape, with code always one of the named constants in common/error_codes.py (e.g. UNAUTHENTICATED, RATE_LIMITED), never a free-text guess. This is discipline enforced by code review and docs/agent-reference/CODING-STANDARDS.md, not the language - nothing stops a new file from skipping it.
The RBAC layer is its own trap for a Spring background: api/gateway/rbac.py's require_role(user_profile, *roles) looks exactly like a Spring Security filter chain decision, but it reads an unsigned user_profile object the caller typed into the request body or query params itself - there's no token verification behind it at all today. It's a documented, deliberate placeholder (Phase 45), not a bug to "fix" on sight.
