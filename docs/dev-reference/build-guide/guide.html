01
Local dev loopthe fast inner loop, before anything touches git
1
Install into a venv
Python 3.12 only, not 3.13/3.14 - chromadb depends on removed Pydantic v1 internals on newer Pythons. Everything imports as from src.hrb_chatbot...., so always run as a module from the repo root.
.venv\Scripts\python.exe -m pip install -r requirements.txt -r requirements-dev.txt
2
Run the full test suite
No test needs a real API key, network call, or costs money - tests/conftest.py's fakes match every real client's method signature exactly, so this passes identically with or without .env configured.
.venv\Scripts\python.exe -m pytest -v --cov=src/hrb_chatbot --cov-report=term-missing --cov-fail-under=45
3
Run it locally and hit it
The equivalent of mvn spring-boot:run - a separate process, not something main.py does by itself (see the Developer Onboarding Guide's bootstrap row). If /health doesn't come back {"status": "healthy", ...}, nothing downstream (Docker, ECR, App Runner) will work either - don't skip straight to containerizing.
.venv\Scripts\python.exe -m uvicorn src.hrb_chatbot.main:app --reload --port 8093
curl http://127.0.0.1:8093/health

Branch strategy - why each promotion existsfeature-* → develop → master
BranchWhat it's forWhat deploys from it
feature-<short-name>one area of new work - one per effort, not one per person. Named feature-<short-kebab-name>, e.g. the current feature-hrb-chatbot-subdomain.nothing directly - ci.yml runs (tests, coverage, security) on every push, so a gate failing is visible immediately, not as a surprise later
developintegration branch - where finished feature branches land and get tested together before they're trustednothing today - it has no deploy target at all; a real gap against "test on develop, then deploy from there," documented as an open, un-made decision (Option A: keep as-is vs. Option B: a second App Runner service, an ongoing AWS cost not provisioned without explicit go-ahead)
masterproduction - what's actually livedeploy.yml - every push here builds, pushes to ECR, and redeploys the real App Runner service. This is the only branch that arms the deploy workflow, no matter how many times develop or a feature branch gets pushed.
Unlike a Spring shop with branch-protection rules, nothing here technically stops a direct push straight to master, bypassing every gate below - no GitHub branch-protection rule requiring a passing CI run or an approval is configured yet (docs/agent-reference/CICD-BRANCHING-STRATEGY.md). The gates exist in CI; nothing today requires going through them.

45% is deliberately not a textbook-sounding round number - the first attempt used 70% before ever actually running the suite, which would have failed on its very first run against code nobody had touched yet. Raise it as real tests get added for real code; never lower it to make a failing build pass.
ci.yml needs no AWS credentials at all - it runs on every push/PR to any branch with zero AWS access, proving only that the app imports, tests pass at the coverage floor, bandit is clean, and the Docker image builds with the real flags (pip-audit runs here too but is report-only). deploy.yml is the only workflow that ever touches real AWS credentials - see the Deployment Verification Guide.
04
The Docker build - and why those exact flagsa plain docker build silently produces a container App Runner pulls but never starts
docker buildx build \
  --provenance=false --sbom=false \
  --output type=image,name=418884736369.dkr.ecr.us-east-1.amazonaws.com/hrb-chatbot:latest,oci-mediatypes=false,push=true \
  .

Every one of these flags is load-bearing, discovered by hitting the exact same generic failure (CREATE_FAILED, image pulled fine, zero application logs) three separate times:

1. Secret ARN missing its random suffix
Secrets Manager appends one to every secret name; App Runner requires the exact full ARN. Fix: never hand-type an ARN, resolve it via secretsmanager list-secrets at deploy time.
2. BuildKit's default provenance/SBOM attestations
A plain docker build wraps the real image in an OCI image index plus an attestation manifest - App Runner pulls it "successfully" and never actually runs it. Fix: --provenance=false --sbom=false.
3. OCI manifest instead of classic Docker v2 schema2
A second, independent cause of the identical symptom, confirmed via docker manifest inspect even after fix #2. Fix: --output type=image,...,oci-mediatypes=false,push=true via buildx, not plain docker build.
# validate before pushing
docker image inspect hrb-chatbot:local --format "{{.Os}}/{{.Architecture}}"   # expect: linux/amd64

# validate what actually got pushed
docker manifest inspect 418884736369.dkr.ecr.us-east-1.amazonaws.com/hrb-chatbot:latest
# expect mediaType: "application/vnd.docker.distribution.manifest.v2+json"
If you ever need to touch that build line, re-run both verification commands above before pushing, not after a failed deploy - someone "simplifying" it back to a bare docker build -t ... . would silently reintroduce one of these three.
05
Push to ECRthe last build-side step before anything can be deployed
1
Push to ECR
Already done by the docker buildx build ... push=true command above. A manual push, if you ever need one for a differently-built image:
aws ecr get-login-password --region us-east-1 | docker login --username AWS --password-stdin 418884736369.dkr.ecr.us-east-1.amazonaws.com
docker push 418884736369.dkr.ecr.us-east-1.amazonaws.com/hrb-chatbot:latest
The image is in ECR now, but nothing redeploys automatically from that alone (AutoDeploymentsEnabled=false) - triggering the actual App Runner deployment, polling for RUNNING, and smoke-testing it is the Deployment Verification Guide's job, not this one.
