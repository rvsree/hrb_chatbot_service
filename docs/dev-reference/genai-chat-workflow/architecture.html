architecture - one ReAct tool-calling loop over in-request files, no index, no persisted documents

GenAI Chat Workflow

A single LLM tool-calling loop behind POST /v1/adhoc-document-chat/query - up to 3 attached files read entirely in memory, 3 real tools, and Postgres-backed session memory that remembers what was said, never the files themselves.

1
The agent loop adhoc_document_agent.py :: run_agent()
SystemMessage + history + question→ llm.ainvoke()→ tool_calls present?
yes → run tool, append output to messages, call the LLM again
no tool_calls→ return answer

No LangGraph, no persisted graph state - this is a plain for loop bounded by DEFAULT_MAX_ITERATIONS, re-invoking the same LLM with a growing messages list until a response carries no tool calls. One real wrinkle, confirmed live: a response can both write real content and call a tool in the same turn (OpenAI allows this) - that content only gets appended to history, not returned, so the loop tracks last_emailed_answer_text and reuses SendEmailWithAnswer's own answer argument as the final answer when set, instead of trusting whatever short wrap-up the model writes on the next turn ("I've emailed it") - fixes the chat window going blank after a query that also sends an email.

3
Tool-calling mechanics the 3 real tools the model can call, and what each one actually touches

Every tool call is dispatched in-process, inside the same loop - there's no second service and no MCP call here (that's single/multi-agentic-rag's job). ReadDocument never reaches outside file_texts; SearchWeb is the one deliberate exception that reaches a real external API.

ReadDocument(filename)Returns one attached file's already-extracted, already-guardrailed text from file_texts; tracks the filename in files_used the first time it's read. An unknown filename returns an error string back into the loop, not an exception.
SearchWeb(query)Calls web_search_agent.run() - reuses multi-agentic-rag's existing Tavily integration directly rather than building a second one. A successful, non-empty query is recorded in web_searches.
SendEmailWithAnswer(recipient_email, subject, answer, email_body_html)Fires only when the current turn's question explicitly asks for it (see Decisions GCW-5). Sends a separately-authored HTML body via SES, attaches the original uploaded bytes (not re-encoded text), and always records email_evidence - sent or failed, never silently skipped.
4
State & memory management 3 Postgres tables, no FKs between them - conversation persists, file content never does

chat_workflow_store.py is deliberately separate from conversation_store.py (the other 3 retrieval modes' own memory) - different shape, same database, same bounded-context-per-table pattern this project uses elsewhere (no cross-table foreign keys; email_send_events.turn_id is a plain integer reference, not an FK constraint).

chat_session_recordsOne row per session - session_id, employee_id, session_title, started_at/last_active, turn_count_total. Always-on, not opt-in like enable_conversation_memory on the other 3 modes.
chat_turn_recordsOne row per turn - user_query_text, agent_response_text, attached_file_names. Only the conversation is durable; the attached files' actual text never lands in this table.
email_send_eventsOne row per send attempt (either path) - recipient_email_address, email_status, trigger_source (model_decision or checkbox_auto), linked to its turn by turn_id.

A real bug memory itself reintroduced, caught live

Stored turns originally carried only the plain answer text, so a later "did you send it?" had no way to know an earlier email actually succeeded - the model answered "I have not sent any email yet" even when it had. The fix: the stored version of each turn's answer (never the user-facing one) gets a [System note: ...] suffix recording the real outcome, stripped by _strip_system_notes() before GET /sessions/{id} ever returns it to a person.
