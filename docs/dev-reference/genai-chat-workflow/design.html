design - api contracts, session model, real constraints

GenAI Chat Workflow

One multipart request in, one grounded answer out - with session memory, dual email paths, and per-file guardrail screening.

Spec Architecture Design Decisions
1
API contract

POST /v1/adhoc-document-chat/query - multipart form, not JSON (file upload).

Form fieldTypeNotes
user_profileJSON stringParsed via UserProfile.model_validate_json, same identity shape as every other route
questionstr, 1-2000 charsScreened by the input guardrail before the agent sees it
files1-3 files.pdf/.docx/.csv only, 10MB each - rejected as 422 otherwise
session_idstr, optionalOmit on the first turn - server generates one; send it back to continue
recipient_emailstr, optionalValidated by a plain regex, not an email-validator dependency
send_email_on_answerbool, default falseCheckbox-driven path - requires a valid recipient_email when true
cc_emailstr, optionalComma-separated; each address validated individually

Response (AdhocDocumentChatResponse): question, answer, files_used, web_searches, email_sent_to, email_evidence, session_id, model_used, iterations, llm_call_count, token_usage, latency_ms. Deliberately no vector_db/search_strategy/citations fields - none apply, there's no KB here.

2
Request flow
validate files→ extract text→ guardrail each file→ guardrail question→ load session history→ ReAct agent→ output guardrail→ checkbox email→ persist turn

A history-load failure for an existing session doesn't fail the request - it logs a warning and continues with empty history, same best-effort principle as persisting the turn afterward: a DB hiccup after the answer is already computed shouldn't turn a successful answer into a 500.

3
The two email paths

Two independent ways an email can be sent in the same turn, each persisted as its own event: the agent's own in-text SendEmailWithAnswer tool call (fires only when the current turn's question explicitly asks for it - governed purely by the system prompt, not a second directive layered on top), and the checkbox-driven path the route handles directly whenever send_email_on_answer is true. If both fire the same turn, the checkbox-driven one wins in the API response (the more deterministic, explicitly-requested one), but both still get their own row in chat_workflow_store's email-event log.

4
Session memory

Always-on for this workflow (not an opt-in flag, unlike the other 3 retrieval modes' enable_conversation_memory) - a session is how a user asks "did you send that email?" in a later turn and gets a correct answer. The stored version of each turn's answer carries a short [System note: ...] suffix recording the real outcome of any email attempt that turn; this suffix is stripped before ever being shown to a person (GET /sessions/{id} strips it from every turn it returns).

5
Real constraints (NFRs)
ConstraintValueWhy
File count≤ 3 per requestBounds context size and extraction time per turn
File size≤ 10MB eachRejected as 422 before extraction is attempted
Extracted text~12k chars/file truncationProtects the model's context window; truncation is surfaced to the user, never silent
File lifetimeIn-request onlyNothing written to S3 or disk - the file exists only for the duration of this one call
Session memoryConversation only, not filesA continued session remembers what was said, not the attached files themselves - re-attach to ask about them again
