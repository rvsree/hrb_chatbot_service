App Runner's service dashboardwhat RUNNING / OPERATION_IN_PROGRESS actually mean
Where it is
Service ARN arn:aws:apprunner:us-east-1:418884736369:service/hrb-chatbot/f957548202f343aa8ca91f341d71d85a, live URL https://mrgysvt6ye.us-east-1.awsapprunner.com - both only derivable from AWS itself, not from any file in this repo (docs/agent-reference/AWS-DEVOPS-RUNBOOK.md's "Resource identifiers" table).
aws apprunner describe-service --service-arn <ARN>
Reading Service.Status
RUNNING is the only healthy terminal state. OPERATION_IN_PROGRESS is the expected value while a deployment is rolling out - not a failure, it's what you poll through. CREATE_FAILED/UPDATE_FAILED are real failures, documented three separate times during this project's own first deployment (see the Build Guide's "3 real bugs" panel, the Docker build one).
Auto-deploy is deliberately off
AutoDeploymentsEnabled is false on this service - pushing a new :latest image to ECR does not redeploy it by itself. A real deploy needs an explicit aws apprunner start-deployment call (what deploy.yml does).
What to check alongside status
SourceConfiguration.ImageRepository.ImageConfiguration.RuntimeEnvironmentVariables - specifically RAG_VECTOR_DB and RAG_METADATA_STORE, easy to forget which is actually live (today: Pinecone is live, Postgres metadata is not - the deployed service still runs RAG_METADATA_STORE=sqlite because a hosted Postgres hasn't been provisioned).

Tailing CloudWatch logs for this serviceand the one real limitation that cost real debugging time
aws logs describe-log-groups --log-group-name-prefix "/aws/apprunner/hrb-chatbot"
aws logs describe-log-streams --log-group-name "/aws/apprunner/hrb-chatbot/<service-id>/service" --order-by LastEventTime --descending
aws logs get-log-events --log-group-name "/aws/apprunner/hrb-chatbot/<service-id>/service" --log-stream-name "<stream>"
Confirmed the hard way, not just documented: when the container itself never starts (as opposed to starting and then crashing), there is no separate application log group with this project's own logging output - only the generic /service group exists, and its two messages ("Successfully pulled your application image... Failed to deploy your application image") don't say why. Seeing that exact pattern with zero app-level logs means check the image itself (manifest format, architecture) before spending time on Python code that never even ran - see the Build Guide's Docker build panel.

Reading a LangSmith tracelocal-vs-prod project split, and what's confirmed vs. unconfirmed about span content
How tracing turns on
common/observability/langsmith_tracing.py's enable_tracing_if_configured() is called once, at import time, from main.py (before app = FastAPI(...) is even built). If LANGSMITH_ENABLED is true and an API key is set, it sets three env vars LangChain's own chains already check - LANGCHAIN_TRACING_V2, LANGCHAIN_API_KEY, LANGCHAIN_PROJECT. There's no explicit "start a trace" call anywhere else in this codebase - it's opt-in instrumentation LangChain does for you.
Local vs. prod project split
_resolve_project_name() appends _local or _prod to the base hrb_chatbot_v2 project name, read from HRB_CHATBOT_LOCAL/HRB_CHATBOT_PROD flags - every checked-out .env defaults to LOCAL=true/PROD=false, production's own App Runner env vars set the opposite. If both are somehow true, _prod wins - a misconfigured prod deploy still gets labeled correctly rather than silently polluting the local project's traces.
hrb_chatbot_v2_localhrb_chatbot_v2_prod
What a trace shows for one query
Not independently confirmed by reading this file alone (it only turns tracing on - it doesn't define spans). What's documented elsewhere in this project: the three retrieval modes (genai-rag, single-agentic-rag, multi-agentic-rag) are genuinely different pipelines - a fixed retrieve-then-generate call, a tool-calling loop, and a LangGraph multi-agent graph respectively - so a trace's shape differs by which endpoint was hit; a LangGraph run in particular would show each graph node as its own nested span. Treat the exact span layout as something to confirm by opening a real trace in the LangSmith UI, not something this doc can assert from source alone.

Where real secrets live vs. plain env varsSecrets Manager for provider keys, App Runner config vars for everything else
WhatWhere it livesWhy
OPENAI_API_KEY, ANTHROPIC_API_KEY, OPENROUTER_API_KEY, TAVILY_API_KEY, PINECONE_API_KEY AWS Secrets Manager, hrb-chatbot/* prefix - 5 real secrets, injected into the running container via App Runner's RuntimeEnvironmentSecrets Real credentials to paid third-party APIs. Secrets Manager appends a random suffix to every ARN (hrb-chatbot/OPENAI_API_KEY-LdC1Q6) - resolved at deploy time via secretsmanager list-secrets, never hand-typed (this exact mistake caused a real CREATE_FAILED once).
RAG_VECTOR_DB, RAG_METADATA_STORE, APP_ENVIRONMENT, HRB_CHATBOT_LOCAL/_PROD, LANGSMITH_ENABLED plain App Runner RuntimeEnvironmentVariables - ordinary, visible config, not secrets None of these are sensitive - they're which-backend-to-use switches read by read_setting(). Putting them in Secrets Manager would just add an API call for no confidentiality benefit.
Postgres credentials (POSTGRES_DB_HOST/_PORT/_NAME/_USER/_PASSWORD) design only - docs/agent-reference/AWS-DEVOPS-RUNBOOK.md documents the exact 5 secrets to create "once provisioned," same hrb-chatbot/* prefix Not live. A hosted Postgres (Neon) hasn't been provisioned yet - this is a real, acknowledged gap, not an oversight to silently work around.
HRB_LMS_MCP_OAUTH_CLIENT_ID/_SECRET (Phase 53, app-to-app OAuth2 to hrb_lms_mcp) docs/dev-reference/auth/oauth2-auth-architecture.html says only ".env: ... plaintext secret, handed over once, never committed" ⚠ Unconfirmed whether the deployed App Runner service holds this as a Secrets Manager entry or a plain env var - that doc describes the local .env convention, not the production injection mechanism. Don't assume either without checking the real App Runner service config.
