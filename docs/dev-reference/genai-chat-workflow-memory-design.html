Chat Workflow Memory

Giving the GenAI Chat Workflow (ad-hoc file chat) its own session-scoped short-term memory and an automatic email-on-answer option, backed by new SQLite tables.

Status: proposal, pending approval Revision 2 - A2A-grounded schema Phase: unassigned No code written yet
01

The problem, in your own transcript

The GenAI Chat Workflow route (adhoc-document-chat/query) has no backend memory at all today. Every turn is built as a fresh [SystemMessage, HumanMessage] pair - no history, no session id passed through. The chat bubbles you see are frontend-only state; the model underneath never sees a prior turn. Your own production conversation shows exactly what that looks like:

You Summarize Accenture offer concisely. also send email with the details to given id Agent Here is a concise summary of your Accenture offer: … Position: Full Stack LLM Development Manager … Base Salary: $215,000 annually … You did you sent email to "rv.sreedharan@gmail.com" ? Agent I have not sent any email yet. If you would like me to send an email… You you need to send email of the response summary generated earlier, is it there in your memory… Agent There is no response summary generated earlier in this conversation.

The agent isn't confused - it's telling the truth. Nothing from turn 1 was ever stored anywhere the model (or anything else) could read it back from.

02

Is this what's called STM?

Yes, exactly. This codebase already uses that term for precisely this concept, in two places:

  • ai/pre_processing/conversation_memory.py's own docstring: "…Postgres-backed (Phase 76), STM and LTM are the same durable store, not two tiers."
  • BACKLOG.md Phase 76 entry: "Conversation storage is in-memory only (STM), no LTM…"

Short-Term Memory (STM) is the turn-by-turn working memory of one session or thread - what did we just say to each other. Long-Term Memory (LTM) is anything that survives and informs other sessions - a learned preference, a fact about the user, a summarized history. This proposal is STM only: one chat workflow session's own turns, nothing cross-session. genai-rag's existing conversation_turns table is the same idea for the other 3 RAG pipelines - this is the GenAI Chat Workflow's own equivalent, deliberately separate (different shape: file attachments and email events don't apply to the other pipelines at all).

03

Architecture

Session id is generated client-side on first attach (same pattern conversation_id already uses for the other 3 modes) and sent on every subsequent turn in that chat. The backend loads prior turns for that session before building the prompt, and - new - decides whether to email, before the answer ever reaches the browser.

    UI --> Route --> Load --> Agent
    Agent --> EmailCheck
    EmailCheck -- yes --> SES --> EmailEvt --> SaveTurn
    EmailCheck -- no --> SaveTurn

The email decision now happens two ways: the model can still call SendEmailWithAnswer mid-reasoning when the question itself asks for it (unchanged, today's behavior) - or, new, the checkbox path fires automatically once the answer is final, independent of whether the question text mentioned email at all. Either path writes the same email_send_events row, so the Explainability evidence view (shipped this week) covers both without change.

04

A2A protocol alignment - what I checked

You pointed me at github.com/jeev1992/real-estate-negotiation-simulator's m2_adk_multiagents module (IK FDE cohort material on Google ADK + the A2A protocol). I fetched the module's README and its wire-format demo script directly via the GitHub API, not from memory.

What it actually teaches

It bundles two separate things: Google's ADK (Agent Development Kit - a full agent framework: LlmAgent, SequentialAgent, LoopAgent, its own session/state system) and the A2A protocol (Agent-to-Agent - an open wire format for agents to discover and call each other over HTTP, independent of ADK). The demos name A2A's core vocabulary explicitly:

  • Task - one unit of work, with a real lifecycle: submitted → working → completed/failed.
  • Message - one conversational turn, tagged role: user or agent.
  • Part - atomic content inside a message: TextPart, DataPart, FilePart.
  • Artifact - a durable output attached to a completed Task.
  • contextId - threads multiple Tasks into one ongoing conversation.
Confirms the SQLite finding above, independently

The README is explicit that .adk/session.db (SQLite) is a runtime artifact, not source code - gitignored, recreated on every run, safe to delete. Even this course's own reference implementation never treats SQLite as durable production storage. That's the same conclusion the App Runner auto-scaling check reached independently, above.

Your direction: A2A concepts via LangGraph, not Google ADK

Agreed - and here's the concrete reasoning, not just a preference:

  • This project already is a LangGraph multi-agent system. multi_agent_pipeline.py already runs Planner → fan-out → domain agents → Reviewer as a real StateGraph. Adding Google ADK on top would be a second, overlapping agent framework doing the same job - exactly what the project's own "no unreviewed libraries" rule exists to catch.
  • The real A2A wire protocol (HTTP + JSON-RPC + Agent Cards) is built for agents that are separate, independently-deployed services - true for the course's buyer/seller agents (each its own adk web server) but not true for any agent in this codebase today: every domain agent in multi_agent_pipeline.py runs in-process, inside one StateGraph.ainvoke() call. There's no network boundary between them to protocol over.
  • What's actually worth taking is the vocabulary and the discipline, not the transport. contextId is exactly what session_id already does below. A Task's explicit lifecycle states are exactly what the new email_status column borrows (§06) instead of a bare boolean. If a future phase genuinely needs to call a separate, independently-deployed agent service - not a hypothetical today - adopting the real A2A SDK then is the right call, reviewed on its own, not folded into this schema work.
Flag before building - needs your decision

This codebase already forbids SQLite in production, on purpose. db_gateway.py: "chromadb/sqlite are local-disk stores - never shared across App Runner's multiple instances… A production request/default that resolves to either is never a legitimate choice there, only a silent split-brain footgun." That's not theoretical here - I checked: hrb-chatbot's App Runner auto-scaling config allows up to 25 concurrent instances, each with its own separate local disk, and App Runner containers have no persistent volume at all - local SQLite data is lost on every redeploy regardless of instance count.

If these new tables use SQLite in production, a user's GenAI Chat Workflow history can silently split across instances or vanish on the next deploy. Two ways forward:

A · SQLite locally, Postgres in prod

Same schema, same table/column names, swappable client behind the existing gateway pattern - exactly how conversation_store.py already does it (SQLite-shaped locally during dev, a real Postgres table in production). Zero data-loss risk, fits the project's own established rule.

B · SQLite everywhere, including prod

Matches what you're standardizing on for MCP/A2A memory elsewhere. Workable only if this workflow is explicitly accepted as "best-effort, can lose history on redeploy or under load" - a real tradeoff, not a bug to fix later.

Everything below (table names, columns, diagrams) is written so either option drops in unchanged - Option A just means the same DDL gets a Postgres dialect for the production client.

05

Conceptual model

Three entities. One employee can run many chat sessions; one session holds many turns; a turn produces at most one email event.

erDiagram
    EMPLOYEE ||--o{ CHAT_SESSION : starts
    CHAT_SESSION ||--o{ CHAT_TURN : contains
    CHAT_TURN ||--o| EMAIL_SEND_EVENT : triggers

    EMPLOYEE {
        string employee_id
        string full_name
    }
    CHAT_SESSION {
        string session_id
        string session_title
        datetime started_at
        datetime last_active
    }
    CHAT_TURN {
        string turn_id
        int turn_sequence_number
        string user_query_text
        string agent_response_text
        string attached_file_names
        datetime created_at
    }
    EMAIL_SEND_EVENT {
        string recipient_email_address
        string cc_email_addresses
        string email_status
        string trigger_source
        datetime sent_at
    }

No cross-schema foreign keys to the existing conversation_turns/employees tables - same bounded-context-with-no-FKs convention this project already uses between hrb_chatbot_v2_core and the MCP-owned tables. employee_id is carried as a plain column, not a real foreign key.

Physical model - SQLite DDL

Table and column names run 2-3 words each, as asked, snake_case throughout (matches every existing table in this project).

ColumnTypeNotes

Third table - "any other metadata"

You asked for a third table for additional metadata beyond turns and email events. Proposing no separate physical table for this: chat_session_records already carries session-level metadata (title, counts, timestamps), and per-turn metadata that isn't query/response text (model used, token usage, latency) is exactly what AdhocDocumentChatResponse already returns today and doesn't need to be durable - it's explainability, not memory. If a real need for a free-form metadata table shows up later (e.g. per-turn tags, ratings), add it then with a real use case, rather than a speculative empty table now.

CREATE TABLE IF NOT EXISTS chat_session_records (
    session_id        TEXT PRIMARY KEY,
    employee_id       TEXT NOT NULL,
    full_name         TEXT,
    session_title     TEXT,
    started_at_utc    TEXT NOT NULL,
    last_active_utc   TEXT NOT NULL,
    turn_count_total  INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_chat_session_employee
    ON chat_session_records (employee_id, last_active_utc);

CREATE TABLE IF NOT EXISTS chat_turn_records (
    turn_id               TEXT PRIMARY KEY,
    session_id            TEXT NOT NULL,
    employee_id           TEXT NOT NULL,
    turn_sequence_number  INTEGER NOT NULL,
    user_query_text       TEXT NOT NULL,
    agent_response_text   TEXT NOT NULL,
    attached_file_names   TEXT NOT NULL DEFAULT '[]',
    created_at_utc        TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_chat_turn_session
    ON chat_turn_records (session_id, turn_sequence_number);

CREATE TABLE IF NOT EXISTS email_send_events (
    event_id                 TEXT PRIMARY KEY,
    turn_id                  TEXT NOT NULL,
    recipient_email_address  TEXT NOT NULL,
    cc_email_addresses       TEXT,
    email_subject_line       TEXT NOT NULL,
    email_status             TEXT NOT NULL CHECK (email_status IN ('sent', 'failed')),
    send_status_message      TEXT NOT NULL,
    attached_file_names      TEXT NOT NULL DEFAULT '[]',
    trigger_source           TEXT NOT NULL CHECK (trigger_source IN ('model_decision', 'checkbox_auto')),
    sent_at_utc              TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_email_event_turn
    ON email_send_events (turn_id);
07

Attach-files popup - new email fields

sequenceDiagram
    participant U as User
    participant P as Attach-files popup
    participant R as Route
    participant A as Agent
    participant S as SES

    U->>P: checks "Send email on answer"
    P->>P: reveal To / CC fields
    U->>P: types To address
    P->>P: validate on blur (real email pattern)
    alt invalid
        P-->>U: inline error, e.g. "someone@" isn't a complete email address
    else valid
        U->>P: Send
        P->>R: question + files + to/cc + checkbox=true
        R->>A: run_agent(...)
        A-->>R: final answer
        R->>S: send_email(to, cc, answer)
        S-->>R: sent / failed + reason
        R-->>P: answer + email_send_events row
        P-->>U: answer renders + Email evidence section
    end
  • Checkbox: "Send email on answer" (off by default, same low-friction default as today's optional field) - reveals To/CC once checked, same collapse pattern the attach panel already uses.
  • To validation: required only when the checkbox is on; a real email-format check (not just "contains @"), inline error under the field, e.g. "someone@ isn't a complete email address - check for a typo before the @ or after the domain." Never a raw regex-failure message.
  • CC: optional even when the checkbox is on; comma-separated, each address validated the same way, same inline error style per invalid entry.
  • Timing: unchanged request shape otherwise - the checkbox path and the model's own in-text SendEmailWithAnswer decision both still fire after generation, before the response renders, matching your phrasing exactly.
