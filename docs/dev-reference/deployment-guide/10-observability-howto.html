Checking LangSmith, CloudWatch, Pinecone & Neon

Written 2026-10-06, after Phase 88's live testing raised the question directly: where does tracing/logging actually show up today, for each of this project's three running surfaces (local, App Runner, the new Phase 88 Lambda)? Answered by reading the code and checking the real dashboards, not assumed. Expanded 2026-10-20 (user-requested) to also cover Pinecone and Neon Postgres usage - both still login-only, no deep-linkable usage page exists for either, confirmed by checking rather than assumed.

Correction, 2026-10-20: the "How to actually check it" section below originally said to select a single hrb_chatbot_v2 LangSmith project. That's been wrong since _resolve_project_name() (common/observability/langsmith_tracing.py) started splitting traces into hrb_chatbot_v2_local and hrb_chatbot_v2_prod - two separate projects, driven by HRB_CHATBOT_LOCAL/HRB_CHATBOT_PROD, prod winning if both are somehow true. Fixed below - re-verified directly against the real code for this correction, not assumed from the original text.
The one-line answer, stated up front: LangSmith shows real traces for genai-rag/single-agentic-rag/multi-agentic-rag's query-side chains (local and App Runner, whenever LANGSMITH_ENABLED=true) — but shows nothing for the ingestion pipeline, anywhere, including the new Lambda path, for two separate, confirmed reasons below. CloudWatch is the real, working way to see what the Lambda ingestion pipeline is doing today.

Why ingestion is invisible to LangSmith, reason 1: the Lambda never turns tracing on

common/observability/langsmith_tracing.py's enable_tracing_if_configured() is the only thing that sets LANGCHAIN_TRACING_V2/LANGCHAIN_API_KEY/LANGCHAIN_PROJECT — and it's called from exactly one place: main.py, line 20, at module import time. That only runs when src.hrb_chatbot.main gets imported — i.e. when the FastAPI app itself starts (local uvicorn or App Runner). lambda_handlers/index_document_handler.py never imports main.py and never calls this function — so even though the Lambda's environment variables include LANGSMITH_ENABLED=true and a real LANGSMITH_API_KEY (copied from App Runner's own config when the function was provisioned), they're inert. No LangChain env var ever gets set inside the Lambda.

Why ingestion is invisible to LangSmith, reason 2: even the FastAPI app's ingestion path wouldn't show much

LangSmith's auto-instrumentation only traces real LangChain Runnables. Ingestion's two LLM calls — OpenAIEmbeddingClient (embeddings, in embedding_generator.py) and OpenAIChatClient (document-metadata extraction, in document_metadata_extractor.py) — both go through this project's own raw-openai-SDK wrapper, never a LangChain class. So turning tracing on for the Lambda (fixing reason 1 alone) would still show nothing for ingestion specifically — the same root cause as the already-tracked genai-rag token-count gap above. Fixing it for real means wrapping the raw openai.OpenAI client with langsmith.wrappers.wrap_openai(), which would fix both gaps at once — not done, tracked in BACKLOG.md.

LangSmith — how to actually check it

Local

  1. Confirm .env has LANGSMITH_ENABLED=true, a real LANGSMITH_API_KEY, and HRB_CHATBOT_LOCAL=true (every checked-out .env defaults to this)
  2. Start the app: .venv\Scripts\python.exe -m uvicorn src.hrb_chatbot.main:app --reload --port 8093 — the startup log line "LangSmith tracing is on (project=hrb_chatbot_v2_local)" confirms it took effect and names the real project
  3. Run any real genai-rag query (POST /v1/genai-rag/retrieve-document/query) or single/multi-agentic-rag call
  4. Open smith.langchain.com, select the hrb_chatbot_v2_local project in the left sidebar (not hrb_chatbot_v2 - that bare name is never actually used), and the trace appears under Runs — usually within a few seconds

AWS App Runner (production)

Same steps, no local setup needed — LANGSMITH_ENABLED=true and HRB_CHATBOT_PROD=true are already live in App Runner's runtime config today, which routes traces into the separate hrb_chatbot_v2_prod project instead. Hit the real URL (https://mrgysvt6ye.us-east-1.awsapprunner.com/v1/genai-rag/retrieve-document/query) with a real query, then check hrb_chatbot_v2_prod on smith.langchain.com - picking the right one of the 2 projects in the sidebar is now how local vs. production traces are told apart, not a tag/metadata field.

Lambda (ingestion)

Nothing to check — confirmed above, tracing is never enabled there regardless of the env vars present. Use CloudWatch (below) instead.

Pinecone — how to check usage

No deep-linkable usage URL exists for this (or any) specific index - confirmed, nothing in this project's own config stores one. The real index is hrb-chatbot-kb (region us-east-1), confirmed live via the production /health endpoint (vector_database.index_name).

  1. Log in at app.pinecone.io
  2. Select the hrb-chatbot-kb index from the index list
  3. The index's own dashboard shows real vector count, read/write units, and storage - the real usage/billing-relevant numbers

Neon Postgres — how to check usage

Unlike Pinecone, Neon does have a real dashboard page for this - the Monitoring tab, not just a bare console landing page.

  1. Log in at console.neon.tech
  2. Select the HR_Benefits project (same database this project's own metadata_database health check reports, confirmed via the production /health endpoint)
  3. The Monitoring tab shows compute usage, storage, and active time - what actually drives Neon's free-tier limits and any paid-tier billing

Worth knowing: Neon's own free tier auto-suspends compute on inactivity, so a dormant project costs nothing between real usage - the Monitoring tab's own activity graph shows this suspend/resume pattern directly.

CloudWatch — console steps

  1. AWS Console → CloudWatch → Log groups (left sidebar, under Logs)
  2. For the Lambda ingestion pipeline: /aws/lambda/hrb-chatbot-index-document — this project's own plain-text logs (get_logger() format) interleaved with the handler's own JSON-formatted lines, one log stream per container instance, named by date and a cold-start id
  3. For the main app (App Runner): two separate log groups exist — /aws/apprunner/hrb-chatbot/f957548202f343aa8ca91f341d71d85a/application (this project's own app logs — what get_logger() writes, same format as local) and /aws/apprunner/hrb-chatbot/f957548202f343aa8ca91f341d71d85a/service (App Runner's own operational logs — deployments, health check results, container start/stop — not this project's code)
  4. For the DLQ-depth alarm: CloudWatch → Alarms → hrb-chatbot-ingest-dlq-depth — fires if any message ever lands in the dead-letter queue
  5. For queue depth generally: SQS console → hrb-chatbot-ingest-queue / hrb-chatbot-ingest-dlq → Monitoring tab has the same metrics graphed

CloudWatch — CLI steps, with the real gotchas this hit

Two real gotchas on Windows Git Bash, both hit live while verifying Phase 88 — worth knowing before copy-pasting these:
  1. Git Bash auto-converts any argument starting with / into a Windows path, which mangles a log group name like /aws/lambda/... into garbage before the AWS CLI ever sees it. Fix: prefix the command with MSYS_NO_PATHCONV=1.
  2. Some log lines contain characters the Windows console's default codepage can't display, crashing the AWS CLI's own output formatting with 'charmap' codec can't encode characters... — happens with --output text/json printed straight to the terminal. Fix: redirect to a file (doesn't fully dodge it either, since the CLI still tries to format for the console first) or, more reliably, use a small boto3 script that writes the file itself with encoding="utf-8" explicitly — see the pattern below.
# Find the most recent log stream for the Lambda:
MSYS_NO_PATHCONV=1 aws logs describe-log-streams \
  --log-group-name /aws/lambda/hrb-chatbot-index-document \
  --order-by LastEventTime --descending --max-items 1 \
  --region us-east-1 --query 'logStreams[0].logStreamName' --output text

# Reliable way to read events (sidesteps the charmap crash entirely):
python -c "
import boto3
client = boto3.client('logs', region_name='us-east-1')
response = client.get_log_events(
    logGroupName='/aws/lambda/hrb-chatbot-index-document',
    logStreamName='<paste the stream name from above>',
    startFromHead=True,
)
with open('lambda_log.txt', 'w', encoding='utf-8') as f:
    for event in response['events']:
        f.write(event['message'])
"

# Or search the last few minutes across EVERY stream at once (useful after
# a multi-document test, where several streams/invocations may exist):
python -c "
import boto3, time
client = boto3.client('logs', region_name='us-east-1')
now_ms = int(time.time() * 1000)
response = client.filter_log_events(
    logGroupName='/aws/lambda/hrb-chatbot-index-document',
    startTime=now_ms - 3*60*1000, endTime=now_ms,
)
with open('recent.txt', 'w', encoding='utf-8') as f:
    for event in response['events']:
        f.write(f\"{event['timestamp']} | {event['logStreamName']} | {event['message']}\")
"
