Architecture — request flow (revised: S3 → SQS → Lambda)

Revised 2026-10-05 from the original S3->Lambda-direct design — SQS is now the primary trigger queue, not just a bolt-on failure bucket. Same reasoning either way needs stating plainly: there is no separate "listener" process to write or deploy. Lambda's own SQS trigger (an "event source mapping") is AWS-managed infrastructure — AWS polls the queue and invokes the Lambda function for you.

Presigned URLs — how they actually work

A presigned URL is a normal S3 URL with extra query-string parameters (a signature, an expiry timestamp, which AWS credential signed it) appended by AWS's own SDK — generated entirely server-side, using this project's own backend credentials, handed to the client as a plain string. The client then uploads directly to that URL with a plain HTTP PUT (or POST for the form-field variant) — no AWS SDK, no AWS credentials, nothing AWS-specific required on the client at all. It works exactly like you'd have built it at JPMorgan (DARCE/UMA) — same mechanism, same reason: keep large file bytes off your own application server.

# Server-side (Lambda-free, just boto3 in the FastAPI app):
import boto3
s3 = boto3.client("s3")
url = s3.generate_presigned_url(
    "put_object",
    Params={"Bucket": "hrb-chatbot-kb-uploads", "Key": f"{document_id}.pdf"},
    ExpiresIn=300,   # link only valid for 5 minutes
)
# Hand `url` back to the client in the API response. That's the whole mechanism.

Does this need JWT or OAuth2? No — two separate questions, easy to conflate

QuestionAnswer
Does generating the presigned URL itself need JWT/OAuth2?No. The "presigned" signature is AWS's own SigV4 request-signing, built into the AWS SDK, signed with the backend's existing AWS IAM identity (the same App Runner instance role already used for every other AWS call). Nothing to do with JWT or OAuth2 — a completely separate mechanism.
Should the endpoint that hands out the presigned URL be protected by real caller authentication?A fair, separate security question — whoever can call that endpoint gets indirect write access to the S3 bucket. Today it would get the same protection every other endpoint already has: the placeholder user_profile RBAC gateway, not real auth. That's an existing, already-documented project-wide limitation (see CLAUDE.md's gateway section) — not something this feature introduces or needs to solve on its own.

Worth knowing for later: this project does already have a real OAuth2 client-credentials flow (Phase 53 — app-to-app, for calling hrb_lms_mcp), so the groundwork exists if/when real human-to-app auth gets built. That's unrelated to presigned URLs working today, though — presigned URLs need nothing further to implement right now.

Fundamentals refresher: encoding/decoding, from the ground up

Going slower here since this is foundational. A file on disk — a PDF included — is just a long sequence of numbers, each between 0 and 255 (one byte). Nothing about a PDF is inherently "text"; it's binary data, full stop.

Some systems were only ever designed to carry text safely — email (historically), URLs, JSON string fields, HTTP headers. These systems can choke, corrupt, or outright reject certain byte values (e.g., byte value 0, or anything above 127) if you hand them raw binary. Encoding is the fix: a mechanical, reversible translation that re-expresses arbitrary binary bytes using only a small, safe set of text characters. Decoding is just running that translation backward to get the original bytes back.

The most common encoding for this is Base64. Concretely, step by step:

  1. Base64 only uses 64 safe characters: A-Z, a-z, 0-9, +, / — every one of them is guaranteed safe in text/URLs/JSON
  2. It takes your binary data 3 bytes at a time (3 bytes = 24 bits)
  3. It re-slices those 24 bits into 4 groups of 6 bits each (6 bits = a number from 0-63 — exactly how many safe characters there are)
  4. Each 6-bit number maps to one of the 64 safe characters, via a fixed lookup table
  5. Result: 3 raw bytes become 4 text characters — which is also why base64 text is always about 33% larger than the original binary

Decoding is exactly the reverse: read 4 base64 characters, look each up to get its 6-bit number back, recombine four 6-bit groups into three original 8-bit bytes.

One common confusion worth clearing up directly: encoding is not encryption. Base64 provides zero security — anyone can decode it instantly, there's no secret key involved. It exists purely to make binary data transportable through text-only channels, never to hide or protect it.

Where this actually shows up in this project's design — and where it deliberately doesn't

ScenarioEncoding involved?
Client uploading the PDF directly to S3 via the presigned URL (this design)No. Raw binary PUT over HTTP — S3's upload API accepts binary natively. This is deliberate: it's exactly why the presigned-URL pattern is preferred over routing bytes through the API.
Lambda reading the file back from S3 (get_object())No. boto3 hands back raw bytes directly — another direct binary call, no text layer in between.
A presigned POST policy's Content-MD5 fieldYes, but only a small checksum of the file (for integrity verification), never the file itself
If file bytes were ever routed through API Gateway + Lambda proxy integration instead (not this design)Yes — API Gateway/Lambda payloads are JSON under the hood, a text format, so a binary body would need base64 encoding on the way in and decoding on the way out. This is the exact overhead the presigned-URL pattern exists to avoid.

So, directly: in this project's actual design, the PDF's bytes are never encoded or decoded at all, anywhere. That's not an accident — it's one of the concrete reasons presigned direct-to-S3 upload was the recommended pattern in the first place.

Non-functional considerations specific to this milestone

ConcernHow this design addresses it
ReliabilitySQS's own redrive policy (maxReceiveCount) retries a failed message automatically, then moves it to the DLQ once exhausted — nothing silently disappears, and the retry/DLQ mechanism is one native SQS feature, not bolted onto Lambda separately
ResilienceLambda invocations are independent and stateless — one document's failure never blocks another's processing, unlike today's synchronous in-request indexing
IdempotencyRe-processing the same S3 object (a Lambda retry, or a replayed DLQ message) must not double-index — reuse the existing content-hash dedup (Phase 16) inside pipeline.py, already built for exactly this
ScalabilityLambda scales per-invocation automatically — a batch of 100 uploaded documents triggers up to 100 concurrent Lambda executions (bounded by account concurrency limits, worth setting a reserved concurrency to protect Pinecone/Postgres from a thundering herd)
MonitoringCloudWatch alarm on DLQ depth (>0 messages = something is failing and needs attention) and on Lambda error rate — neither exists for any part of this system yet (verified: zero CloudWatch alarms currently configured), so this is also where alarming gets introduced for the first time
LoggingLambda logs go to their own CloudWatch log group automatically — worth using structured (JSON) log lines from the start here, unlike the plain-text format the rest of this project currently uses, so Logs Insights queries are possible without regex parsing

See the NFR & Resilience page for the whole-system view — rate limiting, retry/backoff on LLM calls, and load balancing are cross-cutting concerns, not specific to this milestone, so they're covered there rather than duplicated here.

How the Lambda's own code gets deployed (separate from the data flow above)

The diagrams above show how one document flows through this system at runtime. This is a different question: how does a code change to index_document_handler.py (or anything it imports, including ai/doc_processing/pipeline.py) actually reach the running Lambda? Its own workflow, .github/workflows/deploy-lambda.yml - separate from the main app's deploy.yml, both triggered independently by the same push to master.

Why this is a separate workflow at all, not folded into deploy.yml: before this existed, every Lambda deploy was a manual docker buildx build + ECR push + aws lambda update-function-code run by hand - and this project already shipped a real backend fix once that the Lambda silently never received, because nothing kept the two in sync. This workflow is what prevents that specific, already-happened failure from recurring.

Testing considerations — what was actually run, not just planned

  • Unit tests — 6 tests in tests/hrb_chatbot/lambda_handlers/, all faked (no real AWS call), including a regression test for the asyncio bug found below
  • Real integration test, no presigned URL yet (that's Phase 89) — a direct aws s3 cp to the bucket, confirmed via CloudWatch logs and independently via the live production API that the Lambda wrote to the exact same Postgres/Pinecone the running app reads from
  • Idempotency test — re-uploaded to the same key; chunk_count stayed at 1, not 2 (document_version incremented instead) — a clean re-index, not a duplicate
  • Failure-path test — direct aws lambda invoke with a nonexistent S3 key; handler reported a clean batchItemFailures entry, no crash. The full redrive-to-DLQ timing (3 retries × 360s ≈ 18 min) itself was not run to completion — only the per-attempt failure signal was confirmed.
  • Concurrency/multi-document test, run twice — 3 documents uploaded within the same second. SQS batched 2 of the 3 into one invocation; that invocation processed its records sequentially, not in parallel (a plain for loop) — this project doesn't control SQS's own batching, only a batch_size cap. First run found a real bug (below); fixed, rebuilt, and the identical test re-run clean the second time.
  • Golden dataset gate run after ingesting through this path — not done yet; natural to bundle with Phase 89 once there's a real client-facing path to test end to end
Real bug found by the concurrency test, fixed same day: the handler originally called asyncio.run() once per SQS record. The Redis-backed embedding cache caches its client on a long-lived singleton (DBGateway), which outlives any single asyncio.run() call — the second call's fresh event loop left that cached client pointing at the now-closed first loop, raising RuntimeError: Event loop is closed on every record after the first in a batch. Phase 84's own fail-open wrapping caught it (logged a warning, fell back to a real OpenAI call) — no document failed, no data was wrong, but the cache was silently dead for 2nd+ records and every occurrence logged at ERROR level. Fixed by wrapping the whole batch in one asyncio.run() instead of one per record. Re-ran the identical live test afterward: zero errors. Full writeup in RAG-ROADMAP.md's Phase 88 entry.
Two more things found, not fixed here, by design:
  • No input validation. The Lambda doesn't check file type, size, or cross-document content-hash dedup — it indexes whatever's at the S3 key. Low risk today since nothing can reach this bucket except a direct AWS call; Phase 89's presigned-upload endpoint is the right place to add this, not this handler.
  • Update, Phase 90: it does run locally now — against real S3/SQS, no emulation. scripts/run_local_lambda_worker.py polls a real SQS queue directly from localhost and runs the Lambda's own handler as a local process, indexing into local SQLite/ChromaDB — the same real-AWS-SDK-from-localhost pattern as any app that connects out to S3/SQS from a developer's machine (confirmed live). Uses its own separate dev bucket/queue (hrb-chatbot-kb-uploads-dev / hrb-chatbot-ingest-queue-dev), not production's — an earlier attempt pointed at the real production queue and the real deployed Lambda's own SQS trigger almost always won the race for each message (disabling the event source mapping wasn't even reliably fast enough to work around it). Separate dev resources remove the race entirely rather than working around it. See the script's own docstring and RAG-ROADMAP.md's Phase 90 entry for the full story.
