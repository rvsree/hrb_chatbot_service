How was the source built for deployment?

Python has no compile step and no single build artifact like a .jar. The closest equivalent is a two-stage Docker build, which plays the same role your Maven/Gradle build + Dockerfile combo does.

The actual pipeline (CI/CD)

This all happens inside .github/workflows/deploy.yml, triggered on every push to master — think of it as a Jenkins/GitHub Actions pipeline you'd wire for a Spring Boot app, just targeting App Runner instead of Kubernetes/EC2:

1. checkout
2. configure AWS credentials (IAM user scoped to just this job)
3. docker login to ECR
4. docker buildx build --provenance=false --sbom=false ...push=true
   (two flags that matter a lot here — App Runner silently fails
    to start a container built without them; see AWS-DEVOPS-RUNBOOK.md)
5. aws apprunner start-deployment   # tell App Runner to pull + redeploy
6. poll Service.Status until RUNNING (not instant — takes a minute or two)
7. smoke test: curl the live /ping endpoint for a real 200
No AutoDeploymentsEnabled — unlike Kubernetes watching a registry tag, App Runner does not auto-redeploy just because a new image landed in ECR. Step 5 above is what actually triggers it; this is deliberate, confirmed during this project's Phase 10.

Checking health, logs, and deployment status

1. Is the app actually healthy right now?

Skip the console for this — hit the endpoints directly, same as you'd hit Spring Boot Actuator's /actuator/health:

GET https://mrgysvt6ye.us-east-1.awsapprunner.com/ping    # liveness only, instant, no cost
GET https://mrgysvt6ye.us-east-1.awsapprunner.com/health  # real check of every backend (LLM, vector DB, metadata DB)

2. Was the last deployment successful? (AWS Console)

  1. console.aws.amazon.com → search App Runner
  2. Click hrb-chatbot
  3. Overview tab — top-right status badge: Running (good), Operation in progress (mid-deploy), or Create failed/Deploy failed
  4. Activity tab — deployment history, one row per deploy, with timestamps and pass/fail — your App Runner equivalent of a Jenkins build history, specifically for what got deployed and when

3. Reading application logs (your own structlog/print output)

  1. App Runner service page → Logs tab
  2. Two log groups, same split you'd see between a container orchestrator's own events vs. your app's catalina.out:
    • .../service — App Runner's own system events (image pulled, deployment started/failed) — this is all you get if the container never starts at all
    • .../application — your actual FastAPI/uvicorn stdout — request logs, exceptions, everything get_logger() writes
  3. Or via CloudWatch directly: CloudWatch → Log groups → /aws/apprunner/hrb-chatbot/<service-id>/application
Known gap, from the runbook: if a deploy fails because the container itself never starts, there's no /application log at all — only the generic /service log, which won't say why. That pattern almost always means something about the image itself (manifest format, missing entrypoint), not your Python code.

4. Traffic / performance metrics

App Runner service page → Metrics tab — request count, 4xx/5xx rate, latency (p50/p99), CPU/memory. This is the AWS-managed equivalent of wiring Micrometer + Prometheus/Grafana yourself in a Spring Boot app — you get it for free here, just less customizable.

5. Did the GitHub Actions deploy itself succeed?

gh run list --workflow=deploy.yml --limit 5
gh run view <run-id> --log-failed   # only on failure, see exactly which step broke

Your Jenkins "build history" equivalent — gh CLI is now installed and authenticated on this machine, so this works directly from the terminal instead of browser navigation.
