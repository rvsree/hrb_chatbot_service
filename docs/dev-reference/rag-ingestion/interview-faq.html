Describe the stages of a document ingestion pipeline.
  • Discover (find files, skip unchanged ones) -> extract (PDF reader, Word parser, or OCR) -> clean (strip headers/footers/boilerplate) -> chunk -> embed -> store (chunks + metadata in the vector store). Track status per file so one bad document doesn't stop the whole run.
builtai/doc_processing/pipeline.py runs exactly this: extract -> chunk -> embed -> index, synchronously, in one call per upload (POST /v1/genai-rag/ingest-document/documents).
What makes PDFs hard to process?
  • A PDF describes where to draw text, not what it means - no reliable paragraph/heading/reading order. Two-column layouts mix together, tables flatten and lose the link between a number and its header, scanned PDFs are just images needing OCR, and headers/footers repeat on every page and pollute chunks. Always eyeball extracted text before trusting the pipeline.
differentReal extraction is pypdf's PdfReader (extract_text_from_pdf(), text_chunker.py) - plain per-page text extraction, not a layout-aware parser. No OCR path exists for scanned PDFs - an image-only PDF would extract empty text today.
Tables come out garbled and numeric answers are wrong - what do you do?
  • The reader is losing the link between each number and its column heading. Use a layout-aware extractor, convert each table to markdown/CSV so headers stay attached to values, keep each table as one chunk (never split rows from headers), and for real number-crunching give the agent a query tool over a real table instead of doing arithmetic in a prompt.
builtReal: extract_text_from_pdf()'s own docstring - "every page's text plus any tables, appended as markdown blocks" - keeps headers attached to values exactly this way.
A document gets edited - what has to happen in your pipeline?
  • Compare a content hash to the stored one - if it matches, skip. If changed, re-extract and re-chunk; ideally hash each chunk too and only re-embed/replace what actually changed, leaving the rest alone, so a one-line edit to a 100-page document doesn't re-embed everything.
differentReal dedup is whole-document content-hash based (compute_content_hash(), services/documents_service.py) - identical re-upload is skipped. An edited document is re-uploaded as a new version that supersedes the old one (is_current/supersedes, Phase 16/44) - the whole new document gets re-chunked and re-embedded, not a chunk-level delta.
Your ingestion pipeline takes 4 seconds and the target is 1.5 - where do you look?
  • Measure each stage first - usually embedding generation or LLM-based extraction dominates. Batch embedding calls instead of one-at-a-time, run independent stages (e.g. multiple files) in parallel, and consider a smaller/faster model for routine documents.
differentBatch embedding is real (embedding_generator.py embeds all of a document's chunks in one call). No per-stage latency breakdown is returned for ingestion the way query latency is (latency_ms on query responses) - ingestion is synchronous, in-request, with no async/parallel-file path (see S3-ASYNC-UPLOAD-DESIGN.md - design only, not implemented).
How do you keep the index fresh when documents change all the time?
  • Switch from nightly full crawls to reacting to change events; only re-embed chunks that actually changed, using chunk hashes. Track freshness as a metric (how old is the index vs. the source) and handle deletions quickly - showing removed content is worse than showing stale content.
differentFreshness today is request-driven, not event-driven - a document only re-indexes when someone re-uploads it through the ingest endpoint. No freshness/staleness metric is tracked. Deletion is real and immediate though: DELETE /v1/genai-rag/ingest-document/documents/{{id}} removes the document and its chunks together.
What should the ingestion step save so you can filter searches later?
  • Turn each document into typed blocks (heading, paragraph, table) and chunk from those, not from one long string. Save doc_type, section_path, page, effective_date, and access tags on every chunk - every one becomes a search filter later. Save the parsed intermediate form too, so re-chunking doesn't mean re-reading every PDF.
builtReal metadata fields exist per document/chunk - doc_category, department, doc_description, effective_date (document_metadata_extractor.py), section_id (vector_indexer.py) - used by Self-Query filtering at retrieval time (Phase 19-20). No separately-saved parsed-intermediate form though - a document re-chunk still starts from the stored raw file.
