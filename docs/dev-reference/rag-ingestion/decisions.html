Decouple ingestion from the query path entirely
Context
A synchronous upload ties the API's own request thread to however long indexing takes, and competes with live chat traffic for the same capacity.
Decision
Move large/async uploads to presigned S3 + event-driven Lambda - the API process never touches the file bytes or blocks on indexing.
Alternative
Keep everything synchronous, just raise timeouts - doesn't fix the underlying coupling, only delays when it becomes a problem.
Why
Upload/index load and query load have different shapes - decoupling lets each scale on its own trigger.
Trade-off
Real added infrastructure (queue, Lambda, DLQ, a second deploy target) for a benefit that mostly matters at a scale this project isn't at yet.
SQS as the primary trigger, not direct S3→Lambda
Context
S3 can invoke Lambda directly on an object-created event, no queue required.
Decision
S3 notifies SQS, and Lambda's own event-source mapping polls the queue - not a direct S3-to-Lambda trigger.
Alternative
Direct S3→Lambda - simpler, one less resource, but no buffering: a burst of uploads spikes concurrent invocations directly.
Why
A queue gives real backpressure, and SQS's own visibility-timeout/retry becomes the retry mechanism for free.
Trade-off
One more piece of infrastructure to provision and tune (visibility timeout, max receives).
Async upload is additive, not a replacement
Context
The original design intended the async path to eventually replace the synchronous one.
Decision
Both stay - the async endpoint is a separate route; the synchronous one, its tests, and its CI usage are untouched.
Alternative
Cut over fully once the async path works - cleaner long-term, but would retire a working path in favor of a newer one with real, just-found gaps (no input validation at the time, no local test path).
Why
Nothing required an immediate cutover, and the synchronous path still serves its real use - interactive small/batch uploads.
Trade-off
Two upload code paths to maintain indefinitely, not one.
