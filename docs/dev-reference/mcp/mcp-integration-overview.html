MCP Integration Overview

Three phases shipped and live-verified against the real, running hrb_lms_mcp server this session; one more parked as a spec for later. Each phase is a separate concern - routing decides when to call MCP, the registry tracks what's reachable, auth decides who's allowed.

A fixed keyword list ("leave balance", "pto balance", "leave history", ...) against the query text. No NLU, no intent classifier - the honest, simple version, not the final design.

Real LLM tool selection (Phase 55) - the model reads each tool's description and decides, no keyword list. Verified live: correctly chose GetLeaveBalance for a balance question, SearchKnowledgeBase for a policy question.

Failure handling
Any MCP failure (network, auth, tool error) is caught and falls back to normal RAG, not a 500 - the pipeline never assumes MCP is available.
03
Phase 50 - Server/Tool Registryreused tables, not new ones - the same pattern as the user's own v1 project
Live

At every hrb_chatbot_service startup, a real tools/list call populates hr_chatbot.app_tracking's existing (previously empty) mcp_server_registry/mcp_tools_registry/mcp_server_connections tables - not hand-maintained, not simulated. A down server records a failed connection attempt and the app starts anyway.

Real numbers, last verified run
1 server, 6 tools, connection_status: connected, consecutive_failures: 0, real latency logged (796ms one run).
Real bugs found live
3 CHECK constraints on the existing tables rejected values that seemed reasonable ('streamable_http', 'configured', 'failed') - only discoverable by actually inserting, not documented anywhere.

Phase 52 - Analytics MCP Serverparking-lot spec, researched, not started
Planned

A third MCP server for aggregate/historical questions ("what % of PTO goes unused by department") that Phase 49's per-employee tools structurally can't answer - NL2SQL over hrb_emp_lms.leave_balances/leave_requests (already real data), Postgres first, Snowflake later. Researched against real 2026 patterns (Oracle/Microsoft/Google Cloud all shipped official NL2SQL MCP servers) - full spec in docs/agent-reference/RAG-ROADMAP.md Phase 52, deferred until ReAct orchestration exists to route to it.

Whatever OAuth2 pattern secures this later should extend Phase 53's, not reinvent client-credentials per MCP server - already flagged as an open question in the Phase 52 spec.
