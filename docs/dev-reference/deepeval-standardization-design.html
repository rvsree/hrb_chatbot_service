DeepEval Standardization

Replacing the hand-rolled LLM-as-judge prompts with DeepEval, for both live queries and the offline golden dataset - a deliberate, user-approved deviation from the IK FDE Module 5 courseware pattern.

Spec only - implementation explicitly held New dependency, needs approval before any code Touches the live hot path of 3 pipelines
01

Why this is a deviation, and why it's fine

This project's own standing rule is implementation fidelity to the IK FDE Module 5 courseware, which teaches hand-rolled LLM-as-judge prompts, not a third-party eval library - golden_dataset_harness.py's own docstring says so explicitly: "ported directly from the IK FDE cohort's modules/5_evaluation/demo.py, not DeepEval's built-in metrics." Introducing DeepEval reverses that, on both the live path and the offline harness.

Why this is still the right call

The user asked for this explicitly, named the courseware-fidelity tradeoff themselves, and chose to standardize on DeepEval anyway - "let's standardize this." That's an informed, deliberate override, not a silent drift this project's own rules would otherwise flag. Recorded here so the reasoning survives past this conversation.

02

What DeepEval actually provides - researched, not assumed

Confirmed against DeepEval's own docs (deepeval.com/docs) and secondary sources, not guessed. Exact class/parameter names should be re-confirmed against the installed version at implementation time - library APIs move.

MetricWhat it checksNeeds
FaithfulnessMetricDoes the answer stick to the retrieved context, or hallucinate?input, actual_output, retrieval_context
AnswerRelevancyMetricDoes the answer address the question asked?input, actual_output
ContextualPrecisionMetricAre the relevant chunks ranked above irrelevant ones?input, retrieval_context, expected_output
ContextualRecallMetricDoes retrieval contain everything needed?input, retrieval_context, expected_output

All are LLM-as-judge under the hood - same category of technique this project's hand-rolled prompts already use, just with DeepEval's own prompts/parsing/scoring instead of this project's own.

No built-in "Completeness" metric

DeepEval ships Faithfulness/AnswerRelevancy/Contextual* but nothing named "Completeness" - this project's own second response-level metric. Built via GEval with a custom criteria string (e.g. "Does the answer fully address every part of the question, without leaving anything unanswered?"), not a built-in class.

Custom judge model required

This project never calls OpenAI's SDK directly - every LLM call goes through common/clients/llm_client/'s multi-provider gateway (GatewayChatModel already adapts it for LangChain's BaseChatModel). DeepEval needs the same treatment: a class implementing DeepEvalBaseLLM's generate()/a_generate(), wrapping this project's own ask() clients - not a new, separate OpenAI integration bypassing the existing gateway.

Async is opt-in, not automatic

A custom metric's default a_measure() just calls the sync measure() - no real concurrency unless implemented properly. For GEval/built-ins this is handled internally, but the custom judge-model wrapper's own a_generate() must be a real async call (reusing this project's existing async ask() clients), or every metric call blocks the event loop regardless of DeepEval's own async_mode setting.

04

The live-F1 problem, concretely

Still true with DeepEval, not solved by switching libraries

ContextualPrecision/ContextualRecall both require expected_output - a known correct answer to compare against. A live, unlabeled question has none. DeepEval doesn't remove this constraint; it just gives a cleaner implementation of the same judge-based approach this project already uses for groundedness/completeness.

The only way to get a live-time retrieval quality number is to treat it as an estimate: judge each retrieved chunk's relevance to the query on the fly (a GEval-style per-chunk relevance call), derive precision/recall/F1 from those judged labels instead of a pre-existing golden set. This is directly buildable on the same infrastructure, but it must be clearly labeled "estimated" in the UI, never shown as if it were the golden dataset's own exact-match F1 - the two numbers answer different questions.

05

Cost and latency - the real number to decide on

One documented real run: a single DeepEval relevancy test case cost about $0.0027 in judge tokens. This project's hand-rolled judge today makes 2 calls per live answer (groundedness + completeness). A full DeepEval swap adds Faithfulness + Completeness(GEval) + AnswerRelevancy as a floor (3 calls, roughly 1.5× today's judge cost/latency) - plus, if live-estimated F1 is built too, one judge call per retrieved chunk (typically top_k=5, so +5 more calls, call volume roughly 4× today's).

Decision needed before implementation starts

Run all of Faithfulness/Completeness/AnswerRelevancy/live-F1-estimate on every live query (highest cost, most complete), or keep live scoring to Faithfulness+Completeness (close to today's cost) and reserve ContextualPrecision/Recall/AnswerRelevancy for the golden dataset only? Not decided here - a real cost/UX tradeoff, not a technical one.

06

Where this plugs in

  • New dependency: deepeval - needs explicit approval (this project's own "no unreviewed libraries" rule) before any pip install, same gate langgraph-checkpoint-postgres went through.
  • New ai/rag_core/deepeval_judge_model.py - the DeepEvalBaseLLM wrapper around this project's existing multi-provider ask() clients, mirroring langchain_chat_model.py's own GatewayChatModel adapter pattern.
  • Replaces rag_pipeline/evaluations/golden_dataset_harness.py's evaluate_groundedness()/evaluate_completeness()/calculate_retrieval_metrics() internals - same function signatures (every call site in pipeline.py/orchestration_agent.py/multi_agent_pipeline.py stays unchanged), DeepEval runs underneath instead of the hand-rolled prompts.
  • New, additive: AnswerRelevancy scoring (doesn't exist today at all) and the live-F1-estimate path (§04), both opt-in per §05's cost decision.
  • Frontend: the Phase 173 Eval Score 3-group layout (Retrieval/Response/Others) already built gets real, non-placeholder values in the Retrieval Score group once this lands.
