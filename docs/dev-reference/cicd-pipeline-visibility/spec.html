spec - intent, scope, personas, acceptance criteria

CI/CD Pipeline Visibility

A real-time, stage-by-stage view of this repo's own GitHub Actions pipeline inside the Admin Dashboard - not a replacement for GitHub Actions, a thin correlated window onto it.

Spec Architecture Design Decisions
1
Problem

User-requested, 2026-10-15/16, from direct experience during today's real deploy: while PR #45/#46's CI and deploy.yml ran, the only way to know what stage it was in, what had passed/failed, or how long it would take was to ask Claude Code to poll gh pr checks/gh run view and narrate it back in chat. That's a real blind spot - no visual status, no direct log link, no build number, no sense of elapsed vs. typical duration, and no inline view of the golden-dataset eval-gate result that matters most for a release decision.

2
Scope
Already live (Phases 181-184)built
  • github_actions_client.py - real GitHub REST API client, never raises, already reads ci.yml/deploy.yml's latest 5 runs each
  • eval_run_store - every real scripts/run_release_gate.py run persisted (decision, scores, flags, per-case detail)
  • Admin Dashboard's CI/Build Status and Eval Runs tabs - read-only tables, manual refresh only
New in this featureto build
  • Per-job, per-step breakdown of one specific run (not just its final conclusion)
  • Auto-refresh while a run is in_progress, stopping once terminal
  • GitHub's real build number (run_number) shown, not just an internal id
  • A run's nearest-preceding eval-gate result surfaced inline, when one exists
  • Direct "view logs" links per job (GitHub's own job URL, not a log re-host)
3
Personas
admin (Engineering Admin)Only role that can see this - same tier as Architecture Docs/Golden Dataset/CI Status today. This is dev-reference tooling, not HR-facing.
4
Functional requirements
  • A horizontal stage stepper for the latest deploy.yml run: Build image → Trigger App Runner → Wait for RUNNING → Smoke test, each stage showing a status icon (queued/running/success/failed), its own duration, and a link to that step's real GitHub Actions log
  • The run's build number (run_number), triggering commit SHA + message, and start timestamp shown together, matching what GitHub's own UI shows
  • While any tracked run is in_progress, the tab polls and updates without a manual refresh; polling stops once the run reaches a terminal state
  • If an eval-gate run exists for the same or a nearby commit, its PASS/REVIEW/BLOCK decision and headline scores show as an optional extra stage, not a blocking one (eval-gate.yml stays workflow_dispatch-only, not on every push)
  • A link out to the full run on github.com is always present as a fallback - this page is a summary, never a replacement for GitHub's own log viewer
5
Non-functional requirements
  • Polling must respect GitHub's REST API rate limit (5,000 req/hr authenticated) - a single admin's browser tab polling every 10-15s is well within budget; no shared polling across sessions needed at this scale
  • Graceful degradation: if the GitHub API is unreachable or GITHUB_TOKEN is unset, the tab shows a clear message, never a blank screen or stack trace - matches github_actions_client.py's existing never-raises contract
  • No new infrastructure - no WebSocket server, no message queue, no log storage; GitHub Actions stays the single source of truth for both state and logs
6
Acceptance criteria
Live progress, no manual refreshplanned

Watching a real deploy, the stepper updates stage-by-stage without the admin clicking refresh.

Build # and timestamp match GitHubplanned

The number shown is the exact run_number GitHub's own UI shows for that run.

One click to real logsplanned

Every stage links directly to its own GitHub Actions job log, not a generic run page.

Eval-gate result visible when presentplanned

A release's golden-dataset decision is visible without switching to the separate Eval Runs tab.

7
Out of scope
Re-hosting or storing GitHub Actions logs ourselves; a real-time push/WebSocket channel (polling is enough for one admin's own browser tab); multi-repo aggregation (this project has 2 repos with different deploy mechanisms - hrb_chatbot_v2's GitHub Actions and hrb_chatbot_ui's manual S3 sync - only the former has a pipeline to visualize); wiring eval-gate.yml into every push (a separate, already-known, deliberately-deferred decision - see BACKLOG.md).
