2
Polling design
1

On tab open, fetch the latest run per workflow via the existing GET /v1/admin/ci-status, then fetch job detail for the most recent run via the new endpoint below.

2

If that run's status is in_progress, poll the jobs endpoint every 10s (matches this project's existing MCP circuit-breaker cooldown order of magnitude - no new interval convention invented).

3

Once the run reaches a terminal state (completed/cancelled), polling stops - the same "stop once terminal" pattern already used by this session's own CI-watch loop.

4

A manual "Refresh" button stays available regardless, matching every other Admin Dashboard tab's existing convention - polling is a convenience, not the only way to update.

Backed by GitHub's own GET /repos/{owner}/{repo}/actions/runs/{run_id}/jobs - one more read-only call alongside github_actions_client.py's existing ones, same never-raises contract. nearest_eval_gate_run is a best-effort lookup in eval_run_store by nearest timestamp before the deploy's created_at - null when none exists, never an error.

4
Error and empty states
  • No GITHUB_TOKEN configured: the tab shows the same "CI status unavailable" message the existing CI Status tab already shows today - no new failure mode introduced
  • GitHub API rate-limited or unreachable: one retry on the next poll tick, then a visible (not silent) "couldn't refresh - last known state shown" banner, timestamped
  • No runs yet for a workflow: an empty state, not a blank table - matches every other tab's existing "no X yet" convention
