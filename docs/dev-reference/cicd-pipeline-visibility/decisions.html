Spec Architecture Design Decisions
CI-1Buy vs build - 4 options evaluated
OptionCostFit for this project
A. Use GitHub Actions UI directly $0, zero build Already exactly what was used today (gh pr checks, gh run view, the Actions tab). Full log fidelity, real-time, zero maintenance. Gap: lives outside the app, no correlation with golden-dataset results, requires a context switch away from the admin dashboard.
B. Third-party CI dashboard SaaS
(BuildPulse, CircleCI Insights, etc.)		 Per-seat/usage pricing Built for teams with budget and multi-repo portfolios. This is a solo portfolio project with 2 repos and one CI provider already working - paying for a product to watch a system that already emits everything needed over a free REST API is scope and cost mismatch.
C. Self-hosted OSS dashboard
(Grafana + a GitHub Actions exporter)		 $0 license, real infra/ops cost Adds a service to provision, secure, and keep patched, duplicating auth/RBAC this project's own admin dashboard already has. Redundant infrastructure for a single admin's own use.
D. Extend the existing Admin Dashboard
(this feature's actual proposal)		 Engineering time only, reuses live code chosen
GitHub Actions stays the data source (buy - it's already free and already integrated via github_actions_client.py); only the thin correlated view is built, reusing this session's own Phase 181-184 work and the app's existing auth. One new endpoint, one new component - not a new system.
CI-2Polling, not WebSockets or a push channel
Decision
A 10s client-side poll of the new jobs endpoint while a run is in_progress, stopped once terminal.
Why
Matches the user's own stated goal - "simple one to begin with." A single admin's own browser tab is the only consumer; there's no second viewer to fan out to, and GitHub's REST API has no native webhook delivery into this app today (that would mean standing up a public webhook receiver - new attack surface and new infra for a one-admin use case).
Trade-off
Up to 10s of staleness vs. a true push channel - acceptable for watching a 2-8 minute deploy, not acceptable if this ever needs to notify someone who isn't looking at the tab (out of scope - see Spec).
CI-3Build number = GitHub's real run_number
Decision
Show GitHub's own run_number (the number GitHub's UI itself labels "#214") as the build number, not an internally generated counter.
Why
A second numbering scheme for the same run would be a constant source of confusion ("which #214 do you mean") the moment someone cross-references this view against GitHub's own UI or a Slack notification - one number, one source.
CI-4No log re-hosting, ever
Decision
Every "view log" link points at GitHub's own job URL. Nothing fetches, stores, or displays raw log text inside this app.
Why
GitHub already retains logs with correct access control, search, and download - re-hosting them would mean this app owning log retention policy, storage cost, and a second copy of something sensitive (build logs can contain stack traces, partial env dumps) to secure. Directly against this project's own "don't scatter a second source of truth" convention (see CLAUDE.md's gateway/enum pattern reasoning).
CI-5Feasibility verdict

High. The external dependency (GitHub Actions REST API) is free, already authenticated (GITHUB_TOKEN, read-only actions:read scope), and already has a working client in this codebase. The remaining work - one new client method, one new route, one new React component with a poll hook - is a scoped, single-phase addition matching the size of Phase 183 that already shipped this session, not a new subsystem.
