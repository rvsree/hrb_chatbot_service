Why both hrb_chatbot_service and rag_retrieval_service are "live": the Gateway's BACKEND_SERVICE_URL still points at hrb_chatbot_service today — that's genuinely what answers a real retrieval query right now. rag_retrieval_service is a complete, independently-deployed, independently-verified parallel implementation of the same retrieval logic, proven via a real multi-turn Playwright suite against its own live URL — it just isn't the one in the request path yet. Cutting it over is a separate, deliberate decision, not a readiness gap.

2Shared infrastructure — what the backend services underneath actually touch

Neon Postgresone flat public schema in production — the schema-per-domain split (Phase 251) is local-only, see §3
Redisrate-limit state (Gateway), answer cache + STM/LTM conversation memory (chatbot/retrieval)
Pineconevector DB — ingestion writes, retrieval reads, same index
S3 + CloudFrontKB document uploads, leave-docs, and the UI's own static hosting
⚠
Real incident, 2026-10-23: a connection-option change meant to support the schema-per-domain split shipped to production independently of the actual migration SQL — Neon's pooled connection endpoint rejects the search_path option outright, breaking every production query for several minutes before being hotfixed. Production Postgres is still one flat public schema, same as before — see RAG-ROADMAP.md's Phase 251 entry for the full incident.

3Shared library — not a deployed service, but every backend here depends on it

hrb-common-libsconnectors + observability, 10 pip extras in one git-tag-pinned repo (v0.4.0) — not ~10 separate packages, see microservices-interface-matrix.html §2

Used by hrb_api_gateway_service, rag_ingestion_service, rag_retrieval_service, and hrb_platform_components — every repo built during the actual split. hrb_chatbot_service (pre-split) and hrb_chatbot_ui (frontend, different language) don't depend on it.
