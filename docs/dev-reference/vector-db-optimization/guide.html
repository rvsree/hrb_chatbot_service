01
Choosing a chunking strategy

6 strategies, auto-selected by decide_chunking_strategy() when not given explicitly - picks based on document length (very short documents skip chunking entirely; very long ones get a larger chunk size).

StrategyWhat it doesChunk-count tendencyRetrieval impact
recursive (default)Paragraph → line → sentence breaks, falls back to a hard cut.Many, similarly-sized chunks.Balanced precision/completeness - a boundary can still split a fact across two chunks.
fixedSplits on a single separator only.Many, similarly-sized chunks.Similar to recursive, slightly higher chance of a mid-sentence cut.
semanticAn embedding call decides where topics shift - no size ceiling of its own, capped by a safety-net re-split.Fewer, topic-grouped chunks.Better completeness on broad questions, can bury a narrow fact in a larger chunk. Costs a real embedding call per sentence.
markdown / htmlSplits on markdown headers or HTML heading tags.Depends entirely on real headers existing.Can hurt precision badly if the document has none - most PDF-extracted text has neither.
noneNo deliberate splitting - one chunk, capped only as a safety net.Exactly 1 chunk (or a few, for a very large document).Best completeness, zero targeted retrieval - every query against this document returns the same chunk(s).
document_structureThis project's own real section headings ("Section 2: Eligibility", "2.1 ...") - confirmed by regex count against the real KB PDFs, not a generic heading guess.Follows the document's real sections.Better completeness for section-level questions, when real headings exist.
A table is never split across two chunks - table_extractor.py pulls [TABLE]...[/TABLE] blocks out before chunking runs, regardless of strategy.
02
Chunk size and overlap - what actually moves the needle
Chunk size (default 1000 chars)
Smaller = more precise for narrow fact lookups, but loses surrounding context. Larger = keeps context together, but a too-large chunk dilutes its own embedding and hurts retrieval precision - the same problem re-indexing with a different strategy is meant to fix.
Overlap (default 150 chars, ~15%)
Repeats a few characters between consecutive chunks so a sentence right on a boundary still appears whole in at least one chunk. Too little risks losing a boundary fact; too much just duplicates content across chunks, wasting index space for no retrieval gain.
Document-length thresholds
Below DEFAULT_CHUNK_SIZE (1000 chars), a document fits in one chunk regardless of strategy. Above CHUNK_LARGE_DOCUMENT_MIN_LENGTH (10,000 chars default), the default size would fragment it into 10+ tiny, low-context chunks - auto-selection switches to a larger size instead.
03
When to actually re-index a document
1Embedding model mismatch - the clearest, UI-surfaced trigger. A document indexed with one embedding model but queried against a different active one shows a real "⚠ mismatch" warning in the Documents table today - retrieval against that document is unreliable until it's re-indexed with the current model.
2Retrieval quality looks wrong for one document specifically - a narrow-fact query never surfaces a document you know contains the answer. Try document_structure (if the doc has real section headings) or a smaller chunk size before assuming the embedding model itself is the problem.
3A document's own source content changed - re-uploading via "replace" (not a fresh upload) marks the old version not-current and indexes the new file as current, handled by vector_indexer.py's supersede logic automatically, not something to trigger by hand.
Re-indexing is a full re-embed, not incremental - every chunk for that document is deleted and rewritten (old chunk ids computed, stale ones removed, new ones written), confirmed in write_chunks(). There's no partial/delta re-index - budget for a real embedding-API cost per re-index, same as the original upload.
04
Vector DB choice: ChromaDB vs. Pinecone
ChromaDB - local dev default
File-based, no external account needed, zero cost - the right choice for local development and testing. Cannot run in AWS Lambda's ephemeral filesystem (a real constraint this project hit directly), so it's not an option for any serverless ingestion path.
Pinecone - the real production backend
RAG_VECTOR_DB=pinecone is this project's actual live configuration in production. A managed, hosted service - usable from Lambda, no filesystem constraint - at the cost of a real external dependency and its own API latency per call.
Switching the active vector DB is a config value (RAG_VECTOR_DB), not a code change - but switching does NOT migrate existing indexed chunks between backends. Every document indexed under the old backend needs a real re-index under the new one before it's queryable there.
