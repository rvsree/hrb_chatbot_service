Retrieval Strategies

4 search strategies + 2 optional LangChain rewriting classes - the shared retrieval layer every mode uses. 5th pilot in the series.

Spec Architecture Design Decisions Interview FAQ
1
Intent

4 selectable search strategies behind one gateway dict, plus 2 optional LangChain retrieval-rewriting classes layered on top of any of them - the "how do we find the right chunks" layer every retrieval mode shares.

2
Scope
Live today - 4 strategiesbuilt
  • similarity - plain vector cosine/distance search
  • mmr - Maximal Marginal Relevance, trades some relevance for result diversity (lambda_mult tunable)
  • keyword - plain BM25 lexical ranking (rank_bm25) over every current chunk - good for exact terms/acronyms vector search can miss
  • hybrid - BM25 + vector combined via Reciprocal Rank Fusion
Live today - optional rewriting layerbuilt
  • use_multi_query - LangChain's own MultiQueryRetriever, generates several query variants and unions the results
  • use_self_query - LangChain's own SelfQueryRetriever, parses metadata filters out of the query text itself
  • Both need a real LangChain BaseChatModel - served via GatewayChatModel, this project's own adapter over its multi-provider ask() clients, not a per-provider LangChain package
3
Personas

Not a user-facing feature on its own - every retrieval mode (genai-rag, single/multi-agentic-rag) uses this layer internally. The "Retrieval:" dropdown exposed in the UI's tuning bar is the one direct touchpoint a caller has with it.

4
Acceptance criteria
All 4 strategies real, not stubbedmet

Each has its own real implementation - keyword/hybrid aren't a thin wrapper around similarity search.

Provider-agnostic rewritingmet

use_multi_query/use_self_query work with any of this project's own LLM providers via the gateway adapter, not locked to one.

Unknown strategy name rejected cleanlymet

An unrecognized search_strategy value is a clean 422 at the API boundary, not a silent fallback or a deep pipeline failure.
