Embeddings & Similarity4 cards
What is an embedding, and why does cosine similarity work as the comparison metric?
  • A vector encoding of meaning - similar text gets similar vectors even with almost no shared words. Cosine similarity compares direction, not magnitude, so it ignores text length and matches how most embedding models were trained to begin with.
builtDelegated to the vector store (Chroma/Pinecone) rather than custom-coded - matches the course's own recommendation that this is the right default, not something to reinvent.
How do you choose an embedding model?
  • Shortlist from public benchmarks, then test on a few hundred real questions from your own data - that's what actually decides it. Check dimension count (storage/speed), max input length against your chunk size, and whether switching later means re-embedding everything.
builttext-embedding-3-small throughout - no side-by-side model comparison was run as its own feature; the choice was made once and used consistently.
How do embeddings handle company jargon and acronyms?
  • Badly - rare terms were barely seen in training and get matched on spelling, not meaning. Fixes: keep a glossary and expand acronyms, add keyword search alongside embeddings (exactly where embeddings fail), fine-tune on your own data if you have enough.
builtThe "add keyword search alongside embeddings" fix is real here - search_hybrid() (BM25 + vector) exists specifically to catch exact rare terms embeddings miss. No glossary/acronym-expansion step or fine-tuned embedding model.
What's a good embedding-choice checklist beyond the raw benchmark score?
  • Hosted API vs. self-hosted (cost, speed, whether data can leave your network), language support if documents aren't all English, and the real hidden cost: switching models later means re-embedding your entire index, so choose deliberately rather than casually.
noneNo embedding-model migration tooling exists - switching today would mean a manual full re-ingest, with no side-by-side old/new index comparison step built.
Hybrid Search, Reranking & Multi-Query4 cards
What is hybrid search, and how do you merge differently-scaled scores?
  • Running keyword (BM25, great at exact matches) and embedding search (great at meaning) together, since each covers what the other misses. You can't just add the scores - BM25 is unbounded, embedding similarity is 0-1 - so use Reciprocal Rank Fusion: score = sum(1 / (k + rank)) across lists, which needs no tuning.
builtReal, live - search_hybrid() (bm25_search.py, Phase 131) runs BM25Okapi + vector similarity and merges with RRF, RRF_K = 60 - the standard constant, matching the textbook value exactly.
What is a reranker, and where does it sit in the pipeline?
  • A cross-encoder that reads the question and one chunk together, so it judges relevance more accurately than embedding search alone (which never sees them together). Sits between search and the prompt: retrieve wide, rerank, keep the best few - too slow to run over the whole corpus, which is why you still retrieve first.
noneNo cross-encoder reranking step exists. MMR (search_mmr()) is the closest built equivalent, but it optimizes for diversity among already-retrieved results, not relevance re-scoring - a genuinely different mechanism, not a lesser version of the same one.
What is multi-query retrieval, and when is it worth the extra cost?
  • Turn one question into 3-4 differently-worded versions in a single LLM call, search all of them in parallel, merge with RRF and de-dupe. Best for vague questions; a waste of a call on precise ones, so turn it on selectively.
builtLangChain's own MultiQueryRetriever (Phase 20), opt-in via RagQueryRequest.use_multi_query - a real library class layered on top, not hand-written, exactly because the rewriting logic isn't something worth reinventing.
The model keeps picking the wrong search strategy, or search looks fine but answers are still wrong - how do you find where it broke?
  • Check the three RAG measures separately: were the retrieved chunks relevant, is every claim grounded in them, does the answer address the question. Bad context means fix search; good context but a wrong answer means fix the prompt - don't guess which layer broke.
builtAll three are real, separately-scored metrics here (evaluate_groundedness/evaluate_completeness plus precision/recall, DeepEval-backed) - returned on every live answer, not just in offline eval.
Vector Stores, Multi-Tenancy & Caching6 cards
What is a vector store, and FAISS or Chroma - how would you choose?
  • A database built to store embeddings and search by similarity rather than exact match. FAISS is a fast search library with no built-in metadata filtering or persistence handling; Chroma wraps a vector index with filtering/collections/storage included - the easier default under a few million chunks.
builtBoth real, selectable via VectorDB enum - ChromaDB (local default) and Pinecone (hosted, metadata-filterable) behind one gateway interface. No FAISS - skipped entirely since this project always wanted managed filtering/persistence, exactly the gap FAISS leaves open.
What metadata should you store with each chunk?
  • source_id/source_path for citations, chunk_index for ordering, tenant/access tags, updated_at, doc_type, and the embedding model name - adding metadata later means re-processing everything, so decide early.
builtReal fields: doc_category/department/doc_description/effective_date/section_id, used by Self-Query filtering. No embedding-model-name field is stored per chunk, since only one model has ever been used.
How do you keep one customer's documents from being visible to another?
  • Store a tenant ID on every chunk, apply it as a filter inside the search query (filtering after results come back can silently leave you with fewer results or none), make a missing tenant ID an error rather than a search-everything fallback, and write a test proving a query without one returns nothing.
noneNot applicable - this is a single-tenant deployment (one organization's HR documents), so no tenant-filtering mechanism exists. is_current filtering plays an analogous "always applied inside the query" role for document versioning, not tenancy.
How do you switch to a new embedding model without downtime?
  • You can't mix models in one index - their numbers mean different things. Build a second index with the new model, backfill while the old one keeps serving, compare both on a real test set, then move traffic gradually behind a flag, keeping the old index ready to roll back to.
noneNo dual-index migration path exists - switching the embedding model today would mean a manual full re-ingest with real downtime, since only one collection/namespace is ever active per vector DB.
Where can you safely cache in a RAG system?
  • Question embeddings (safe, long-lived, no document data). Search results, keyed on question + tenant + filters, with an index-version bump whenever documents change. Full answers with a short expiry - most valuable, most risky if stale. Any cache built from document content must include the tenant ID in its key, enforced in the cache wrapper, not left to callers to remember.
differentReal full-answer caching exists (Redis, answer_cache.py, Phase 78) - exact-match on the normalized query plus every search parameter, shared across all 3 retrieval modes, each pipeline-namespaced. No separate embedding-level or search-result-level cache - just the one answer-level layer, and live-data tool calls (e.g. leave balance) are explicitly excluded from caching since a cached live answer would be a correctness bug.
Should an agent with both API tools and RAG decide which to use, and how?
  • APIs for live, exact, per-user facts (this employee's leave balance); RAG for written knowledge (policies, guides). Expose search as just another tool with a clear description of what it's not for, and keep user-specific live data out of the search index entirely so it physically can't answer a live question from a stale document.
builtExactly this split - try_route_to_mcp() checks first for live-data keywords (leave balance/history) and routes to the real MCP tool; everything else falls through to vector retrieval. Live leave data has never been indexed into the vector store.
Context Injection, Prompting & Multi-Hop8 cards
What is RAG in simple terms?
  • Search your own documents for the relevant bits, then paste them into the prompt - an open-book exam instead of a memory test. Lets the model answer about private/up-to-date data, and lets you show sources so answers can be checked, with no retraining needed.
builtThe whole shape of this project - retrieve real benefits-policy chunks, inject into the prompt, generate grounded in them, return real sources alongside the answer.
What goes in a RAG prompt template besides the retrieved chunks, and how do you stop the model answering from its own knowledge?
  • An instruction to answer only from the provided text, permission to say "I don't know," each chunk clearly numbered and labeled, the question placed last. If the model still ignores retrieved text: first confirm the right chunk was actually retrieved (a search problem, not a prompt problem); if it was, make the instruction more explicit, require a citation on every claim, and verify in code that every citation actually points to a chunk you sent.
builtReal, structured prompt template with few-shot examples (response_generator.py, Phase 48) and real citations returned as sources alongside every answer. No automated check that strips a citation pointing at a chunk never sent, though - that verification step is manual, not code-enforced.
You have 40 relevant chunks and room for 10 - how do you choose?
  • Rerank and keep the top 10, remove near-duplicates (wasted slots), make sure not all 10 come from one document, put the strongest chunks at the start and end (the middle gets less model attention). Summarize-then-inject if it still doesn't fit.
differenttop_k (default 5) bounds the retrieval itself rather than over-fetching and trimming down - no reranking pass, no explicit single-document diversity cap. MMR (when selected as the search strategy) is the closest built mechanism for avoiding redundant results.
Why do follow-up questions break RAG search, and how do you fix it?
  • A follow-up like "what about the enterprise tier?" leaves out the subject - searching that alone matches almost nothing, since the missing context lives in earlier messages, not the current one. Fix: rewrite into a standalone question using the chat history (a small model call) before searching, and log the rewritten question since it's the first thing to check when search fails.
noneA real, honest gap - conversation history is passed to the generation step (chat_history parameter, generate_answer()) but the search query itself is never rewritten using it. A vague follow-up would search literally and likely under-retrieve, even though memory is enabled.
A question needs facts from three different documents - why does RAG struggle, and what's the fix?
  • One search looks for a single chunk matching the whole question - no such chunk exists when each document holds only one piece, so each piece looks like a weak match individually. Fix: break the question into sub-questions, search each separately, combine in one final step.
builtExactly this - decompose() (Phase 130/68) splits a compound question into sub-questions, each retrieved/answered independently, then merged by reviewer_agent.review() when there's more than one.
Two retrieved chunks contradict each other - what should the system do?
  • By default the model just picks one, usually whichever it saw first - bad. Store and send metadata (source, status, effective date) so the model has something to decide with; give it a clear rule (prefer current version, prefer the official source); if it still can't resolve, show both with their dates rather than confidently picking wrong.
differentResolved upstream instead of at answer-time: the is_current/supersedes model means only one version of a policy is ever marked current and searchable by default - so two live, contradicting, equally-current chunks shouldn't normally coexist in the first place, rather than being resolved by the model at generation time.
How do you add citations so users can check an answer, and strip a fake one?
  • Give each prompt chunk a short ID ([1], [2]), tell the model to cite after sentences drawn from it, then look up and show the real source. Remove any ID the model invented that was never actually sent - that's a fake citation, worse than none.
differentReal sources are returned with every answer (the actual retrieved chunks, not model-generated citation markers), which sidesteps the "model invents a citation" failure mode by construction - there's no in-text [1]/[2] marker scheme for the model to fabricate from.
What should happen when the documents genuinely can't answer the question?
  • Search always returns its top results even when nothing is relevant, so you need an explicit check after retrieval - a score threshold or a cheap "could these actually answer this?" check. Say so clearly and suggest rewording rather than sending weak chunks and hoping. Log every refusal; that list is the best guide to what content is actually missing.
builtReal relevance-bar filtering exists at the search layer (_meets_relevance_bar(), Chroma-distance/Pinecone-score thresholds in search_similarity()) - chunks below the bar are dropped before reaching the prompt. No explicit "nothing cleared the bar" refusal log, though.
RAG Evaluation7 cards
What are precision and recall in retrieval, and which matters more?
  • Recall: of everything that could answer the question, how much did you retrieve. Precision: of what you retrieved, how much was actually useful. Recall matters more in RAG - an answer that's never retrieved can never be given; low precision costs tokens and can distract the model, but is survivable.
differentReal, both computed (Phase 55) - but via DeepEval's LLM-judged ContextualPrecision/Recall, not the course's exact-set-based calculation. F1 is computed with the same formula either way.
You have no labelled data - how do you build a RAG test set?
  • Pick a few hundred chunks across your document types, ask an LLM to write a question each chunk alone can answer - free question-and-correct-chunk pairs. Check a sample by hand (generated questions often reuse the chunk's exact wording, which makes search look better than it is), and add real user questions from logs, which are messier on purpose.
builtReal golden dataset exists (resources/golden_dataset/golden_dataset.json, 22 hand-written cases) - hand-curated rather than LLM-generated-then-sampled, so it skips the "reuses the chunk's exact words" risk this question describes, at the cost of being smaller.
What are the three things you measure in a RAG system (the "RAG triad")?
  • Context relevance (were the retrieved chunks about the question), groundedness (is every claim in the answer supported by those chunks), answer relevance (does the answer address what was asked). Together they tell you which layer to fix, not just that something's broken.
builtAll three real and returned live - evaluate_groundedness/evaluate_completeness (DeepEval Faithfulness/AnswerRelevancy) plus precision/recall, scored on every real answer via _score_live_answer(), not just offline.
What is an LLM judge, and how do you know it can be trusted?
  • A model used to score another model's answers - cheap and fast, but it's a model too, so it can be wrong. Validate it by hand-labeling a couple hundred examples including tricky middle cases, comparing agreement against how often two humans agree, and using a different model as judge than the one that wrote the answer.
differentReal LLM-judge scoring (DeepEval) is live in production, not just offline eval. No documented human-agreement validation pass exists to calibrate the judge against - trusted as-is, a solo project with no second annotator to compare against (an honest, factual limitation, not a gap to silently assume away).
Retrieval finds the right chunks but users still get wrong answers - where's the problem?
  • In the prompt or generation step, not search. Check groundedness specifically - common causes are the model preferring its own knowledge over the provided text, or the key chunk being buried in the middle of a long prompt where it gets less attention.
builtDirectly diagnosable here - groundedness is scored separately from context relevance on every answer, so this exact failure mode (good context, bad groundedness) shows up as a number, not a guess.
How would you test a RAG change before showing it to users?
  • Run it against the offline test set first - stop if it loses there. Shadow it (serve the old version, run the new one in parallel, score both on the same real questions, no user risk), then a small percentage of real traffic, with guardrails that auto-stop the test on errors/latency/refusal-rate spikes.
differentThe offline-test-set step is real and wired into CI (eval-gate.yml, manual trigger, Phase 80) - a genuine PASS/REVIEW/BLOCK gate before a release is considered safe. No shadow-testing or percentage-rollout infrastructure exists; a change that passes the gate ships fully, not gradually.
You have no labelled data for a brand-new domain, and your eval harness needs to prove it actually catches regressions - how do you know it works?
  • Deliberately break something (remove a document, corrupt a chunk) and confirm the harness's score actually drops - an eval harness that never fails on a known-bad case isn't proving anything.
builtVerified for real, not hypothetically - the golden-dataset harness was confirmed to score 0.00 on a 401(k) question specifically because 3 of 6 KB documents were missing from the index at the time (a real incident, BACKLOG.md), proving the harness does catch a real regression rather than always reporting green.
