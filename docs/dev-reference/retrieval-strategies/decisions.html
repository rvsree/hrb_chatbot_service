RS-1rank_bm25 for keyword search, not a managed hybrid-search vector DB feature
Context
Some vector DBs (Pinecone included) offer their own managed hybrid/sparse-dense search. This project built keyword/hybrid search itself instead, with the standalone rank_bm25 library.
Decision
Plain BM25 lexical ranking via rank_bm25, combined with vector results via Reciprocal Rank Fusion, computed in this project's own code - not a vector DB's built-in hybrid feature.
Alternative
Use Pinecone's own sparse-dense hybrid search support - would remove the need to load the full corpus per query, but ties the implementation to one specific vector DB's own API, breaking the gateway-backed "swap providers freely" pattern this project uses everywhere else.
Why
Matches the IK FDE course's own workshop approach (per the module's docstring: "the workshop's own choice") - courseware fidelity, not re-derived independently this round.
Trade-off
Real cost: BM25 needs the full corpus text per call, re-tokenized every time, rather than a persistent index a managed hybrid feature would maintain - a genuine scaling concern flagged in Design, not hidden.
RS-2A GatewayChatModel adapter instead of LangChain's own per-provider packages
Context
MultiQueryRetriever/SelfQueryRetriever need a real LangChain BaseChatModel - LangChain ships per-provider packages (langchain-openai, langchain-anthropic, etc.) that implement this directly.
Decision
A small adapter (GatewayChatModel, common/clients/llm_client/langchain_chat_model.py) wraps this project's own existing multi-provider ask() clients instead of adding LangChain's own per-provider packages.
Alternative
Add the real per-provider LangChain packages - more "native" to LangChain's own ecosystem, but per CLAUDE.md's own recorded reasoning, ran into a real dependency conflict that ruled them out (full detail in RAG-ROADMAP.md's Phase 20 entry, not re-derived here).
Why
One adapter over this project's own existing gateway keeps provider selection consistent everywhere (the same LlmProvider enum, the same gateway pattern) instead of two separate provider-selection mechanisms existing side by side.
Trade-off
The adapter only implements as much of LangChain's BaseChatModel interface as these 2 retriever classes actually need - not a general-purpose drop-in replacement for every LangChain integration this project might want later.
