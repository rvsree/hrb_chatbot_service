Scaling & Latency Design

How this project's own request chain spends its time today, what actually helps at each layer, and what changes once agentic-rag adds multi-step tool calls on top. Written for the "how do you scale an AI system beyond Docker/Kubernetes" interview question.

Guardrails tripled the LLM call count per query (input check, generation, output check - all real gpt-4.1-mini calls), each one a full network round-trip. This is the single biggest lever in this project's own latency story, and it's a direct consequence of Phase 7 landing - not a hypothetical.
Run checks in parallel, not sequentiallynot built

The output guardrail can't start before generation finishes (it checks the answer), but nothing requires the input guardrail and the embedding call to run one-after-another - they read the same query, independently. A true win only shows up once independent steps are actually awaited together.

Stream the generation responsenot built

Today the client waits for the full answer before anything renders. Streaming tokens as they're generated makes the perceived latency the time-to-first-token (~500ms-1s), not the full 2-4s - the actual work doesn't get faster, but the wait feels shorter.

Cheaper model for guardrail checksnot built

Guardrail checks are yes/no safety classifications, not open-ended generation - they don't need the same model tier as the actual answer. A smaller/faster judge model for self_check_input/self_check_output shrinks two of the three LLM legs.

Token logging is already therelive

Every client (openai_client.py, anthropic_client.py, open_router_client.py) already logs prompt/completion tokens per call - the raw data for a real latency/cost dashboard exists today, just not visualized yet.

2
Caching layers what caching actually saves at each stage - and where it can't help
Embedding cacheknown gap

Same query text embedded twice pays the embedding-API cost twice. A hash-of-query -> vector cache removes that - flagged in this session's own IK courseware self-audit, not yet built.

Semantic response cachenot built

Near-duplicate questions ("what's the 401k match" vs "how much does the company match on 401k") could reuse a prior full answer if judged similar enough - higher payoff than embedding caching, also higher risk of serving a stale/wrong-context answer.

Retrieval cachenot built

Cache the vector-search result for a query hash, skip re-querying Pinecone/Chroma on a repeat. Cheap to add, but retrieval is already the smallest slice of the latency budget above - low leverage compared to caching the LLM calls.

What caching can't touchby design

Guardrail checks and generation both depend on the live query text and retrieved context - caching helps repeat or near-repeat questions, not the first time any specific question is asked. It shrinks the tail, not the floor.

3
Horizontal scaling why this API can safely run many replicas, and what would break it
Already stateless-safelive

Every request carries its own identity (user_profile) and every dependency (LLM, vector DB, metadata store) is an external service reached through a gateway - no in-process session state to keep replicas in sync. Any number of App Runner instances can serve requests interchangeably today.

App Runner autoscalinglive

The deployed service already runs on App Runner (see docs/agent-reference/AWS-DEVOPS-RUNBOOK.md), which scales instance count off concurrent request volume automatically - no separate Kubernetes/ECS layer needed for this project's current scale.

What would break itwatch for this

Adding an in-memory cache, an in-memory rate limiter, or agent conversation memory that isn't backed by an external store (Redis, Postgres) would silently break horizontal scaling - a second replica wouldn't see the first replica's state. Worth flagging explicitly before agentic-rag's memory work starts.

Postgres metadata storenot yet live

Code is fully implemented (Phase 2.5) but the deployed service still runs on SQLite - blocked on provisioning a hosted Postgres (Neon), not on code. SQLite doesn't handle concurrent writers from multiple replicas safely; this becomes a real blocker the moment there's more than one instance writing metadata.

4
Async decoupling for ingestion why the write path (upload/index) and read path (query) should scale independently

Today, ingestion is synchronous and in-request: a document upload blocks on extract -> chunk -> embed -> index, all in the same HTTP call (ai/doc_processing/pipeline.py). That's fine for one document at a time, but it means a large batch upload ties up a request thread for as long as indexing takes, and couples query-path scaling to ingestion-path load.

One open design question, not yet resolved: the existing docs/agent-reference/S3-ASYNC-UPLOAD-DESIGN.md has S3 events triggering Lambda directly, with SQS used only as a dead-letter queue for failed Lambda invocations. Batch processing (queuing many documents, controlling concurrency, retry-with-backoff across a large upload) genuinely wants SQS as the main queue between S3 and Lambda, not just the DLQ - that's a real change to the existing design doc, worth deciding deliberately rather than drifting into during implementation.
5
What changes once agentic-rag lands the same latency/scaling questions, with a multi-step loop instead of one pass
Latency multiplies, not addswatch for this

A ReAct loop that calls 3 tools sequentially before answering isn't "generation + a bit more" - it's several more full round-trips, each with its own guardrail exposure if guardrails wrap every step. The waterfall in section 1 becomes a loop, not a line.

Parallel tool calls, where independentnot built

If an agent decides to check two unrelated tools (e.g. a benefits lookup and a PTO balance lookup), running them concurrently instead of one-after-another is the single biggest lever once tool-calling exists - same principle as the input-guardrail/embedding overlap in section 1, at a bigger scale.

Timeouts and circuit breakersnot built

A single slow LLM call today just makes one query slow. A stuck tool call inside a multi-step agent loop can hang the whole interaction - each tool call needs its own timeout and a circuit breaker so one bad tool doesn't take down every agent request using it.

This is when LangSmith earns its keepalready built, off

Tracing is built and toggled off today because a single retrieve-then-generate pass has little to trace. A multi-step agent loop is exactly the case tracing exists for - debugging "why did the agent call tool B instead of tool A" without a trace is close to impossible.

6
How real systems approach this industry reference points - clearly separate from what's built here
Model cascading Route the easy/cheap classification calls (like guardrail checks) to a small fast model, reserve the expensive model for the actual generation step - the same idea flagged as "not built" in section 1's guardrail-model card, generalized.
Speculative retrieval Start the vector search before the input guardrail check finishes, since they read independent inputs, and simply discard the retrieval result if the guardrail blocks the query - trades a little wasted work for a shorter worst-case path.
Read replicas for the vector DB Managed vector DBs (Pinecone, already this project's live backend) handle this internally; a self-hosted Chroma at real scale would need its own replica strategy, which is exactly why the managed option was chosen for production here.
Backpressure over autoscaling alone Autoscaling (App Runner today) handles smooth load growth well but not sudden spikes or a slow downstream dependency - a queue in front of expensive work (ingestion, batch eval) absorbs bursts instead of scaling infrastructure to match every spike.
Cost and latency are the same lever Every technique above (smaller judge model, caching, streaming) reduces both at once - in an LLM-backed system, unlike a traditional API, latency and per-request cost are rarely separate problems to solve independently.
7
Infrastructure at scale - databases, security, load balancing, logs, tracing system-level, not feature-level: what each piece of shared infrastructure needs as the user base grows
Postgres (Neon) - metadata + sessionslive

Production now runs RAG_METADATA_STORE=postgres against a real Neon database (HR_Benefits), not SQLite - schema-per-bounded-context (hrb_chatbot_v2_core/_sessions, hrb_emp_lms, hrb_lms_mcp_auth), no cross-schema FKs, matching this project's gateway-per-backend pattern. Real gotcha already hit and fixed: Neon's pooled connection endpoint (PgBouncer, transaction mode) can silently remap a logical connection to a different backend process between transactions - session state set once on connect doesn't survive that remap. At real concurrent-user scale, the next lever is read replicas for the query-heavy conversation/feedback tables, not re-architecting the schema split.

Secrets managementlive

AWS Secrets Manager holds every API key/credential App Runner injects at runtime (hrb-chatbot/* prefix, 5 secrets) - nothing sensitive is a plain App Runner environment variable. Scales fine as more secrets are added; the real limit is operational (rotating a secret still means a manual redeploy today, no automated rotation policy).

Identity / RBACknown limitation

Documented elsewhere, worth repeating in a scaling context: require_role() reads an unsigned, caller-supplied user_profile straight from the request - a formality, not real authentication. This doesn't get worse with scale (it's equally weak at 10 or 10,000 users), but it does mean rate limiting and input guardrails are currently the only real abuse controls - real OAuth2 (human-to-app, still design-only, see docs/dev-reference/auth/oauth2-auth-architecture.html) is the actual fix, not a scaling one.

Rate limitinglive, horizontally-safe

Redis-backed (Phase 84, rate_limiter.py) - fixed-window counters via INCR/EXPIRE against Upstash, replacing an earlier in-memory version that only worked single-process. Already correct for the "many stateless replicas" model this whole doc assumes (section 3) - no further change needed to scale this specific piece, only to tune the actual request-count thresholds as real traffic is observed.

Load balancinglive, managed

App Runner's own managed load balancer fronts every instance today - no separate ALB/NLB to provision or scale. This covers single-region traffic distribution across replicas; it does not cover multi-region failover or geographic routing, which would need Route 53 plus a second region's own App Runner service - not a current requirement at this project's real scale.

Logslive, but basic

App Runner ships stdout to a CloudWatch log group automatically - fine for today's single-service, low-volume debugging (see AWS-DEVOPS-RUNBOOK.md's "Reading App Runner logs"). No structured log aggregation, search, or alerting (ELK/Datadog/CloudWatch Insights dashboards) yet - once there's more than one container to correlate across (section 8), grepping one log group stops scaling as a debugging strategy.

LangSmith tracingbuilt, off by default

Wired in (common/observability/langsmith_tracing.py) but LANGSMITH_ENABLED=false by default to stay inside the 5,000-trace/month free tier - an all-or-nothing toggle today. The real scaling gap: LANGSMITH_TRACING_SAMPLE_RATE is documented in .env.example as "not yet wired" - sampling a fraction of calls, not flipping tracing fully on or off, is what makes this affordable once query volume actually grows past hobby-project scale.

8
Per-service container scaling one service today runs everything - what independent scaling actually requires

Today, hrb_chatbot_v2's single Docker image serves every route - chat queries, document upload/ingestion, admin, leave workflow - as one App Runner service, scaling as one unit even though these workloads have nothing in common: a large PDF batch upload is CPU/IO-bound and bursty, a chat query is LLM-latency-bound and steady. hrb_lms_mcp already proves the alternative works in this project: it's its own separate App Runner service (Phase 118, live at hrb-lms-mcp.rvsree.dev), scaling independently of the chat API that calls it over real OAuth2 client-credentials auth, not in-process.

Query API stays App Runnerlive

The chat/query path is already stateless (section 3) and already runs on App Runner's own autoscaling - this is the one piece that doesn't need to change shape, only to shed the workloads below that don't belong on its scaling curve.

Ingestion as its own compute unitdesigned, not built

Section 4's S3 -> SQS -> Lambda path is exactly this pattern, made concrete: a document upload surge spins up Lambda concurrency independently, never competing with query-path App Runner instances for CPU - today both share the same container, so a big batch upload can slow down unrelated chat queries.

MCP server as proof of the patternlive

hrb_lms_mcp is already deployed, containerized, and scaled separately from this project's own API - the Dockerfile mirrors hrb_chatbot_v2's own two-stage build (see AWS-DEVOPS-RUNBOOK.md-style pipeline), proving the per-service container approach isn't hypothetical here.

Frontend needs no container at alllive

hrb_chatbot_ui is a static Vite build on S3 behind CloudFront (Phase 117) - it scales by CloudFront's own edge caching, not App Runner instances, and has zero compute cost to provision as traffic grows.
