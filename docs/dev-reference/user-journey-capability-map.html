ΣWhat the journeys actually demand, not assumed up front

Reading top to bottom: journeys 1-2 justify rag_retrieval_service as one capability (static + live data, same conversational path). Journey 3 proves it needs durable, days-long async state, not just request/response. Journey 4 proves rag_ingestion_service is a genuinely different traffic shape and deserves its own service. Journey 5 proves platform/admin is its own concern with zero LLM involvement. Journeys 6-7 prove the future services (employee_401k_service, chat_audio_service) extend the system by composing with what exists, not by duplicating it.
