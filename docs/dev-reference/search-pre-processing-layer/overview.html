Search Pre-Processing Layer

The thin layer between the Gateway and RAG/CAG/Agent pipelines - intent classification, CAG-vs-RAG-vs-Agent routing, and context assembly (user profile, STM/LTM, feedback). Formalizes six files that already existed as scattered pieces into one coherent layer with a clear boundary.

Overview Spec Architecture Design Decisions

Purpose

Today, a query arriving at the Gateway goes straight to whichever pipeline the caller explicitly named - the caller does the classification work itself by picking a dropdown option. This layer takes that job away from the caller: one entry point that reads the query, decides whether a cached answer already exists (CAG), which pipeline should handle it if not (Reflex Agent vs. Agentic Workflow - Phase 240), and assembles everything that pipeline needs to know about this request (who's asking, what they've said before, how they felt about the last answer) before handing off.

Scope

Covers three responsibilities, each already partly built as its own file under ai/search_pre_processing/ (renamed 2026-10-21 from ai/pre_processing/ - the old name undersold what it's becoming): intent classification (query_decompose.py, feeds Phase 240's router), CAG-vs-RAG decision (new - the cache-check logic currently inlined in pipeline.py, extracted here), context assembly (conversation_memory.py, context_builder.py - STM/LTM, user profile, feedback signals, real split detailed in Design).

Does not cover guardrails' own pass/fail logic (guardrails_input.py stays a sibling file, called by this layer, not merged into it - its job is safety, not routing) or the generation pipelines themselves (RAG/CAG/Agentic Workflow stay exactly as they are, just invoked by this layer instead of invoked directly by the Gateway's forward).

High-level workflow

  1. 1Query arrives from the Gateway, forwarded unchanged (identity, conversation_id, query text).
  2. 2Context assembly - fetch STM (this conversation's recent turns, fast), check for a recent feedback signal, read the user profile.
  3. 3Intent classification - decompose/normalize the query, decide its shape (simple lookup vs. multi-domain).
  4. 4CAG check - exact-match cache lookup; a hit returns immediately, skipping steps 5-6 entirely.
  5. 5Routing decision - on a cache miss, pick Reflex Agent or Agentic Workflow (Phase 240) using the classification from step 3.
  6. 6Hand off to the chosen pipeline with the assembled context attached - the pipeline itself doesn't re-fetch any of this.

Where this fits

Lives inside today's hrb_chatbot_service, and - per the Interface Matrix's own boundary rules - stays inside rag_retrieval_service once the microservices split happens. It's business logic (routing decisions need RAG-domain knowledge), so it was never a Gateway candidate.
